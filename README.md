# 销售标准管理 · CRM 项目章程（路线 B：TS + NestJS 全栈）

> 本文档是 AI 协作开发的"交通规则"。每次让 AI 改代码前，先读它。

## 一、技术栈定案（2026-09-05 决策）

- **后端**：NestJS 12（Node + TypeScript）+ MySQL 8 + Redis
- **前端**：Vue 3（TypeScript）+ Vite + Element Plus
- **全栈统一语言/类型**：前端与后端共用一套 TypeScript 类型，来源是后端 OpenAPI（Swagger），由 `openapi-typescript` 生成到 `frontend/src/api/types.ts`。**禁止手写对接、禁止前后端各维护一份接口类型**（双真相源是 AI 出错重灾区）。
- **数据库为唯一真相源**：DB 约束（唯一索引、CHECK、生成列）兜底业务不变量；应用层只做"友好提示"，不替代约束。
- **ORM 待定**：TypeORM 或 Prisma 二选一（见第七节待确认项）。骨架阶段用 Repository 接口 + 内存 Fake 验证业务逻辑，不锁定具体 ORM。

## 二、抑制 AI 错误的四道闸（按杠杆排序）

1. **数据库约束兜底**：唯一索引（撞单/激活冲突）、CHECK（审批人≠申请人）、生成列（active_key）。→ 挡"撞单、重复激活、自批"。
2. **类型安全贯穿前后端**：后端 DTO（class-validator 运行期校验）+ 前端 TS + OpenAPI 生成共享类型。→ 挡"字段拼错、枚举乱传、接口错位"。
3. **自动化测试当护栏**：每条业务铁律写单测/集成测，CI 必跑（当前本地 `npm test`）。→ 挡"公海规则、掉海判定、状态机错乱"。
4. **人工 SME 复审闸**：关键模块（业绩/提成/掉公海/脱敏）上线前由你走查关键流程。→ 挡"逻辑语义错"（类型与测试都挡不住这类）。

> 第 4 点是 solo + 不读代码者的"第二道防线"：你读 TS（JS 超集，Vue 即用 TS）可扫结构；但业务正确性最终靠测试 + 你给的"验收检查点"。

## 三、Git 分支策略（防 AI 改错无法回退）

- `main`：受保护的基线分支，只放"已评审通过"的状态。初始化时提交需求文档（见下方"基线例外"）。
- `dev`：集成分支，各模块测试通过后的合并目标。
- `feat/<模块名>`：AI 每开发一个模块，从 `dev` 切一个 feature 分支（如 `feat/business-relation`）。改完 + 测试绿 → 合并回 `dev`。
- `feat/doc-<主题>`：纯文档改动（章程 / 需求 / 方案对比 / 核查报告 / 构想图 / 归档等）从 `dev` 切文档分支（如 `feat/doc-branch-strategy`）。文档不跑单测，但**同样禁止直接落 `main`**，合并前由七叔走查（或 AI 给出变更摘要供确认）。
- 里程碑打 tag（如 `v0.1-mvp-org`）。
- **铁律**：AI 绝不直接往 `main` 写；任何大改都在 feature 分支，出问题 `git reset` / 删分支即可回退。
- **基线例外（一次性，不再适用）**：本仓库初建为快速搭骨架，commit `c0be033`（.gitignore）、`354b5f3`（后端骨架 + 前端桩 + 原型）及"文档体系（§九 §十 + 本节）"三次基线提交直接落在 `main`，属**初始化一次性例外**（含本节自身的落地）；自本规则生效起，包括文档在内的所有改动一律走 `dev` + `feat/*` 流程，不再开例外。

## 四、spec-driven 开发流程（AI 每次按此顺序）

1. 锁需求（已有：销售CRM开发需求/前端需求/接口API/数据库设计 四份文档）
2. 锁 DB Schema 为唯一真相（《数据库设计文档》V1.1，约 34 张表，以该文档为唯一表结构真相源）
3. 后端按模块实现 + 写铁律单测（当前阶段，Repository 用 Fake 验证逻辑）
4. 从 OpenAPI 自动生成前端类型（`npm run gen:types`）
5. 前端按类型开发
6. 你用浏览器走查 + 勾验收检查点
7. 通过后合并 `dev`

## 八、需求变更全文档对齐规则（铁律）

**触发**：任何需求变更（新增/修改/删除功能、字段、流程、规则），经七叔确认后生效。

**对齐动作（强制）**：变更确认后，必须同步审视并修订**所有相关文档**，不允许"只改一处、别处漂移"：

1. **级联优先级**（冲突时以上游为准，并在下游标注）：
   - ① 业务规则 → 《销售CRM开发需求.md》（V2.0）为最高事实来源
   - ② 表结构 → 《数据库设计文档》（V1.1）唯一真相源
   - ③ 接口端点 → 《接口API文档》（V1.3）
   - ④ 页面与字段 → 《前端页面开发需求文档》（V2.5）
   - 关联文档：《技术栈方案对比》《销售CRM项目摘要-给老板看》同步更新摘要与结论
2. **不变量**：① 技术栈以本文档（路线 B：NestJS 12）为准；② 工作流以 6 步状态机为准；③ 台账扩展字段以 `field_template` + `ledger.extra_fields` JSON 为准；④ 意向跟进体系以 V1.1 的两字段正交（进度≠紧迫）+ 两轴（客户等级≠业务线价值）为准。
3. **留痕**：每次对齐在涉及文档顶部"修改记录"补一行（版本/日期/改了什么）；重大变更打 `git tag`。
4. **校验**：变更落地后，重新跑一次"需求一致性核查"（见《需求一致性核查报告》），确认无新漂移再合并 `dev`。

> 目的：让"同一事实在任意文档只有一种说法"，避免开发按过期描述实现。

## 十、文档时态与状态规则（2026-09-08 定）

**核心原则**：用"文档位置"作为唯一时态信号——**现行有效文档留在用途目录，过去时 / 被取代文档移入根目录 `归档/`**。七叔翻阅文件夹时，四个用途目录里只该看到进行时文档；历史文档沉到 `归档/`，不干扰日常。

> 本规则能成立，依赖 §九 铁律②：文档间以"标题 + 版本号"互引、不依赖路径。因此把文档从用途目录挪到 `归档/` 不会断任何引用——两条规则配套。

**四态定义**：

| 状态 | 位置 | 含义 |
| --- | --- | --- |
| 草稿 | 用途目录（标题注明「草稿」） | 未确认，可能大改 |
| 现行有效 | 用途目录 | 当前生效，被引用为真相 / 依据 |
| 已归档·历史 | `归档/<用途>/` | 功能作用已完结，备查不常用 |
| 已废弃·被取代 | `归档/<用途>/` | 被新版取代，地图标注取代者 |

**归档触发（铁律）**：

1. **不自动归档，绝不因"放着久了"归档。**
2. 当某文档的"功能作用"已完成（如：方案对比已出决策、一致性核查的整改已落地），**AI 主动提问七叔"是否归档"，由七叔拍板**；七叔确认后才挪入 `归档/`。
3. 出现新版本取代旧版时，同理先问七叔，确认后旧版入 `归档/` 并在文档地图标注"被《新文档 Vx》取代"。
4. 归档 = 移动，**绝不删除**；移动后引用按 §九 铁律② 自动成立，无需改链接。
