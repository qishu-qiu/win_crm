## 二、设计总纲：一份事实账本，三个出口

本架构只回答一句话：**系统是销售的助理，不是销售的监工，也不是老板的收银机。**

核心结构：

```
        销售出口（干活用）          经理/老板出口（看盘用）          客户出口（履约用）
  「吃我说的」我认账          「吃我留下的」被动算           「吃承诺与节点」自动触达
 承诺到点提醒 / 今天该找谁     队伍健康度 / 客户盘子处境       履约通知 / 续约提醒 / 服务回访
 一句话档案 / 少填表          掉海风险榜 / 回款与转化          （V1 可后置，架构预留）
        ▲                              ▲                              ▲
        └──────────────┬───────────────┴──────────────┬───────────────┘
                       ▼                              ▼
              CRM 引擎 · 一份事实账本（本架构全部数据表）
    承诺 · 预约 · 事件流(跟单/客情) · 业务关系 · 公司档案 · 合同回款 · 工单
```

### 设计五铁律（任何新需求先过这五条）

| # | 铁律 | 白话 | 违背后果 |
|---|---|---|---|
| T1 | **加规则 = 加行，不是加列** | 新判断/新节奏/新提醒一律写进配置表（cadence_rule / dict / field_template），`business_relation` 等主表**永不新增判断列** | 表越加越胖、销售被迫维护一堆状态（旧版教训） |
| T2 | **录入摩擦趋近于零** | 销售干活时 10 秒顺手留（挂电话勾一句、顺手约时间）；**任何"为让系统/经理好看"而设的必填项一律砍掉** | 销售变文员，数据变假 |

> **T2 唯一例外（出口复盘点选必填）**：判死 / 流失出口必须点选一次死因（30 秒、该客户一辈子只判死一次、错过时机不可补、且直接决定公司"客户为什么不要我们"的战略数据）。**文字永不强制**。此例外全架构仅此一处，新增任何必填必须先过 §十八 评审。
| T3 | **经理出口只吃"留下的"，不吃"填的"** | 报表统计只从事件流/回款/工单被动聚合；**绝不要求销售确认处境、点卡点、填报表字段** | 销售为老板打工，系统成负担 |
| T4 | **推导只建议，销售说了算** | 系统推导（阶段推进、处境、价值）一律"建议态"，销售一键接受/拒绝；拒绝留痕可反哺规则 | 系统自作主张，销售不信任 |
| T5 | **停用不删** | 表/字段/字典项/字段模板停用后保留（disabled），历史数据照常展示，物理删除仅限草稿态 | 历史断裂、追责无据 |

### 本架构相对"档案式思路"的五个关键调整（理念对照，非系统迁移）

1. 承诺从"跟单里一段自由文本"升格为**一等实体**（commitment）——系统能回答"答应客户什么、何时兑现、办没办"。
2. 跟单从"单张记录表"演进为**事件流**（action_event）——业务互动、客情动作、@同事求助、系统事件统一沉淀，支持自动落账。
3. 处境/健康度等"判断"**不建表、不落库、不要求销售维护**，全部由事件流被动统计得出（经理出口）。
4. 阶段（客观进度）由销售在写事件时**顺带推进**（建议态+一键确认），不再独立填表。
5. 客情动作（请客/送礼/问候）成为独立动作类型，与业务跟进分轨，支撑"老钱罐别冷落"。
6. 竞品不再是一句"写在 summary 里的背景"：**每次写跟单事件可顺手标记**"这单有竞品吗 / 是哪家 / 什么情况"，关系表的竞品态势字段只是**最近一次标记的快照**（录入只在事件、列表读取在关系）；策反/防守/竞争关系**推导只读**，销售零单独标注负担。
7. 经验继承靠"**出口复盘**"（转已合作 / 判死 / 流失三个出口的顺手一问），**不是独立复盘作业**：win 由系统自动建档、经理主导决定是否沉淀入弹药库（本部门可见，总经理可设全公司）；loss 判死死因必选、文字缓写；churn 已合作流失统一出口（被撬/到期未续费等均为原因标签），高价值流失经理介入回访。

## 三、业务核心术语（大白话 ↔ 系统映射）

| 术语 | 系统落点 | 大白话 |
|---|---|---|
| 公司档案 | `company` + `company_profile_tag` | 一家客户公司一份，身份/制度/决策链建档勾一次全公司共享 |
| 业务关系 | `business_relation` | "我负责这家公司的法律线"——最小业务单元，谁×哪条产品线×归谁管 |
| 联系人 | `contact` + `company_contact` | 人；手机号唯一撞单核心；就职关系可跨公司留历史 |
| 客户等级 | `business_relation.customer_level`（S/A/B/C/D，**自动算**） | 回款贡献 = 这客户一年给我多少钱；S=头部大额老钱罐 |
| 开发价值 | `business_relation.value_tier`（high/medium/low/pending） | 实力×契合度 = 这客户还值不值得我挖，与等级**两套轴** |
| 进度（阶段） | `business_relation.stage_id` → 6 步状态机 | 客观事实：谈到了哪一步 |
| 紧迫（计划档） | `business_relation.urgency`：weekly 周重点 / monthly 月重点 / quarterly 季度跟 / long_term 长期跟 / gray 灰度(默认) | 主观计划：我打算多快拿下它；**周重点=本周要有动作（标记即承诺本周）** |
| 灰度 | urgency=gray | 还没下结论的客户；超期不定性走"灰度寿命"提醒 |
| 承诺 | `commitment` | 心脏：我答应客户 X / 客户答应我 Y / 我定本周判 Z；有期限、有状态 |
| 事件/跟单 | `action_event` | 已发生的互动：电话/微信/拜访/请客…一句话留痕，是统计唯一来源 |
| 卡点 | 字典 `pain_point` + `action_event.pain_point_id` | 客户卡在哪（价格/效果/信任/见不到人/时机…）可选点选 |
| 客情动作 | `action_event`(action_type=meal/gift/greeting) | 请客/送礼/问候——维护关系，不是推进成交 |
| 预约 | `appointment` | 定好时间要见/要办的事，完成必须留一条事件 |
| 今日动线 | `daily_agenda` | 每天清晨系统排好"今天该花时间在谁身上"（工作台首页数据源） |
| 协同 | `relation_member.member_type=collaborator` | 共同跟进（可共同写事件、全文可见、全号）；**正式协同走审批**；**@求助 = owner 即时授予的临时协同，权限一致**（限时、可收回） |
| 公海 | `sea_rule` + `sea_record` | 无主客户池；掉海原因/领取历史全留痕 |
| 竞争并行 | 跨部门同产品线同客户 | 各跟各的、事件互不可见，谁先签约谁得 |
| 客户坐标 | `company.longitude/latitude` | 公司在哪。建档时人工用高德坐标拾取器点选，非必填；地图类应用后续由程序实现 |
| 竞品态势 | `action_event.competition/competitor_id`（每次跟单顺手标记）+ `business_relation.competition`(最近一次快照) | 客观事实：这客户**没竞品 / 在用某竞品 / 正在比价**；在跟单事件里顺手点，不是独立判断 |
| 竞品关系（策反/防守/竞争） | 系统推导（只读，不落库） | 未合作×在用竞品=**策反**；未合作×比价/无竞品=**竞争**；已合作=**防守**。系统自己读出来，不要求销售打标 |
| 流失 | `review`(type=churn) + 原因标签 review_churn_reason | **已合作客户没了**：被竞品撬走 / 到期未续费 / 服务不满 / 我们疏忽…都是同一类"流失"，只是原因标签不同 |
| 出口复盘 | `review` | 三个"出口动作"上的顺手一问：转已合作（win 经理主导沉淀）/ 判死（loss 死因必选）/ 流失（churn 原因标签+高价值回访） |
| 赢单弹药库 | `review`(type=win, status=published) | 经理决定收录的赢单打法，**默认本部门可见**，总经理可设全公司——把销冠脑子里的经验变成公司资产 |

**业务信条（不落表，但影响所有设计）**：不存在吊着我们的客户，吊着的都不是意向。真实意向只有两种卡点——**见不到人** / **犹豫效价**。

## 四、ER 总览

```
department ─┬─< employee >─┬─ employee_role ─ role ─ permission_matrix
            │              └─ dept_manager（管辖 N:M）
            └─ dept_rule（等级档位/灰度寿命/节奏默认，部门经理配）
system_config（gm 级全局开关：弹药库可见范围等）
product_line ─┬─< field_template（台账扩展字段元数据）
              └─< sea_rule（公海规则 L1-L4）

company ─┬─< company_contact >─ contact ─ contact_change_log
         │                        └─ contact_trait（谈判特质 ≤3）
         ├─ company_profile_tag（身份/制度/决策链，打标人留痕）
         ├─ 地理信息（longitude/latitude GCJ-02 + 精度/来源/状态，自动解析）
         └─< business_relation ─┬─ relation_member（owner / collaborator）
                                 ├─ relation_stage_log（阶段推进留痕）
                                 ├─ relation_label（风险等人补标注，留痕）
                                 ├─< appointment（预约）
                                 ├─< commitment（承诺 ★心脏）
                                 ├─< action_event（事件流 ★谁·何时·对谁·结果）
                                 ├─< contract ─< payment_record
                                 ├─< workorder ─< workorder_log
                                 └─< sea_record（入公海历史）

commitment ─< daily_agenda（今日动线，ref 承诺/预约/节奏）
cadence_rule（节奏规则：经理配；含掉海/新客/S级客情/灰度）
competitor（竞品名册：经理维护，销售只读引用）
review（出口复盘 ★转已合作/判死/流失：经理是弹药库收录闸门）
approval（转交/协同/手机号变更/手机号解锁 四型一单；报销一期不做）
notification（站内/微信预留；三出口都会写）｜ dict_type ─< dict_item
operation_log（操作留痕）｜ visit_log（外出登记：纯行政考勤，不产生业务事件）
```

## 五、域 A：组织与权限

### A1 department 部门
`name`、`parent_id`(0=根)、`service_enabled`(客服开关)、`status`(active/disabled)

### A2 employee 员工
`work_no` UNIQUE、`name`、`phone` UNIQUE、`password_hash`、`primary_dept_id`、`extra_dept_ids` JSON、`product_line_ids` JSON、`direct_manager_id`(直属经理/审批链)、`status`(active/resigned/disabled)

### A3 dept_manager 管辖部门（经理查数范围 = 本表集合）
`dept_id + employee_id` 联合唯一

### A4 role / A5 employee_role
- role：`code`(sale/service/delivery/admin/dept_manager/gm) + `name` + `is_builtin`；内置 6 条，builtin 不可删
- employee_role：`employee_id + role_code` 联合唯一（一人多角色）

### A6 permission_matrix 权限矩阵
`perm_key`(如 cross_dept_private / contract_amount / phone_unlock) × `role_code` → `level`(visible/masked/denied)

### A7 product_line 产品线
`name/code` UNIQUE、`dept_ids` JSON(承接部门)、`service_cycle_days`、`status`

### A8 dept_rule 部门规则（经理可配，写入留痕）
| 字段 | 说明 |
|---|---|
| dept_id UNIQUE | 适用部门 |
| level_tiers JSON | 客户等级金额档位 `[{level:S/A/B/C/D, minAmount}]`——**每部门各自定义**，回款到账事务内自动算等级 |
| gray_remind_days | 灰度 N 天未定性 → 提醒销售下结论（判定承诺） |
| gray_release_days | 再 M 天未动 → 列为公海释放候选，经理确认后释放 |
| s_social_days | S 级客户客情节奏默认间隔（建议 45） |
| newbie_first_follow_hours | 新联系人/新关系首次跟进窗口（建议 48h） |

### A9 notification 通知
`user_id`、`title/content`、`biz_type`(commitment_due/cadence/drop_warn/gray/approval…)、`biz_id`、`channel`(site/wechat 预留)、`read_at`；三出口都会写：销售出口提醒本人，经理出口推送预警，客户出口（预留）走站外。

### A10 operation_log 操作留痕
`operator_id`、`action`、`target_type/target_id`、`detail` JSON；激活/转交/审批/规则/字典/权限/字段模板等改动全量落。

### A11 dict_type / dict_item 字典
- dict_type：`code` UNIQUE + `name`
- dict_item：`type_id` + `item_code` + `label` + `sort` + `builtin`(内置不可删，可停用) + `status`
- 修改写 operation_log；系统内置字典种子见 §十六

### A12 system_config 系统级配置（全局开关，gm 可改，留痕）
`config_key` UNIQUE(如 `ammo_scope`: dept/company 赢单弹药库可见范围) + `value` JSON + `updated_by/updated_at`；写入留痕 operation_log。仅 gm/admin 可改，普通经理只读。

## 六、域 B：客户资产与公司档案（三层标签之①②）

### B1 company 公司（唯一档案）
| 字段 | 说明 |
|---|---|
| full_name | 公司全称，INDEX；查重（相似度应用层算） |
| credit_code | 统一社会信用代码 UNIQUE（可空；撞码强制使用已有档案） |
| industry_l1/l2、province/city/district、scale | 行业/地区/规模 |
| completeness_1/2/3 | 三档完善度 0-100（写入重算） |
| website/address/bank_name/invoice_title/tax_no | 成交后强制补组 |
| longitude / latitude | **经纬度** DECIMAL(10,6)/DECIMAL(9,6)，可空。建档时**人工调高德坐标拾取器点选**（不做地址自动解析，实战易错）；**非必填**，可后补。坐标系统一 **GCJ-02**（换底图时在出口层转，库内不变） |

### B2 company_profile_tag 公司档案标签（身份/制度/决策链）
`company_id` + `group_code`(company_identity_tag 多选 / company_policy_tag 多选 / decision_chain 单选) + `tag_id` + `tag_code`(冗余防字典改名) + `marked_by/marked_at`(打标人留痕)
- 联合唯一 `uk(company_id, group_code, tag_id)`；决策链每组仅 1 条（应用层保证）
- 建档人工勾一次、全公司共享、不随部门隔离；覆盖式更新，删除物理删行（留痕见 operation_log）

### B3 contact 联系人
| 字段 | 说明 |
|---|---|
| name / phone | phone **UNIQUE**（撞单校验核心） |
| wechat/email/gender/birthday | 联系方式 |
| decision_role | decision/influence/execute（决策/影响/执行） |
| tags JSON | 个人自由标签（爱喝茶/老板亲戚…），与谈判特质分栏并存 |
| trait_summary JSON | 谈判特质冗余（从 contact_trait 派生展示） |
| status | active/left/freelance |
| phone_frozen_until | 手机号变更审核冻结期（24h） |

### B4 contact_trait 联系人谈判特质（≤3）
`contact_id` + `trait_id/trait_code`(价格敏感/关系型/方案型/专业控…可自定义) + `marked_by/marked_at`
- 联合唯一；**每人 ≤3**（超出 422）
- 特质跟着人走（换公司保留），不随就职表

### B5 company_contact 就职关系（N:M 含历史）
`company_id + contact_id + is_current + joined_at + left_at + position`；一人多段就职全留痕。

### B6 contact_change_log 联系人变更留痕
`contact_id + field + old_value + new_value + approval_id`；手机号变更必须关联审批单。

### B7 地理坐标（只存字段，地图应用不在本架构定义）

- **就两个字段**：`company.longitude/latitude`，**不建独立地址表、不加状态/精度/来源/行政区划等任何附属字段**（2026-09-09 七叔拍板：只要经纬度）
- **一家公司一个地址一个坐标**（V1 单地址）
- 坐标一律**人工用高德坐标拾取器点选**，**不做地址自动解析**（实战易错）；非必填，可后补
- 坐标系统一 **GCJ-02**（高德口径）；将来换底图在出口层转换，库内不动
- 列表「**地址是否维护**」为**派生展示**：`address` 或 `longitude` 任一为空 → 显示"未维护"标记。**不新增字段、不建标签**（T3：系统能推导的不设字段）
- **地图展示 / 附近检索 / 顺路推荐等一律不在本架构定义**，属后续产品与程序实现范畴，方案确定后再回本文档补充

## 七、域 C：业务关系与归属协同

### C1 business_relation 业务关系 ★收敛（只留归属与两轴判断）
| 字段 | 说明 |
|---|---|
| company_id / dept_id / product_line_id | 三元组 |
| stage_id | 工作流阶段引用（6 步，客观进度） |
| urgency | **紧迫档**：weekly/monthly/quarterly/long_term/gray(默认)。纯手动、无自动降级；**标 weekly = 本周必跟名单，不自动生成承诺**（承诺是日级动作，周级名单生成日级承诺没锚点）；写事件时轻提醒"周重点勿忘"，周五 cadence 自动清点"本周周重点都动过没有" |
| value_tier | 开发价值档：high/medium/low/pending(默认空)。手动，愿意标才标。**不再设金额预估字段**——档位是"实力×契合度"的人判断，金额谁填都不准且无人敢信，只留一个软档位 |
| customer_level | S/A/B/C/D（回款贡献，**回款到账事务内按部门 dept_rule 自动算**，不手填；S=头部大额回款客户，如"每年大量回款的老钱罐"） |
| competition | **当前竞品态势快照**（可空=未知）：none 无竞品 / in_use 在用竞品 / comparing 比价中。**录入不在本表**——销售写跟单事件（D2）时顺手标记，事务内回写本快照；列表/推导读本字段。**不设"策反/防守/竞争"标签**——由本字段×stage 自动推导 |
| competitor_id 可空 | 关联 `competitor` 名册（最近一次标记的在用/比价对象）；同样由事件回写，可空=知道有竞品但没指名 |
| sea_status | private/dept_sea/company_sea |
| gray_release_at | 灰度寿命释放候选时间戳：命中 dept_rule.release_days 置位；经理确认释放后清空并转公海 |
| last_event_at | 最近一次 action_event 时间（含客情/求助/系统事件，语义宽于"跟进"），INDEX 供预警扫描 |
| next_action_hint | 可空：一句话"上次说好下次干嘛"（从最近承诺/事件冗余，销售出口展示用） |
| 唯一索引 | `uk_active_rel`：同 公司+部门+产品线 仅一条私海活跃关系（生成列 active_key 实现，私海=三元组，否则 NULL） |

> **T1 铁律落点**：本表不再新增任何判断列。判断一律走：承诺（行动）、cadence_rule（节奏）、事件流统计（健康度/处境）。

### C2 relation_member 关系成员（owner / collaborator）
| 字段 | 说明 |
|---|---|
| relation_id / employee_id | 关联 |
| member_type | **owner**（主责销售=该客户关系经营+维护第一人，1）/ **collaborator**（协同人：正式协同或被@求助者，多） |
| source | collaborator 的来源：`collaborate` 协同审批通过 / `ask_help` @求助即时授予 |
| valid_until | 仅 collaborator 用：协同有效期（到期自动失效，解除事件读写权与全号可见）；NULL=长期（仅正式协同） |
| added_by / added_at / revoked_by / revoked_at | 授予人/时间；撤销人/时间（owner 可随时收回 collaborator） |

**协同语义**：协同 = 共同跟进，不是临时标签。协同人拥有该关系下 action_event 的**共同读写权**与联系方式的**全号可见**。
- **正式协同**：owner 或经理发起、**审批通过**后写入（source=collaborate）；可长期（valid_until=NULL）或带期限。
- **@求助（ask_help）= 轻量临时协同（2026-09-09 七叔拍板：权限与协同一致）**：owner 写事件 @ 同事，**即时授予被@者与正式协同人相同的读写权与全号可见**（source=ask_help），默认 7 天自动收回（dept_rule.ask_help_days 可配）、owner 可随时撤销、全量留痕、**不需要审批**（喊帮忙要快）。想长期共同跟进 → 走正式协同审批，不把 ask_help 当常驻授权。

**主责变更（生病 / 离职 / 换人）**：客户经营主责**永远只有一个 owner**（谁在岗谁维护，合同签单人不等于维护人）。
- 换人维护 = **transfer 转交审批**（G1）变更 owner，全量留痕；
- 短期无法跟进（如病假）→ 授 collaborator(带 valid_until) 请同事代看，**不必转让所有权**；
- **离职**：管理员发起批量转交——其名下私海业务关系全部 transfer 给指定人（或回公海），已签合同 signer_id 不动（业绩历史归原签单人），后续维护自动归新 owner；离职交接支持分批确认。

### C3 relation_stage_log 阶段推进留痕
`relation_id + from_stage/to_stage + action(normal/jump/rollback/lost) + reason + operator_id`；跳级/回退/异议无解双出路（回落长期跟 or 判流失）全量落此表。

### C4 relation_label 关系级标注（风险等人补标签，取代散 JSON）
`relation_id + group_code(risk 风险 / other) + label_id/label_code + marked_by/marked_at + remark`；联合唯一 `uk(relation_id, group_code, label_id)`。
自动风险信号不落库，由规则从事件流实时派生只读回传（O16 风格）。

### C5 appointment 预约
`relation_id + contact_id + appointment_at + note + status(pending/done/rescheduled/expired_archived) + action_event_id`(完成时强制关联事件：**完成预约必留一条事件，服务端强制 422**)；改期留 `reschedule_log` JSON。

### C6 visit_log 外出登记（纯行政考勤，与业务解耦）
`employee_id + depart_at + expect_return_at + actual_return_at + destination + transport + note`；relation_ids JSON 可选（仅备注去了哪些客户）。
- **定位 = 行政考勤**：核对外出时间是否属实、外出是否合规（七叔：查外出时间的，与业务无关），**不自动产生任何业务事件、不关联报销**；
- 拜访客户后的业务结果由销售在预约完成（C5，422）或手动写 `action_event(visit)` 记录——两条路分开，行政不污染业务、业务不背行政包袱。

### C7 competitor 竞品名册（轻量主数据，非"竞品档案库"）
| 字段 | 说明 |
|---|---|
| name + product_line_id | 联合唯一 `uk(name, product_line_id)`——**竞品按产品线归属**（法律/财税/招聘的对手不是同一拨人） |
| positioning | 一句话定位（这对手卖给客户什么），**不是**价格表/功能对照表 |
| note 可空 | 补充（维护节奏：谁在更新、上次确认时间） |
| created_by / updated_by | 维护留痕；**只允许 manager/admin 维护，销售只读引用** |
| status | active/disabled（停用不删） |

> **为什么不是"竞品档案库"**：竞品价格/政策三个月一变，做成"库"让销售维护 → 录入者≠受益者，必腐（T2/T3）。名册只解决"客户在用谁、卡在谁手上"的**引用与统计**；"怎么打赢"靠 D6 赢单弹药库，按需沉淀、不预填。真正威胁统计（我们输给谁几次、被谁挖走）全部由复盘/事件被动聚合。

## 八、域 D：行动引擎 ★（助理版心脏：承诺 / 事件 / 动线 / 节奏 / 卡点）

### D1 commitment 承诺表 ★心脏
| 字段 | 类型/说明 |
|---|---|
| relation_id | 所属业务关系 |
| contact_id 可空 | 对着哪个联系人 |
| owner_id | 承诺人（销售本人） |
| party | **me**(我答应客户) / **them**(客户答应我) / **verdict**(我自己定的检查/判定点) |
| ctype | reply 给答复 / quote 发报价方案 / meet 约见面 / deliver 交付资料 / decision 判定去留 / followup 跟进 / social_meal / social_gift / social_greeting |
| content | 一句话承诺内容 |
| due_at | 到期时间（me/them 的兑现点；verdict 的判定日） |
| remind_at | 提醒时间（默认 due 当天清晨） |
| status | open / done / expired(逾期) / waived(豁免，注明原因) / cancelled |
| done_at / done_by | 兑现时间/人 |
| source_event_id 可空 | 由哪条事件产生（如跟单里说"明天发报价"） |
| closed_event_id 可空 | 哪条事件证明兑现（如发了报价那条，系统建议销项） |

- 索引：`idx(owner_id, status, due_at)`、`idx(relation_id)`
- 业务规则：
  - party=me → 到期提醒"你答应 X 的，办了吗？"，引导写一条事件即建议自动销项
  - party=them → 到期提醒"客户答应 X，去问一句"，语气是催客户不是催自己
  - party=verdict（判定）→ 灰度/判断题客户专用：到期动线提示"跟还是放，给个结论"；结论=推进阶段 或 判流失/回落长期跟，留痕 stage_log
  - 逾期未办 → 次日动线置顶标红；豁免必须填原因
  - **录入摩擦**：写事件时"有承诺吗？"默认无；有 → 三快选（我发资料 / 他给答复 / 约见面）+ 可选时间（默认明天），10 秒完成

### D2 action_event 事件流 ★（谁·何时·对谁·结果；取代单张跟单表）
| 字段 | 类型/说明 |
|---|---|
| relation_id | 必填 |
| contact_id 可空 | 跟谁互动 |
| actor_id | 操作人（销售或 system） |
| action_type | **phone 电话 / wechat 微信 / visit 拜访 / onsite 现场 / email 邮件 / meal 请客 / gift 送礼 / greeting 节点问候 / ask_help @求助 / note 纯备注 / system 系统** |
| summary | 一句话结果（销售说的人话，≤200 字） |
| outcome 可空 | 进展：advanced(有推进)/stalled(没推进)/await_reply(等客户答复)；空=中性 |
| stage_forward 可空 | 系统建议的下一阶段（有推进时提示"是否推进到 X 步"，销售确认后才落 stage_log）；**限频：同客户距上次阶段变更 ≥3 天 或 跨里程碑（进入面访/逼单等）才建议**，防高频打扰 |
| pain_point_id 可空 | 卡点字典项（可选，只在客户真卡住时点；**卡住必选主卡点+一句话补充**） |
| competition 可空 | **本次跟单涉及的竞品态势**：none / in_use / comparing；写事件时顺手勾（默认沿用上次），事务回写 business_relation.competition 快照。**UI 口径：折叠成一行"这单有竞品吗？"，默认"无"直接跳过、有才展开**（competitor_id + 一句话）——竞品对多数单子是低频事实，不许变成高频负担 |
| competitor_id 可空 | 本次标记的竞品（关联 `competitor` 名册）；可空=只知有竞品不知是谁 |
| competition_note 可空 | 竞品情况一句话（客户怎么说/对方什么动作），≤100 字 |
| duration_min 可空 | 本次投入分钟（算单位时间价值用；电话可自动估，拜访/客情手填可选） |
| mentioned_user_ids JSON | ask_help 时 @ 的同事（通知用）；**@ 即向被@者授予该关系 collaborator 级临时读写权**（见 C2，默认 7 天自动收回） |
| source | manual(手记) / auto(系统自动，如预约完成/通话导入) / import |
| visit_log_id / appointment_id 可空 | 关联外出/预约 |
| idempotency_key UNIQUE | 防重复提交 |
| attachments JSON | 附件 |

- 索引：`idx(relation_id, event_at)`、`idx(actor_id, event_at)`、`idx(pain_point_id)`
- 业务规则：
  - 完成预约/拜访回填 → 自动产生 visit/onsite 事件（auto）
  - 承诺兑现检测：写事件命中"给客户发过报价/资料"等 → 建议关联销项对应 commitment（closed_event_id）
  - **可见性继承关系**（见 §十七 权限）：本人全文、协同可读写、他人私海不可见、公海仅"近30天 N 次"概览、跨业务线金额/深度信息脱敏
  - 写事件是销售日常唯一必做动作——就一句话 + 最多两个可选点选，**无任何为报表设的必填**

### D3 cadence_rule 节奏规则（经理/公司配，加提醒=加行）
| 字段 | 说明 |
|---|---|
| scope_dept_id / scope_line_id 可空 | 空=全局默认；部门可覆盖 |
| trigger JSON | 触发条件（谓词）：如 `urgency=weekly`、`urgency=gray & 距最近事件>dept.gray_remind_days`、`新关系无事件>newbie_hours`、`已合作S级 & 距最近social>s_social_days`、`sea_status=private & 距掉海<=3天` |
| suggest_action | 到点给什么建议：文案 + 动作类型（写事件/改期/销承诺/判结论） |
| soft | 是否"仅提醒不催"（S级客情=soft；掉海预警=非 soft） |
| enabled / sort | 启停/优先级（命中多条取优先级最高） |

**核心思想**：正向节奏（新客 48h、S 级 45 天请顿饭、灰度到期给结论、周重点周五检查）与既有底线规则（掉海、灰度寿命）**统一收进本表**，全部"加行不加列"。

### D4 daily_agenda 今日动线（每日组装产物，工作台数据源）
| 字段 | 说明 |
|---|---|
| user_id + biz_date | 谁、哪天 |
| ref_type / ref_id | commitment / appointment / cadence / relation(掉海硬提醒) |
| relation_id / contact_id | 冗余方便直达 |
| reason | 为什么今天该找 TA（承诺到期/逾期/预约/掉海倒计时/新客48h/S级客情…） |
| priority | 逾期红 > 今天 > 顺延 |
| status | open / done / snoozed(推明天) / ignored(放弃，可选原因) |
| action_hint | 建议动作（去写事件/去销承诺/去改期） |

- 组装规则（每日清晨定时）：承诺今日到期/逾期 → 预约今日 → 节奏规则命中 → 掉海倒计时 ≤3 天 → 按优先级排序，逾期置顶标红
- **降噪收敛（防红墙）**：逾期 ≤3 天 → 逐条置顶红；逾期 >3 天 → 自动收入「逾期抽屉」不再逐条占首页（每日一条汇总提示）；**掉海倒计时/灰度判定/今日预约等硬约束永远置顶**；ignored(放弃) 同一客户同一原因 7 天内不再重复推
- 处理反馈：done 引导写事件并自动销承诺；snoozed 自动改 remind_at 明天；ignored 留痕（防骚扰与规则学习）

### D5 卡点字典（走 dict，不建表）
组 `pain_point`，种子：`price` 卡价格 / `effect` 卡效果 / `trust` 卡信任 / `decision_maker` 见不到决策人 / `timing` 时机未到 / `competitor` 竞品对比 / `internal` 内部流程慢 / `other` 其他。展示文案可自定义。
写事件时可选点选；经理出口按卡点统计"客户盘子卡在哪"（近 N 天分布）。

### D6 review 出口复盘 ★（经验继承的入口与经理闸门）
**不新增"复盘作业"**：三个出口动作（转已合作 / 判死 / 流失）发生时，在**同一个弹窗里顺手一问**；错过时机即不可补，故全部内联出口动作，绝不事后单独填表。

| 字段 | 说明 |
|---|---|
| relation_id / review_type | type：**win** 新签 / **loss** 判死（未合作，我们主动放弃）/ **churn** 已合作客户流失 |
| why_code 可空 | 主因码，走字典（win→review_win_reason；loss→review_loss_reason；churn→review_churn_reason，见 §十六） |
| competitor_id 可空 | 关联竞品名册：**可选、不点名**。销售大多只知道"有竞品、客户跟别家合作了"，具体哪家看客户愿不愿意透露——**能说才填，不说不强求**，统计按"有竞品（未点名）"归并 |
| detail 可空 | 复盘正文（≤200 字）。win：销售可填可不填，**经理无论销售填没填都可修订**；loss：文字可缓到次日；churn：经理回访后填结论 |
| manager_note 可空 | 经理批注（win 决定收录前可补充"这条值得学什么"）；churn 的经理回访结论 |
| status | open(win 待经理处理) / published(win 经理决定收录=进弹药库) / dismissed(win 经理决定不收录，可注明原因) / closed(loss/churn 统计闭环) |
| created_by / manager_id / manager_done_at | 谁填的、哪个经理处理的、何时 |

**触发与流转**（三型独立，互不串扰）：

1. **win 新签复盘（经理主导，销售可填可不填）**
   - 触发：**转已合作（stage→6）时系统自动创建一条 win review（open 态）**——不是销售自愿建，而是每次签约自动建档，经理侧"新签复盘待处理"队列自动多一条。销售可在转合作弹窗顺手填一句"赢在哪"（**可填可不填，10 秒可跳过**，T2）
   - 状态机：建档 = open（仅本人+直属经理可见）→ **经理审阅：无论销售填没填，经理都可直接修订 detail / 补 manager_note** → 觉得有沉淀价值 → **published 收录进赢单弹药库**；觉得是运气单/无普适打法 → dismissed 不收录（可注明原因）
   - **处理分级与时效（防经理积压）**：S/A 级签约 → 经理必须逐条处理；B/C/D 级 → 经理可批量收录/驳回，**超 30 天未处理自动 dismissed（不收录）**——经理是弹药库质检员，但不能让质检本身变成新负担
   - **经理是弹药库唯一收录人 + 修订人**：废话（"客户认可我们专业度"）经理直接改掉或丢弃；销售没写的单，经理凭对单子的了解补写。销售零负担、零丢脸
   - **弹药库可见范围：默认本部门可见；总经理可在设置中改为全公司可见**（A12 system_config）

2. **loss 判死复盘（点选必填，文字可缓）** ★T2 唯一例外
   - 触发：判死（stage_log action=lost / 灰度判死 / 手动放弃）弹窗
   - **死因点选必填**（服务端 422 兜底）：没真需求 / 输给竞品 / 我们没跟住 / 预算问题 / 决策链断了 / 说不清
   - **"输给竞品"不点名哪家**：competitor_id 选填——销售往往只知道有竞品、客户跟别家合作了，具体是哪家客户未必透露；统计归入"输给竞品"一类即可，不用逼问
   - 文字教训**当天不强制**：次日 daily_agenda 提醒"昨天判死那单的教训还没写"，情绪平复后补，质量更高
   - 为什么死因强制、文字不强制：死因是结构化底线（公司要知道客户为什么不要我们），文字是个人反思（逼不出来）；判死本身低频（一单一生判一次），30 秒成本可接受
   - status 直接 closed 进死因看板

3. **churn 已合作流失复盘（统一出口，原因=标签）**
   - **建模口径：被撬回访、到期未续费、服务不满……是同一类——"已合作客户流失"**，只是原因标签不同（review_churn_reason **单选主因**，可附备注），**不按原因分类型、不分流程**
   - 触发：已合作客户流失确认（到期未续 / 明确终止 / 关系标记流失）
   - 销售初填：流失原因标签（被竞品撬走[可带竞品] / 到期未续费 / 服务不满 / 我们疏忽 / 客户经营变故…）
   - **高价值流失（按 customer_level 分级，S/A 级强制）经理必须亲自回访客户听真话**：防"甩锅式死因"（被撬的常写"竞品低价"，到期未续的常被忽略成"客户没预算"——真实原因往往在客户嘴里），也是挽留机会 → 回访结论写 manager_note → closed
   - 与 loss 的区别：loss 是我们主动放弃未合作客户（销售自评足够）；churn 是已合作客户抛弃我们（**无论哪种原因标签，高价值的都要经理去听一次**）

**推导出口（只读，不落库，T3）**：
- 竞品关系三分 = `business_relation.competition`(事件快照) × `stage`：未合作(in_use)=策反 / 未合作(none/comparing)=竞争 / 已合作=防守
- 赢单弹药库（本部门/gm 设全公司）、死因看板、流失原因分布 = review 的三种消费视图，全部来自销售"本来就要点"的出口动作，**零额外报表填报**

## 九、域 E：交易与服务

### E1 contract 合同
`contract_no` UNIQUE + `relation_id` + `product_line_id` + `contact_id` + `signer_id`(签单人锁定=业绩归属，终身不变) + `amount` + `paid_amount` + `pay_type` + `sign_date` + `service_start/end` + `auto_renew` + `remind_days` JSON(30/60/90 续约提醒) + `attachments` JSON + `status`(unpaid/partial/running/done/terminated)

> **维护归属**：签约后的维护责任不跟 signer 走，跟**该产品线业务关系的当前 owner** 走（谁在岗谁维护，见 C2）；signer 仅作业绩历史锁定。**不再单独设 maintainer 字段/角色**——避免"签单人、维护人、owner"三套归属打架。

### E2 payment_record 回款流水
`contract_id + amount + paid_at + method + voucher_file_id + created_by`；回款事务内更新 contract.paid_amount/状态，并按 dept_rule 重算 customer_level，写 ledger。

### E3 workorder 工单
`order_no` UNIQUE + `type`(aftersale/opportunity) + `relation_id` + `title/content` + `source` + `priority`(P0-P3 仅售后) + `assignee_id` + `sla_deadline` + `est_effort_min` 可空(工时估算：0.5h/1h/2h/半天，点选——算"回款少事多"投入产出) + `status`(created/assigned/processing/confirming/closed) + `upgraded_from_id`(升级互链)

### E4 workorder_log
`workorder_id + action + from_status + to_status + reason + operator_id`（升级必填原因）

### E5 ledger 客户台账（扩展字段铁律落点）
`contract_id + company_id + product_line_id + customer_level + sign_date + expire_date + 通用 8 项 + extra_fields` **JSON**（Key 必须已登记 field_template，未登记拒收）；索引 `(product_line_id, expire_date)`；高频统计 Key 走生成列+索引（DBA 逐个评估，不动主表结构）。

### E6 field_template 字段元数据（登记唯一入口）
`product_line_id + field_key`(`uk(product_line_id, field_key)`，保存后不可变) + `label` + `control_type`(text/number/date/select/multiselect/link，**不可变**) + `required/sort/show_in_list`(可改) + `options` JSON + `status`(active/disabled，**停用不删**)

## 十四、数据权限与脱敏

**库中永远是明文全量**（保证归属方可用）；脱敏一律在应用层按 permission_matrix 渲染。可见分档：

| 查看场景 | 联系方式可见度 | 事件/跟单可见度 |
|---|---|---|
| 归属本人 / 本人售后 | 完整手机号 | 全文（本人可写） |
| 协同人 collaborator（正式协同 / @求助时效内） | 完整手机号 | 全文（可共同写） |
| 公司档案抽屉·非归属部门联系人 | `****{后4位}` +「申请解锁」 | 不显示具体事件 |
| 公海卡片/列表 | 脱敏 `xxx****xxxx` | 仅「近 30 天事件 N 次」概览 |
| 跨业务线金额 | 完全脱敏（不显示数字） | 仅"N 个工单进行中"概览 |

- 数据范围：销售=本人私海(owner/collaborator)+公海；经理=dept_manager 管辖部门；总经理=全部；他人私海不可见（除非协同/@求助授权）
- 坐标属公司档案基础信息（非敏感）；将来做任何地图展示时，**图上客户必须走同一套数据权限过滤**（他人私海不上图，公海可见）——属应用层实现，本架构只保证字段在、权限模型在
- 赢单弹药库（review published）：**默认本部门可见**（同部门销售可搜可学）；总经理经 system_config(ammo_scope=company) 改为全公司可见；未收录的 win review（open/dismissed）仅本人+直属经理可见
- 协同/转交走审批；解锁/变更走审批且留痕；合同水印、操作日志为应用层责任

## 十七、业务规则速查（实现时逐条过测试）

1. 同一 公司+部门+产品线 仅一条私海活跃关系（撞单/激活竞态由唯一索引兜底）
2. 手机号唯一；信用代码唯一；撞码引导用已有档案
3. 完成预约 → 服务端强制生成一条 action_event（422 兜底）；外出登记（visit_log）纯行政考勤、**不自动产生业务事件**
4. 承诺：me 到期催自己；them 到期催客户；verdict 到期给结论；豁免必填原因
5. 周重点（weekly）= 标记即承诺本周动作；系统建议生成本周 commitment，可跳过
6. 阶段推进 = 建议态（写事件时有进展 → 提示推进），确认落 stage_log；跳级/回退留痕
7. 客户等级 = 回款贡献自动算（dept_rule 档位），任何人不可手填
8. 开发价值（value_tier）与客户等级两轴独立；默认 pending，愿标才标
9. 掉海/灰度/协同到期/节奏 = cadence_rule + dept_rule/sea_rule 统一调度（T1）
10. 协同（collaborator）= 共同跟进，可共同写事件+联系方式全号可见；**正式协同走审批**（可长期/带期限）；**@求助（ask_help）= owner 即时授予的临时协同，权限与正式协同一致**（默认 7 天自动收回、owner 可撤销、全量留痕、无需审批）；想长期共同跟进必须走正式协同审批，不把 ask_help 当常驻授权（C2）
11. 手机号：归属/协同全号；非归属脱敏+申请解锁；变更走审批+冻结 24h
12. 金额/敏感信息库中明文全量，脱敏应用层；跨业务线金额完全脱敏
13. 自定义台账字段：先登记 field_template，key/类型不可变，停用不删，未登记拒收
14. 不存在吊着我们的客户 → 卡点只认"见不到人 / 犹豫效价"两类核心，其余为表象
15. 竞品标记在**跟单事件**里顺手做（D2：competition/competitor_id/note），`business_relation.competition` 只是最近一次事件快照（读优化），**销售无需单独维护竞品字段**；竞品三分（策反/防守/竞争）= 快照 × `stage` 推导只读，不设标签
16. 竞品名册只存"名称+产品线+一句话定位"（C7），经理维护、销售只读引用；**禁建价格表/功能对照类档案库**（录入者≠受益者必腐，T2/T3）；"输给竞品/被撬"均**不点名**（客户愿透露才填 competitor_id，否则按"有竞品未点名"归并统计）
17. 出口复盘 D6：**win 转已合作自动建档**（open），销售可填可不填，**经理无论销售填没填都可修订并决定收录/不收录**进弹药库（本部门可见，gm 可设全公司）；loss 判死死因点选必填（422，T2 唯一例外）文字次日缓写；**churn=已合作流失统一出口**（被撬/到期未续/服务不满均为原因标签，不分类型），高价值(S/A)流失经理必须回访核实
18. 完成预约必留事件（服务端 422）；判死必选死因（服务端 422）——两者同为"出口动作的强制性",但死因只点选不作文
19. 客户经营主责 = 唯一 owner（谁在岗谁维护，2026-09-09 拍板）；合同 signer 只锁业绩历史、不绑维护；换人走 transfer 审批、短期代看授带期限 collaborator、离职由管理员批量转交私海（转指定人/回公海），历史业绩归原 signer 不动（C2/E1/G1）
20. 客户坐标 = `company.longitude/latitude` **两个字段**，一家公司一个坐标；**人工用高德坐标拾取器点选、不做地址自动解析、非必填**；坐标系统一 GCJ-02；列表「地址是否维护」由 `address`/`longitude` 非空派生，**不新增字段不加标签**（B7）

## 十九、实施起点（全新架构，无旧系统包袱）

1. **本架构是全新起点**：旧档案式表结构仅停留在纸面设计、从未编码实现，**不保留、不迁移、不做兼容层**，直接按本文档 §四～§十六 从零建库；

3. 历史数据：旧系统无生产数据可迁；如有少量手工试录数据，按需人工补录，不做程序化迁移；
4. 开发顺序建议（与依赖关系一致）：域 A/B/C（组织与客户底座）→ 域 D 行动引擎（commitment/action_event/daily_agenda）→ 域 E/G（交易审批）→ 域 F（公海）→ 定时任务与三出口视图。
