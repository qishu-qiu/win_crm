# 销售CRM 数据架构 · 全面盘点与评审建议

> 性质：**只评不改**。本文件不修改《数据架构文档》等任何现行规格，仅输出盘点结论、评价与改进建议，供七叔拍板后决定是否吸收。  
> 依据：`需求规格/销售CRM数据架构文档.md` V1.1（现行唯一 Schema 真相源）；`需求规格/销售CRM业务需求文档.md` V1.0。  
> 日期：2026-09-09

---

## 一、总体结论（先说人话）

1. **架构骨架是健康的**：40 张表、7 个域，分层清晰，`business_relation` 处在正中心，事件流单表 + 权限继承的设计能扛住日常场景，且文档已解决"字段该放哪"的判据问题（§十七 A.1）。
2. **真正要警惕的不是"表设计"，而是三件事**：
   - **索引覆盖不完整**——文档只给 4 张核心表列了索引，其余 30+ 张表"索引现状"是空白，落库前必须补一张全表索引清单；
   - **经理统计类查询缺预聚合层**——"所有统计从 action_event 被动聚合"在小数据量成立，到百万级会开始慢，需加汇总表/物化视图；
   - **owner 归属与唯一约束存在并发/软删陷阱**——`uk_active_rel`、`phone UNIQUE`、`approval` 等需要落到"同事务 + 条件更新"语义，否则并发会出脏数据。
3. **量级判断**（估算）：按 200 名销售、人均每天 ~~20 条事件计，`action_event` 年增约 100~~150 万行，5 年约 500~800 万行；`daily_agenda`/`notification`/`operation_log` 同量级。**MySQL 单库单表扛到千万级没问题，但需要从第一天就把分区、归档、汇总想清楚**，避免中途大改。

## 三、设计评价（分维度）

### 3.1 做得好的（保持，别动）

1. **分层收敛**：company 档案 → relation（公司×部门×产品线三元组）→ 事件/承诺/合同/工单，一棵清晰的主线，没有任何"越层直连"。
2. **判断列不膨胀**（T1）：主表不加判断列，判断走承诺/节奏/事件统计——这是本设计最值钱的一条纪律，评审中强烈支持。
3. **数据库约束兜底**：phone/credit_code/order_no 等 UNIQUE、uk_active_rel 生成列、idempotency_key、applicant≠approver CHECK、422 强制留事件——"DB 是唯一真相源"落到了实处。
4. **字段归类判据已文档化**（§十七 A.1）：事件级/关系级回写/实时派生三句话能挡住 90% 的加列冲动。
5. **权限继承事件可见性**：跟单不存可见性字段、由 relation_member + 应用层判断——正确且省列。

### 3.2 值得改的（按优先级）

| #  | 问题                           | 影响                             | 建议                                                                                |
| -- | ---------------------------- | ------------------------------ | --------------------------------------------------------------------------------- |
| D1 | **缺全表索引清单**                  | 落库时靠 DBA/开发临时补，易漏 → 慢查询        | 在数据架构文档补一张"每表索引"总表（40 张全覆盖），见 §四                                                  |
| D2 | **owner 唯一性无 DB 兜底**         | relation_member 可能两个 owner     | 生成列 owner_flag（member_type='owner'→relation_id，else NULL）+ 唯一索引，等价 partial unique |
| D3 | **contact_trait ≤3 无 DB 兜底** | 应用层 422 之外无第二道闸                | 触发器或在写入 SQL 用 COUNT 子查询校验（INSERT...SELECT WHERE cnt<3）                            |
| D4 | **统计无预聚合层**                  | 经理看板/健康度/公海 30 天 N 次 → 每次现算事件流 | 增加日级汇总表（见 §五），明细表只做钻取                                                             |
| D5 | **daily_agenda 每日全量重建**      | 写放大 + 行数线性涨 + 重复提醒风险           | 重建改为"先失效昨日 open → 再插入今日"；按 biz_date 分区；closed 超 30/90 天清理                         |
| D6 | **soft delete × UNIQUE 冲突**  | 删掉的手机号/信用代码被占用，无法再建/再录         | 明确"删除=物理删行 or 唯一键加后缀占位"策略，二选一写死                                                   |

## 四、大数据量查询性能评估

### 4.1 量级估算（按本司多业务线规模）

| 表                       | 年增量估算     | 5 年规模     | 风险                |
| ----------------------- | --------- | --------- | ----------------- |
| action_event            | 100~150 万 | 500~800 万 | **高**（主查询表）       |
| daily_agenda            | 50~80 万   | 300~400 万 | **高**（每天每人 3~8 条） |
| notification            | 50~100 万  | 300~500 万 | 中（只读已读）           |
| operation_log           | 30~60 万   | 150~300 万 | 中（只增，分区即可）        |
| commitment              | 30~60 万   | 200~300 万 | 中                 |
| business_relation       | 5~10 万    | 30~50 万   | 低（但被高频 join）      |
| company/contact         | 3~5 万     | 20~30 万   | 低                 |
| contract/payment/ledger | 2~5 万     | 10~25 万   | 低                 |
| workorder               | 3~6 万     | 15~30 万   | 低                 |

> 结论：**唯一会到千万级的是 action_event + daily_agenda**。千万行在 MySQL 8 + InnoDB 完全可扛，前提：索引对、查询不扫全表、历史可归档。

### 4.2 逐查询场景核对（哪些会慢、为什么）

| 场景                              | 现有索引                                   | 十万级                 | 千万级      | 缺什么                                                                                 |
| ------------------------------- | -------------------------------------- | ------------------- | -------- | ----------------------------------------------------------------------------------- |
| 关系内时间轴（relation_id+event_at 分页） | idx(relation_id,event_at) ✓            | 快                   | 快        | 覆盖索引可加 (relation_id,event_at,action_type,summary 前 N) 避免回表                          |
| "某销售最近跟进"（actor 视角）             | idx(actor_id,event_at) ✓               | 快                   | 快        | —                                                                                   |
| 客户列表(本人 owner+协同+公海)            | relation_member idx(employee_id,...) ✓ | 快                   | 快        | 列表 join business_relation 需 uk/主键即可                                                 |
| 公海卡片"近30天N次"                    | **无**                                  | 可                   | **慢**    | 每行一个 COUNT 子查询 → 改为一条 `GROUP BY relation_id` 批量查，或维护 relation.last30d_count 由事件事务回写 |
| 经理统计：按 部门×人×产品线×日 聚合            | **无**                                  | 勉强                  | **慢/超时** | 必须加日级汇总表（见 4.3）                                                                     |
| 阶段漏斗/健康度（事件流派生）                 | idx(pain_point_id) 单列选择性低              | 可                   | **慢**    | 汇总裁 + 派生列                                                                           |
| 掉海扫描（每小时）                       | idx(last_event_at,sea_status) ✓        | 快                   | 快        | —                                                                                   |
| 公司名模糊搜索/查重                      | full_name 普通 INDEX                     | 慢（LIKE '%..%' 不走索引） | 不可用      | 见 4.3 全文检索方案                                                                        |
| 待审批列表                           | approval 无                             | 可                   | 慢        | idx(approver_id,status)                                                             |
| 我的工单/SLA                        | workorder 无                            | 可                   | 慢        | idx(assignee_id,status,sla_deadline)                                                |
| 台账按产品线到期                        | idx(product_line_id,expire_date) ✓     | 快                   | 快        | —                                                                                   |


### 4.3 更优解决方案（按性价比排序）

**① 增加"日级行为汇总表"（强烈建议，第一期就建）**
新增类似 `relation_daily_stat / team_daily_stat`（或一张宽表按维度冗余）：
- 数据：`(biz_date, dept_id, product_line_id, owner_id, relation_id, action_type, cnt, first_at, last_at)` 或聚合到 部门/人 级；
- 写入：每日 05:00 定时任务从 action_event GROUP BY 回填（与 daily_agenda 同批），或事件写入时异步累加；
- 读取：经理看板、健康度、跟进频率、公海"近30天N次"全部查汇总表，**明细表只承担"点进时间轴钻取"**；
- 效果：统计查询从"扫几百万行"降到"读几万行"，QPS 余量大。

**② action_event 按月分区 + 归档**
- RANGE 按 event_at 月分区；超过 24~36 个月的旧分区做归档（迁移到归档表/低成本库，或 DROP PARTITION 前先导出）；
- 权限/统计不受影响（分区对 SQL 透明）；DELETE 旧数据变成秒级分区操作。

**③ daily_agenda 按 biz_date 分区 + 收敛重建**
- 重建逻辑：同事务先 `UPDATE daily_agenda SET status='expired' WHERE user_id=? AND biz_date<today AND status='open'`，再批量 INSERT 今日——避免每日全表重写；
- closed/ignored 超 30 天定时清理或分区归档。

**④ 公司名查重/搜索上 FULLTEXT（ngram）**
- MySQL 8 `FULLTEXT` + ngram parser（中文分词），替代应用层 LIKE 相似度——company.full_name 千万内都毫秒级；
- 若后续量大再上 ES，但 **V1 别上 ES**（多一个组件你维护成本高）。

**⑤ ledger 与 contract 去重 or 明确唯一真相源**
- 现在 sign_date/expire_date/customer_level 两处定义 → 违反 L1 精神。建议：**contract = 交易事实源，ledger 只做"每业务线台账视图 + extra_fields"**，重复列改为读取时派生或只允许从 contract 同步，防止两处对账不一致。

**⑥ 关键高频查询加覆盖索引**
- 时间轴：`idx(relation_id, event_at) INCLUDE (action_type, contact_id, actor_id, summary(前缀), outcome)`——按 MySQL 支持的最长前缀 + 需回表字段做取舍。

**⑦ 写放大控制（last_event_at / next_action_hint / competition 回写）**
- 现状：事件写入事务内更新 business_relation —— 正确，但要**保证同一关系的事件提交顺序**，避免行锁竞争激烈时死锁（多个人同时给同一关系写事件 = 同一行 UPDATE，InnoDB 会串行锁，正常）；
- 建议：把这几列回写 + relation 状态机演进放**同一个写事件服务**里统一做，别散在多个 service 里各自 UPDATE。

**⑧ 读多写少的报表走只读副本（最后再说）**
- 只有到"主库 CPU 因报表查询被打满"时才引入读写分离/只读实例；**前期靠①汇总表足够**，别提前引入架构复杂度。

### 4.4 一句话建议（给落库）
> 从第一天就建：**全表索引清单 + action_event/daily_agenda/operation_log 分区 + 日级汇总表 + 公司名 FULLTEXT**。这四样在数据量小的时候零成本，数据量大时免重构；其余优化（读写分离、ES、归档冷库）等真到瓶颈再上。

## 五、并发与一致性风险（容易被忽略）

| # | 场景 | 风险 | 建议语义 |
|---|---|---|---|
| C1 | 抢公海客户（两人同时认领） | 双写 owner | 认领 = 一条 `UPDATE business_relation SET sea_status='private', owner_id=? WHERE id=? AND sea_status IN('dept_sea','company_sea')`，影响行数=1 才算赢；失败 409 + 前端提示已被领 |
| C2 | 激活竞态 | 已由 uk_active_rel 兜住 ✓ | 保持生成列方案；撞 1062 → 409 返回归属人 ✓ |
| C3 | 转交/协同审批通过瞬间 | 与事件写入并发 | 审批通过 = 事务内写 relation_member + operation_log；owner 变更建议带版本号乐观锁 |
| C4 | 手机号变更冻结 24h | 冻结期外又被改 | contact.phone_frozen_until + 更新时校验；phone UNIQUE 撞则回滚 ✓ |
| C5 | 事件幂等 | idempotency_key UNIQUE ✓ | 前端生成 UUID；重试同 key 命中返回原事件 |
| C6 | 完成预约强制留事件 | 422 ✓ | 保持服务端强制；改期/取消的联动也建议 422/显式规则 |
| C7 | 汇总表与明细对账 | 定时任务失败漏算 | 汇总任务要可重跑（按 biz_date 覆盖重算），并留"最后成功日期"水位线 |

## 六、全局日志系统设计建议

### 6.1 现状盘点
- 已有：`operation_log`（一张通用操作留痕，target 多态、detail JSON）+ 各域状态史表（relation_stage_log / workorder_log / contact_change_log / sea_record / relation_member 变更）+ 全表审计字段（created_by/updated_by）+ approval 审批记录。
- 缺：**统一字段规范**（无 before/after 对比、无 IP/UA、无请求链路 id）、**只增不改约束**、**保留/归档策略**、**敏感动作（解锁看号/导出）分类可查**、**系统运行日志（请求/异常/慢 SQL）落点**。

### 6.2 设计原则（四层分工，别混）
1. **业务状态史（领域表）= 已够，不动**：给业务页面当"时间线"用，随业务权限读。
2. **操作审计 = operation_log 升级为全局统一审计**：回答"谁在何时对什么做了什么、改前改后"，面向安全与追责。
3. **敏感安全日志 = 复用一个分类**：解锁看全号、批量导出、权限变更等动作单独 action 前缀，永久留痕。
4. **系统运行日志 = 不进数据库**：请求/异常/慢 SQL/定时任务执行 → 应用日志文件（Nest Logger / Winston），保留 30–90 天，跟业务表彻底分开。

### 6.3 operation_log 升级方案（字段建议）

| 建议字段 | 说明 |
|---|---|
| id / occurred_at | 主键 + 时间（按月分区） |
| req_id | 请求链路 id（一次操作多行日志可关联） |
| operator_id / operator_name | 操作人（快照冗余，防离职后查不到名） |
| dept_id / product_line_id | 操作人所处上下文（供经理按部门查） |
| action | 统一编码 `模块.动词`，如 `approval.approve` / `phone.unlock.view` / `event.create` |
| target_type / target_id | 多态对象（同现设计） |
| before / after JSON | **本次变更前/后快照或 diff**（新增，审计核心价值） |
| detail JSON | 补充说明（现设计保留） |
| ip / user_agent | 来源（解锁/导出必记，防批量捞号） |
| 变更约束 | **只 INSERT + SELECT；无 UPDATE/DELETE 权限**（DB 账号级隔离） |

### 6.4 落地要点
1. **写入方式**：NestJS 全局 AOP（拦截器/装饰器 `@Audit('action')`）在业务事务内写——与业务同成功同失败，不留"业务失败但日志成功"的脏记录；
2. **查询入口**：管理端"审计日志"页，按 operator/action/target/时间区间过滤；权限 = permission_matrix（默认仅 dept_manager 看本部门、gm 看全部）；
3. **敏感动作**：`phone.unlock.*`、导出类动作 **永久保留**（≥3 年，与普通日志不同 TTL），写入时 detail 不含全号明文→或对查询者脱敏（遵循"库中明文、出口脱敏"铁律）；
4. **系统运行日志**：Nest Logger + 按天轮转文件（`logs/`），慢 SQL 单独记录（`long_query_time=1s`）供优化索引；
5. **定时任务执行日志**：daily_agenda/汇总任务写一张轻量 `job_run_log(job, run_at, status, rows, cost_ms, error)`——排查"今天动线为什么没组装"全靠它。

### 6.5 边界提醒
- operation_log 不替代领域状态史表：页面时间线读 `relation_stage_log` 等（业务可读权限）；审计日志仅供管理端追责。两者都写，但**别试图合并成一张**（语义不同、权限不同、保留期不同）。
