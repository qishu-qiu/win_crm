## 一、AI 行为硬约束（★ 最高优先级 · 2026-09-12 七叔拍板）

> 本节约束 AI 自身行为，**优先级高于一切"默认推进"惯性**。七叔已多次重申"要跟我确认"，且曾因 AI 擅自推进被当场叫停。

- **A 明文执行令**：凡 **装依赖 / 写文件 / 跑命令 / 调用有副作用工具**，必须收到七叔**当轮明文执行令**（如"装 X""走 Y""写进去"）。**严禁**从"我建议 X"自行推导成"按 X 做" —— 建议与执行令之间必须有七叔的明确指令桥接。
- **B 短回复不外推**：七叔回"继续 / 采纳 / 好的 / 等"等短词，**仅对最近一个待办有效**，绝不外推到其他未决议题；多议题**逐条单独确认**，不合并。
- **C 动手前先发「准备做」**：跨界执行前先发"我准备做：___。回『执行』我才动"，未回『执行』**原地停住**。
- **D 回退机制**：七叔一喊"等一下 / 我没说 / 谁确认的 / 谁给你确认的"→ **立即回退到等待指令态、承认擅自推进、不辩解往前蹭**。
- **根因备忘**：2026-09-12 曾把"第 2 个顺手写进正文"误读为对"装哪套 skill"的整体批准，并自写"收到走 X" —— 属**范围偷换 ＋ 建议变决定**双重错误。**此错不得重演。**
- **E 提交前逐文件认领（2026-09-12 新增 · 多窗口并行）**：**禁用 `git add -A` / `git add .` / `git commit -a`**。提交前必跑 `git status --short` 逐条认领，**只显式 `git add <本轮自己动过的具体路径>`**。工作树里若有**另一个窗口正在改、尚未改完**的文件（尤其 `服务端/`），**一律不碰、不提交，原地报告**（"这两处不是我这轮改的，要一起提交吗？"），等七叔指令。
- **E 根因备忘**：2026-09-12 一次 docs 提交用 `git add -A`，把另一窗口**改到一半**的 `服务端/prisma/migrations/0001_init/migration.sql`（补 `ENGINE=InnoDB`）与 `服务端/.env.example`（新文件）一并带进 `ffd899e`。七叔未撤回，但**"别人的半成品挂在别人的提交名下"此错不得重演**。

| 3 | **归档目录检索污染**（旧文档近乎同名） | grep 到作废口径照做 | `.ignore` 机械隔离 `归档/`；归档件加"⚠已作废"头标 |
| 4 | **负面约束只收一半** | AI 以为"表里没有＝允许"，自行补全被封路功能 | 需求 §十六 收全为**完整清单**，"表里没有"才代表允许 |
| 5 | **机械扫描只扫 `.md`** | 漏掉 `schema.prisma`、`prisma/README.md`、过程 HTML 的旧版本引用 | 扫描覆盖全部文本类型（`.md / .html / .prisma / .sql / .json`） |
| 6 | **版本沿革写进正文** | 正文漂着旧版本号，改一处漏一处 | 沿革只留 `git`，文档内删「修改记录」 |
| 7 | **派生对外文档没同步** | 给老板的摘要说出已推翻口径 | L0 联动要求**同批、同次提交** |
| 8 | **AI「缺一块就自行补全」** | 实现被封路的功能 | 动手前先查需求 §十六；"表里没有"才代表允许 |
| 9 | **同事实多处落点＝双真相源** | 改一处漏两处 | L1 单一事实源；非权威位置**只留指针** |
| 10 | **`git add -A` 扫进别人未完成的改动**（多窗口并行：工作树 ≠ 本轮改动范围） | 另一窗口改到一半的服务端文件被挂进 docs 提交 `ffd899e` | 提交前 `git status --short` 逐文件认领；**只 add 本轮明确路径**；他人未完成改动原地报告等指令 |
| 11 | **`@/` 路径别名只活在编译期**：`tsconfig.paths` ＋ jest `moduleNameMapper` 能骗过 `tsc --noEmit` 与单测，但 **`tsc` 不会重写产物里的路径** | 源码里写 `@/kernel` 的进程，本地三绿全过、CI 也过，却**到 `node dist/main.js` 才报 Cannot find module** | **src 内一律相对路径**（如 `../../kernel`），`@/` 只留给 spec；口径已写死在 `服务端/src/kernel/index.ts` 顶部注释 |
| 12 | **`nest build` 默认读 `tsconfig.json`**，不会自己排除测试文件 | `dist/` 里混进 10 个 `*.spec.js`：发行产物不卫生，测试代码被带上生产 | 新增 `服务端/tsconfig.build.json`：`exclude` 全部 `*.spec.ts` ＋ 独立 `tsBuildInfoFile`（避免与 `tsc --noEmit` 抢同一个增量文件）；验收＝dist 里 spec 数 **0** |
| 13 | **Jest 载不动 NestJS 12**（`@nestjs/common@12.0.1` 是 `"type": "module"` ESM-only） | 凡含 `@Injectable` 的用例一律 `Must use import to load ES Module` —— 守卫 / 拦截器 / 服务**全都写不了测试** | `test` 脚本改用 `node --experimental-vm-modules node_modules/jest/bin/jest.js`；**运行时不受影响**（Node 24 原生 `require(ESM)`，已实测能取到 `Module` / `Injectable` / `NestFactory`） |
| 14 | **`@nestjs/testing` 没装**（M0-02 只装了 Jest，没装它） | 用例里 import 不到 → `tsc` 直接 TS2307；顺手一装就变成「未拿执行令装依赖」 | 单测要 DI 容器时用 `@nestjs/core` 的 `NestFactory.createApplicationContext`（**零新依赖**，且比测试模块更接近真实装配路径）；真要装 `@nestjs/testing` 须先拿执行令 |
| 15 | **拿 Proxy 做「库访问绊线」放进 DI 容器**（想证「没查库」） | Nest 的 `callModuleInitHook` 会对容器里**每个 provider** 读 `onModuleInit` 等生命周期钩子 → 绊线被框架自省误伤而抛，用例**假红**，跟业务有没有查库毫无关系 | 「不碰库」改用两条硬证：① 容器里**根本不放**库客户端也能装配成功（若注入 Prisma，Nest 此刻报依赖解析失败）；② 断言类上**构造依赖个数**（多挂一个依赖立刻红） |
| 16 | **测试假件比真实形状少字段** | 用例假红：守卫读元数据时 `executionContext.getHandler is not a function`，看着像守卫有 bug，实际是假件不是真形状 | 假件按**真实上下文形状**造：`getType` / `getHandler` / `getClass` / `switchToHttp` 一个不少；**假红先修假件，再怀疑被测代码** |
| 17 | **计划书判据与规格冲突**：开发计划 M0-35 写「坏 DTO → **422**」，而接口 API §2.4 **第一行**把「字段缺失 / 类型错 / 枚举非法」定为 **400 / 20001**（422＋204xx 是**业务校验**专用，如「完成预约未留跟单」） | 照计划写会把「前端传错类型」错记成业务校验失败；前端按 422 分支处理则**全线接错** | 按 `CONSTRAINTS` 首行「与规格冲突时以规格为准」取 **400 / 20001**；冲突**写进批次报告＋实现文件顶部注释**，不静默按计划做；计划书口径待修订 |

> **三条最核心**：① 先读《废止口径登记表》＋需求 §十六，再动手；② 改文档＝必须 git 提交，四份同批同次；③ 不要自行补全"缺的一块"，先查是否被封路。

## 三、通例（由上述坑提炼，适用于所有文档与协作）

- **"防 AI 误读"的自检，必须出现在 AI 真会读到的那一页**（表头 / 章节首行），**不能只写在章程** —— 因为 AI 读表时不会回头翻章程（2026-09-12 定）。
- **规则本体放"读者会直接打开的那份文件"里**，上级文档只留**指针与动作项**。
- **元规则（本文这类）的落点唯一**：新增同类规则一律追加进本文（见首页维护铁律）。
- **同一事实只允许一个权威落点**；非权威位置必须显式标注定位（如「索引·非规范」），否则会被 AI 当成规范。
- **"三绿"不等于"能跑"**：`tsc` / `lint` / `test` 全过只证明**编译期与测试期**成立。凡涉及**模块解析、依赖加载格式、打包产物**的改动，必须**真起一次进程**（`node dist/*.js`）才算验完 —— 坑 11 / 12 / 13 都是"三绿全过但跑不起来或产物不干净"（2026-09-14 定）。
- **否定式约束（"不许查库 / 不许越权 / 不许依赖某层"）要用「无法表达」来证，不要用「跑一遍没发生」来证**：前者是结构事实（依赖没注入 → 不可能调用），后者只覆盖一次执行、还容易被框架自身行为干扰（坑 15）（2026-09-14 定）。
- **判据与规格冲突时**：先比规格（上游优先），按规格做；**冲突本身必须写进报告**并在实现处注明依据，**不许静默按计划/顺手口径做**（坑 17）（2026-09-14 定）。
