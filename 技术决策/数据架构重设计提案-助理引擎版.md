## 二、为什么重设：档案室 vs 助理

用"助理四件事"当尺子量旧库（详见当日讨论与记忆）：

| 助理该做到的 | 旧库现状 |
|---|---|
| ① 系统替我记 | follow 全靠销售手敲，无自动沉淀 |
| ② 系统替我分 | 阶段/紧迫/价值全靠手贴，系统读不懂也算不了 |
| ③ 按处境提醒 | 只有"全表扫超时"的惩罚式定时任务，无正向节奏 |
| ④ 回答"今天该干嘛" | 无承诺实体、无卡点结构化、无每日动线数据源 |

**核心病根**：`business_relation` 一行承载 7 组判断字段（stage/urgency/value_level/risk_tags/coop_tags/gray_release_at/no_progress_count）——**加一条规则 = 加一列**（`gray_release_at` 即活证据）。表越来越胖、销售被迫维护一堆状态、系统还推导不了。

## 三、重设计总纲：换脊柱，不换底座

```
┌─────────────────────────────────────────────────────┐
│  事实底座（原样沿用，一张不改不删，约 2/3 表）          │
│  组织权限 · 公司档案 · 联系人 · 归属协同 · 审批        │
│  合同与回款 · 工单台账 · 公海规则                      │
└─────────────────────────────────────────────────────┘
        ▲ 读事实（只读，不写）
┌─────────────────────────────────────────────────────┐
│  助理引擎（本提案新增，约 6 张表）                      │
│  ① 事件流 action_event      —— 自动替我记              │
│  ② 处境 situation           —— 推导"客户现在啥情况"     │
│  ③ 承诺 commitment          —— 答应的事有期限           │
│  ④ 节奏 cadence_rule        —— 每类处境到点提醒         │
│  ⑤ 动线 daily_agenda        —— 今天该花时间在谁身上      │
│  ⑥ 规则 situation_rule      —— 经理配置推导口径          │
└─────────────────────────────────────────────────────┘
        ▼ 写回（销售确认后的结论）
┌─────────────────────────────────────────────────────┐
│  旧判断字段搬家区：stage/urgency/value_level/risk_tags │
│  /gray_release_at 停用不删，数据一次性迁入处境表        │
└─────────────────────────────────────────────────────┘
```

**设计三原则**（与既有三铁律并存，不冲突）：
1. **底座只读**：引擎表只读底座事实，反向不写底座判断字段（旧列停用不删）。
2. **加规则 = 加行，不是加列**：新处境/新节奏/新卡点全走配置表行，`business_relation` 永不新增物理判断列。
3. **推导可纠偏**：系统推导的处境默认"建议态"，销售一键确认或纠正，纠正留痕（见 §五 决策点 A）。

## 四、核心重设计：五块怎么改

### 4.1 business_relation 收敛为"归属事实行"

只留：三元组（company × dept × product_line）、owner/maintainer/collaborator、sea_status 归属状态、签单锁定等**归属类事实**。
判断类字段（stage_id / urgency / value_level / risk_tags_manual / coop_tags / gray_release_at / no_progress_count）**全部搬出**，由 situation 表接管当前值，历史由 situation 变更记录承接（替代 relation_stage_log 的职责）。

> 客户等级 `customer_level`（回款贡献）仍系统自动算，位置不动；`value_estimate` 价值评估迁入处境/价值层。

### 4.2 新增处境域：situation + situation_rule（推导"现在啥情况"）

**situation 处境表** —— 每个业务关系当前处境 + 历史：
| 字段 | 说明 |
|---|---|
| relation_id | 关联业务关系 |
| situation_code | 处境：new_contact(刚上钩48h) / progressing(常规推进) / blocked(卡点中) / verdict_due(待判定·本周) / closing(攻坚·近期收款) / nurturing(养客·长期培养) / maintaining(维护期·已合作) / dormant(沉睡待激活) / at_risk(掉海预警)…（枚举可扩，走配置） |
| pain_point | **卡点字典**（见 4.4），null=无卡点 |
| stage_id | 兼容保留：6 步阶段引用（初步建联→…→已合作） |
| value_tier | 开发价值档（实力×契合度，推导+人工可改） |
| source | derived(系统推导) / confirmed(人工确认) / overridden(人工纠正) |
| decided_by / decided_at / note | 谁确认/纠正、何时、理由 |

**situation_rule 推导规则表** —— 部门经理配置"什么情况算啥处境"，加规则=加行：
| 字段 | 说明 |
|---|---|
| dept_id / product_line_id | 适用范围 |
| trigger | 触发条件 JSON（如：距上次跟进>N天 且 无承诺 → dormant；有承诺今日到期 → verdict_due） |
| target_situation | 推导出的处境 |
| suggest_action | 给销售的建议下一步（话术/动作类型） |
| priority / enabled | 优先级、启停 |

推导输入 = 事件流统计（最近动作、承诺到期、签约回款、工单…）＋ 底座事实（等级/价值），全由引擎算，销售只确认。

### 4.3 新增承诺域：commitment（答应的事有期限）

**commitment 承诺表** —— 行动项实体，取代 `follow_record.next_action` 自由文本：
| 字段 | 说明 |
|---|---|
| relation_id / contact_id / owner_id | 归属 |
| party | **me(我答应客户) / them(客户答应我)** —— 两种跟进策略完全不同 |
| type | reply(答复) / quote(发报价方案) / meet(约见面) / verdict(本周判定去留) / deliver(交付物) / gift_meal(客情动作)… |
| content | 承诺内容 |
| due_at / remind_at | 兑现期限 / 提醒时间 |
| status | open / done / expired(逾期) / waived(豁免，注明原因) |
| source_event_id | 由哪条事件/跟单产生（可溯源） |

到点没兑现 → 自动进 daily_agenda 并标红；兑现 → 系统检测动作（如写了该客户跟单/完成预约）可建议自动销项，人工确认。

### 4.4 卡点结构化 + 客情动作独立

- **卡点字典**（复用现有 dict_type/dict_item 机制，不新建表）：`pain_point` 组 = price(卡价格) / effect(卡效果) / trust(卡信任) / decision_maker(见不到决策人) / timing(时机未到) / competitor(竞品对比)…写跟单时"点选+一句话补充"。
- **客情动作**：在事件流/承诺里增加类型 `meal(请客) / gift(送礼) / greeting(节点问候)`，与业务跟进分轨。S 级客户由 cadence_rule 单独配"客情节奏"（默认 30~45 天一次），解决"老钱罐别冷落"。

### 4.5 事件流 + 节奏 + 动线（自动记、到点提醒、今早排活）

| 新表 | 白话作用 | 关键设计 |
|---|---|---|
| **action_event 事件流** | 所有"发生的事"自动沉淀为一条：电话、拜访、签约、回款、工单、系统判定… | who / when / relation_id / action_type / summary / source(manual·auto·import) / payload JSON；**电话/打卡等可自动落**，手动动作一键提交即成记录 |
| **cadence_rule 节奏规则** | 每类处境×客户档配"多久提醒、提醒啥"，经理可配 | situation_code × customer_tier / interval_days / remind_action / quiet_mode(安静模式：老钱罐少打扰) |
| **daily_agenda 每日动线** | 每天清晨自动组装"今天该花时间在谁身上"——工作台首页数据源 | user_id / date / ref_type(commitment·cadence·预约…) / reason / status(待办·完成·推迟·忽略) |

> 掉公海/灰度释放等**既有惩罚式规则保留**（是底线保障），但不再是提醒主力——正向节奏提醒由 cadence_rule 承担，两者互不冲突。

## 五、待七叔拍板的决策点

| # | 决策点 | 方案 A | 方案 B | 我的建议 |
|---|---|---|---|---|
| **A** | 处境推导错了怎么兜底 | **只建议不自动改**：系统推导显示"系统判断：卡在价格？"，销售点确认/纠正后才生效（慢但稳，纠正留痕可反哺规则） | **推导即生效**：处境自动更新，销售看到不对再改（快，但错判会误导动作） | **A**。CRM 里推导错误会被放大（客户被错误放弃/骚扰），"建议态 + 一键确认"负担极小、信任累积快；客观类推导（如"N 天没动→沉睡建议"）可自动生效 |
| **B** | 卡点写跟单时是否必选 | 必选（选一个主卡点才能存） | 可选（默认"无卡点"） | **B 可选**。只在客户确实卡住时点选，避免给每单加负担——但一旦选了必须结构化+可补充一句话 |
| **C** | 客情节奏默认值 | 公司统一默认（S级 45 天一次，经理级可调） | 每部门自定 | **C**：走 dept_rule 同级配置，先给公司默认值，部门可覆盖 |
| **D** | 承诺要不要"我答应客户"与"客户答应我"分开提醒话术 | 分开（me=提醒我去兑现；them=到点问客户"您上次说今天答复"） | 合并 | **分开**。them 类到点提醒是"催客户"，跟 me 类"催自己"语气完全不同 |

> 除以上 4 点外，**既有已拍板规则全部不动**：撞单唯一索引、掉公海规则、三层标签归属、跟单可见分档、协同=共同跟进、手机号脱敏+申请解锁、金额明文库+应用层脱敏、跨业务线不可见等，均在底座沿用范围内。

## 六、落地与迁移（不覆盖原表）

1. **V1.2 文档一字不改**。本提案确认后，正式表结构定稿以"新增章节 + 表结构补丁"方式并入数据库设计文档（升 V1.3/2.0，届时按 §九 流程先问七叔、旧版入归档）。
2. **建新表 ≈6 张**（action_event / situation / situation_rule / commitment / cadence_rule / daily_agenda）+ 字典组（pain_point、客情动作类型走 dict，不新建表）。
3. **旧判断字段搬家**：一次性数据迁移将 business_relation 当前判断值写入 situation 首行（source=confirmed，标注"历史迁移"）；旧列停用不删，代码层不再读写。
4. **过渡期**：新引擎先读底座事实 + 既有 follow_record 历史；跟单写入逐步切到事件流语义，接口层做兼容映射（旧端点出参不变，避免前后端全量返工）。
5. **不新增实体时的替代**：若确认后发现某引擎表可并入现有表（如承诺挂 follow_record 扩展），按"最小新增"原则压缩。
