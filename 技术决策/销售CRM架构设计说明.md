## 二、结论先行（一页话）

> **本章用途**：结论概述，**非执行依据**（执行规范见 §四~§七，约束见 §三）。

**架构形态＝模块化单体（Modular Monolith）**：

1. **一个代码库、两个进程** —— Web（处理接口）＋ Worker（跑定时与异步），同一个代码库、两个启动入口。
2. **一个库、一个缓存** —— MySQL 8 单库（46 张表）＋ Redis。不分布式、不分库分表。
3. **按域切块、边界硬卡** —— 7 个业务域 = 7 个模块；跨模块**只走 service 接口与领域事件**，禁止直接查对方的表；边界用 ESLint 强制，不靠自觉。

> **为什么这样能"两头兼顾"**：验证期 = 一次构建一次调试、改规则只动一个文件夹、AI 每次只看一个域；扩展期 = Web 直接多开实例（Worker 永远只有 1 个）、加缓存 / 只读副本是"改配置"、域边界＝服务边界（将来拆服务是**搬文件夹**，不是重写）。

## 三、决策记录与禁用边界（约束卡 · 非执行规范）

> **本章用途**：记录「为什么选它、哪条路已经堵死」。**这是给 AI 的负面约束**——做取舍时先看这里，别走已被否掉的路。

**决策留痕（评估过的三条路）**：

| 方案 | 长什么样 | 结论 | 留下的约束 |
| --- | --- | --- | --- |
| **大泥球单体** | 所有代码混在一起，谁都能查谁的表 | ❌ 边界糊了不可逆；改一处崩一片；将来想拆也拆不动 | **禁止**跨域直查表、禁止无序依赖（见 §5.1） |
| **★ 模块化单体（选它）** | 一个部署单元，内部按业务域硬隔离 | ✅ 开发速度≈单体，边界质量≈微服务；**是唯一"现在做、将来省大钱"的投入** | 执行规范见 §四 / §五 |
| **微服务** | 7 个独立部署的服务 | ❌ 分布式事务 / 服务发现 / 链路追踪 / 多进程调试会拖死速度；且本项目无人运维 | **禁止**引入微服务 / 服务发现 / 跨服务分布式事务（理由详见 §十） |

**明说代价（做取舍时把这两条算进来）**：

- 模块边界靠**工具强制**，不靠自觉 —— 破坏边界的代码 `npm run lint` 直接失败、提交不上去（**具体配置规则见 §5.4，本章不复述**）。
- 前期要多写一点"接口与事件的样板代码"，比完全开放的单体**慢约 10~15%** —— 换的是后期**不用重写**。

> **（以下为比喻·非规范）** 一栋楼里的各个部门，共用一套地基和水电（数据库），但每个部门有自己的门牌、规章、账本。将来哪个部门忙不过来，整建制搬到隔壁楼就行。
>
> ⚠ **此比喻仅用于向人解释，不构成技术约束**；读到它时不得据此推断"需要做物理搬迁兼容层"。

├── package.json

    │   ├── engine/              #    域 D 行动引擎
    │   ├── trade/               #    域 E 交易与服务

    │   └── approval/            #    域 G 审批中心

    ├── report/                  # ★ 报表与统计（独立圈出，预留只读副本入口）

### 4.1 域内部统一四层

以 `company` 为例，**每个域都是同一套骨架**：

```
modules/company/
├── company.module.ts            # 模块声明：exports 只暴露 service
├── company.controller.ts        # ① 接口层：只收参数、调 service、回结果
├── company.service.ts           # ② 应用层：编排 + 事务边界（$transaction）
├── domain/                      # ③ 领域层：纯业务规则，不 import 框架/Prisma
│   ├── dedupe.policy.ts         #    撞单判定
│   └── mask.policy.ts           #    脱敏口径
├── company.repository.ts        # ④ 数据层：唯一允许 import Prisma 的地方
└── dto/                         # 请求 / 响应对象（class-validator + OpenAPI）
```

### 4.2 每层「只能做 / 不许做」

| 层 | 只能做 | 不许做 |
| --- | --- | --- |
| **① controller** | 解析请求、调**一个** service 方法、返回 | 不写业务判断、不碰 Prisma |
| **② service** | 编排多步、开事务、发事件 | 不写复杂规则（下放 domain）、不写 SQL |
| **③ domain** | 纯函数 / 纯类：入参出参都是普通对象 | **不 import `@nestjs/*`、不 import Prisma**、不查库、不发 HTTP |
| **④ repository** | 查库 / 写库，返回领域对象 | 不写业务判断、不发事件 |

> **为什么这么分？** —— `domain` 层是**业务规则的保险箱**。因为它不碰框架、不碰数据库，可以拿假数据直接单测。掉海判定、公海规则、目标进度、脱敏口径这些**最怕写错**的地方全放这里，改错了测试立刻变红。这也是本项目"用人不读代码、靠 AI 写"模式下最关键的一道护栏。

### 4.4 前端目录与组件约定（★ 2026-09-16 拍板 · P-02）

> **为什么补这一节**：本节以前**只管服务端** —— 前端的目录与「跨页复用」**没有任何落点**，于是"同一个东西在多个页面各写一份"没有任何约束（＝服务端一号坑「双真相源」的**前端版**）。
> **触发场景（七叔举例）**：*鼠标停在联系人上显示联系人信息* —— 这种卡会在工作台 / 关系列表 / 详情页**同时出现**：**没有规矩时它必然变成三份，改一处漏两处**。
> **大厂做法**（调研件：`过程产出/前端目录与组件复用-调研.md`）：组件分四层 ＋ **重复 ≥2 次才抽** ＋ **统一出口**；字节的做法是**靠 lint 硬卡，不靠自觉** —— 与本项目 §5.1「靠工具，不靠自觉」同源。

| 层 | 放在哪 | 职责 | 例 |
| --- | --- | --- | --- |
| 基础件 | **不自己写** | 长得对、能交互 | Ant Design Vue（Button / Table） |
| **业务组件** | `前端/src/components/` | **跨页复用**的业务件，只回答"长什么样" | `ContactHoverCard.vue`（联系人悬停卡） |
| 区块 | `前端/src/components/`（只给一个页面用则就近放页面内） | 页面的一块 | 查询条件 ＋ 表格 ＋ 分页器 |
| 页面 | `前端/src/views/` | 组装 ＋ 取数 | 业务关系列表页 |

**三条硬约定**
1. **依赖单向**：`views` → `components` → 基础件。**`components` 不许 import `views`，也不许直接 import `api/`** —— 数据由页面喂进来（否则每个页面各配一次取数＝又一份真相源）。
2. **抽取判据**：**同一个东西第二次出现，就必须搬进 `components/`**；只出现一次的不许提前抽（防"为复用而过度抽象"）。
3. **展示口径不进组件**：中文名 / 颜色 / 格式映射一律走 `前端/src/*.ts`（如 `relation.ts`）；组件只管渲染。

**取数与类型**：`前端/src/api/` 按域一个文件；**接口类型一律取自 OpenAPI 生成物**（`api/types.ts`），**禁止手写对接**（双真相源是 AI 出错重灾区）。
**机械卡点**：**已装 ESLint**（2026-09-16 拍板落地）—— `前端/eslint.config.mjs` 用 `no-restricted-imports` 把**约定 1** 变成硬卡（组件不许 import `views` / `api`；页面之间不许互相 import），**`npm run lint` 失败＝提交不上去**（同 §5.1「靠工具，不靠自觉」）。
> ★ **前端提交前必跑双绿**：`npm run lint` ＋ `npm run build`（前者卡目录方向，后者卡类型）。本版**只上这一条**卡点、不铺开 recommended 全家桶 —— 先让这一条真的守住，其余规则**渐进**开启（与服务端当年"先卡边界、后补规则"同节奏）。

## 五、模块边界（谁能调谁）

> **★ 本章为执行规范，施工时以本段为准。**

### 5.1 依赖分层（严格单向）

```
第 0 层  kernel       内核：上下文 / 事件 / 审计 / 错误 / 通用 —— 零业务依赖
第 1 层  org     (A)  组织与权限：人 / 部门 / 角色 / 规则 / 字典 / 通知 / 目标
第 2 层  company (B)  客户资产：公司 / 联系人 / 文件
第 3 层  relation(C)  业务关系：归属 / 协同 / 阶段
第 4 层  engine  (D)  行动引擎：承诺 / 事件流 / 动线 / 复盘
         trade   (E)  交易与服务：合同 / 回款 / 工单 / 台账
         sea     (F)  公海与流转：公海规则 / 入海历史
         approval(G)  审批中心
```

**三条硬规则**：

1. **只能依赖"比自己低"的层**：B 可用 A；C 可用 A、B；D/E/F/G 可用 A、B、C。
2. **同层之间禁止直接依赖**：D 不许 import E；E 不许 import F（需要协作走事件，见 §5.2）。
3. **A 不许依赖任何业务域**（它是底座；连横切层都不依赖，见 §七.1）。

### 5.2 跨域通信的三条路（按"要不要立刻知道结果"选）

| 场景 | 走哪条 | 例子 |
| --- | --- | --- |
| 我马上要用它的结果 | **同步调对方 service**（只许调 `exports` 出来的 service，**禁止查对方的表**） | D 组装今日动线时查 C 的关系详情 |
| 我做完一件事，别人可能关心，但我不等结果 | **发领域事件**（`eventBus.emit()`） | C 阶段推进 → D 落 action_event、A 发通知 |
| 我要改多个表且必须一起成功 | **本域内开事务**（`$transaction`）；**不发跨域大事务** | 抢公海：改 sea_status ＋ 写 owner ＋ 写 sea_record |

> **为什么跨域不发大事务？** 因为将来拆服务时，跨服务事务要换成最终一致。如果现在就把它写死在一个大事务里，将来每一处都得重写。反过来，**域内事务天然独立**，拆开后一行不用改。

### 5.3 首批要落地的跨域事件清单

| 事件 | 谁发 | 谁听 | 干什么 |
| --- | --- | --- | --- |
| `RelationCreated` | C | D | 落首条 action_event（建档） |
| `RelationStageAdvanced` | C | D / A | 落事件；**回退时**发经理 `stage_revert` 知会 |
| `RelationReleased`（掉海 / 判死 / 流失） | F / C | D / A / E | 落事件 ＋ 通知 ＋ 关系状态回写 |
| `RelationClaimed`（领公海） | F | D / A | 落事件 ＋ 通知前 owner |
| `ActionEventRecorded` | D | C | **有效沟通才回写** `last_event_at`；快速标记不算 |
| `ContractSigned` | E | D / C / F | 落事件 ＋ 阶段推进 ＋ 老客户徽标 |
| `PaymentReceived` | E | D / C | 落事件 ＋ 触发客户等级重算 |
| `ApprovalApproved` / `ApprovalRejected` | G | 各域 | 执行审批通过后的动作（转交 / 解锁） |
| `CollaborationGranted` | G | C | 写入 `relation_member.collaborator` |

> 事件只带**最小信息**（谁、什么时候、对哪个对象做了什么）。拿到事件后若要更多数据，**回查对方的 service**，不把对方的表结构塞进事件里。

### 5.4 怎么保证边界不被破坏（本节最关键）

> **靠工具，不靠自觉。** 这是"过期不补"那条决定的唯一实现方式。

用 ESLint 的 `no-restricted-imports` 配置：

| 目录 | 允许 import |
| --- | --- |
| `kernel/**` | 任何非业务包，**但不许 import `modules/*`**（业务规矩不准下沉进内核）**、也不许 import `shared/**`**（`shared` 依赖 `kernel`，反向引即**成环**；内核要用的通用能力都在内核内） |
| `modules/org/**` | `kernel/**` |
| `modules/company/**` | `kernel/**`、`modules/org/**` |
| `modules/relation/**` | `kernel/**`、`modules/org/**`、`modules/company/**` |
| `modules/{engine,trade,sea,approval}/**` | `kernel/**`、`modules/org/**`、`modules/company/**`、`modules/relation/**` |
| `modules/*/**` | **不许 import `shared/**`**：横切层由 `APP_GUARD` / `APP_INTERCEPTOR` / `APP_FILTER` / `APP_PIPE` **运行时全局生效**，域不必也不许自己引；域要用的通用能力（上下文 / 错误 / 事件 / 审计）一律走 `kernel/**`（见 §七.1） |
| `modules/*/*.repository.ts` | **只许被自己域内的文件 import**（别人不许直连你的仓储） |
| `modules/*/domain/**` | **不许 import `@nestjs/*`、`@prisma/client`** |

**违反 = `npm run lint` 失败 = 提交不上去。** 不需要人记，机器帮你拦。

## 六、进程模型（Web / Worker）

> **★ 本章为执行规范，施工时以本段为准。**

| | **Web 进程** | **Worker 进程** |
| --- | --- | --- |
| 入口 | `src/main.ts` | `src/worker.ts` |
| 启动方式 | `NestFactory.create(AppModule)` ＋ HTTP | `NestFactory.createApplicationContext(WorkerModule)`，**不监听端口** |
| 装什么 | 全部 7 个域 ＋ `shared` ＋ `report` | `kernel` ＋ `jobs` ＋ 用到的域（engine / sea / org / trade） |
| 干什么 | 处理接口请求 | 跑《数据架构文档》§十二 定时任务清单（掉海判定、日汇总、动线组装、各类提醒）＋ 消费异步事件 |
| 扩几个 | **可以扩到 N 个** | **永远只跑 1 个** |

**为什么现在就拆？** 两行启动代码的事。但不拆的后果很具体 —— 《数据架构文档》§十二 里有「掉海预警（每小时）」「日级行为汇总（每日 05:00）」这类任务：将来 Web 扩到 3 个实例，这些任务会**在 3 个实例上各跑一遍**，同一个客户被掉海 3 次、统计数据被算 3 遍。这是最难排查的一类 bug，而且那时候再拆还要动部署方式。

```json
"scripts": {
  "start:web":          "nest start",
  "start:worker":       "nest start --entryFile worker",
  "start:prod:web":     "node dist/main.js",
  "start:prod:worker":  "node dist/worker.js"
}
```

## 七、横切层设计（数据权限 / 脱敏 / 审计 / 异常）

> **★ 本章为执行规范，施工时以本段为准。**

> 这是本项目**最容易出事**的地方：5 个角色 × 多种查看场景 × 3 类脱敏。**如果散在 ~80 个接口里各写一遍，必然有漏的。**

### 7.1 请求上下文（一次解析，全程可用）

请求进来，鉴权守卫解析登录凭证，把"当前是谁"塞进请求上下文：

```
RequestContext = {
  employeeId, deptIds, roleCodes,                                   // 我是谁、管哪些部门、什么角色
  dataScope: { type: 'self' | 'serving' | 'dept' | 'all', deptIds },// 我能看到谁
}
```

> **★ 关键**：横切层**只读这个上下文、不查数据库**。这样 A 域（组织权限）自己也能用同一套横切，不会出现"A 域调权限、权限查 A 域"的循环依赖。
>
> **⚠ 别把上句读成"域可以 import `shared/`"**：这里的"用"＝**运行时**由全局注册统一生效；**业务域代码只许引 `kernel/**`**，不得直连 `shared/**`（§5.4 表格）。正因如此，`@Public()` 这种**要写在域 controller 上的标记**放在 `kernel/context/`（§4 目录树），而不是 `shared/`。

### 7.2 数据范围：判定一处收口，落地各域自己拼（2026-09-15 校正措辞）

> **业务口径权威落点＝《需求》§4.2**（谁看得到谁）；本节只讲「**怎么落到查询条件**」这一层，出参形态见 `→数据架构§十一`。

**分两步，别混成一处**：

- **① 判定（唯一入口）**＝ `kernel/data-scope/data-scope-target.ts`：把上下文里的 `dataScope.type` 翻成**中立的范围描述**（`all` / `depts` / `self` / `serving`，见下表）。★ `scope.type` 的判定**只允许出现在这一个文件**，各域**不许**自己写 `if (scope.type === 'all')`。
- **② 落地（各域自己拼）**＝ 各域 service / repository 按范围描述选**本域**的查询：`business_relation` 的归属落在**成员表**、`employee` 只有部门、`company` 是全公司共享（**根本没有 owner**）—— 表语义各不相同，**内核不替各域决定 SQL**（否则要为每张表在内核里加分支）。

⚠ **数据范围拦截器（`shared/interceptors/data-scope.interceptor.ts`）不查库、不改查询**：它只把「**本次请求的范围**」打标到请求上（供出口 / 审计 / 测试用同一把键取）。★ 原文「**拦截器把"我能看到谁"注入到查询条件里**」**作废** —— 拦截器挂在 Nest 的响应管道上，**改不了** service 内部的 Prisma 查询（2026-09-15 校正）。

**四档语义**（口径不变）：

- **销售** `self`：`owner_id = 我` ∪ `relation_member 里我是 collaborator 且未过期`（含 `ask_help` @求助）∪ `公海`（★ 2026-09-18 明确＝**本部门**公海，**别部门的公海看不到**；且公海**可读不可写**，唯一例外＝改开发价值）
- **交付 / 客服** `serving`：**仅「服务中」客户**（＝**在合同服务期内**，2026-09-14 定）及其公司档案 / 合同 —— **只读**、**不进公海**、**不触发掉公海**
- **部门经理** `dept`：`dept_id ∈ 我管辖部门`（`dept_manager`）
- **总经理 / 管理员** `all`：不过滤（管理员另有「**只读** ＋ **每次查看写 `operation_log`** ＋ **不解除金额脱敏**」约束，→ 接口 §2.2）

> **档位只表达"能看到谁"**：`只读` / `留痕` / `不脱敏` 属**写权限与出口渲染**，不塞进档位值（塞进去会逼每个消费方解析一堆与可见范围无关的位）。
> ⚠ 一人多角色的合成规则（如「销售 ＋ 交付」）**规格未定义**，本项目技术口径＝**取更宽的那一档**，宽窄序 `all > dept > self > serving`（与"主角色取权限最大者"同思路）；已记入 M1 完成报告「规格缺口」待拍板。

**所有列表查询必须经过 ①（kernel 的判定入口）**；禁止在 repository 里手写 `where owner_id = ...`（那＝在第二处落点重造范围判定）。

### 7.3 脱敏渲染（判定在 kernel，渲染在各域出口 —— 2026-09-15 校正措辞）

> **业务口径权威落点＝《需求》§4.3**；本节只讲「**出口渲染**」这一层（出参形态亦见 `→数据架构§十一`）。

**★ 原文「返回前**统一处理**」已按实现校正**：脱敏是**三处一条链**，不是"由拦截器统一改写"：
① **判定规则** ＝ `kernel/common/desensitize.ts`（跨业务线**按部门**判）＋ 各域 `domain/`（本域私有规则，如 B 域联系人「锁」的可见性）；
② **出口渲染** ＝ **各域 service 组装出参时**按规则填（列表 / 卡片给 `phone_masked`、详情给 `phone`、被 owner 上锁且查看者非 owner 给 `phone_locked`）；
③ **出口豁免** ＝ `@DesensitizeExempt()`（报表 / 看板 / 汇总）：拦截器只**读标记 ＋ 打标到请求**，**不逐字段改写**。
★ 为什么拦截器不改写：它**拿不到「这条记录属于谁」**（锁要读 `contact.phone_locked_*`、金额要读关系归属部门）—— 按字段名猜规则＝把"哪张表哪个字段怎么脱敏"再写一遍＝**第二真相源**（→ 踩坑 #9）。

**渲染矩阵**：

| 角色 / 场景 | 联系方式（**详情**） | 联系方式（**列表 / 卡片**） | 跨部门金额 | 跨部门跟单全文 |
| --- | --- | --- | --- | --- |
| 归属本人 / 协同人 | **全号** | `xxx****xxxx` | 真实金额 | 全文（可写） |
| 部门经理·**管辖内** / 总经理 | **全号** | `xxx****xxxx` | 真实金额 | 全文 |
| 销售 / 客服 / 交付 / 经理·**跨管辖** | **全号** | `xxx****xxxx` | `amount: null`＋`amount_masked` | **不可见** |
| **该关系已掉公海（无主）· 所属部门内** | **全号**（掉海 → 原 owner 的锁自动失效，→需求§4.3 二） | `xxx****xxxx` | 按上面各档 | **全文（跟单 ＋ 承诺 ＋ 阶段留痕）· 只读**。**唯一可写 ＝ 「开发价值」`value_tier`**（开发价值＝**部门共同维护** ⇒ 销售也能标；⚠ **不看 owner** —— 无主关系没有 owner 可看）；**写跟单只能在私海** |
| 管理员 | **全号**（只读＋留痕） | `xxx****xxxx` | `amount: null`＋`amount_masked` | 全文（只读） |
| **任意角色 · 该联系人被 owner 上锁且查看者非 owner** | **`phone_locked`（不给 `phone`）** | `xxx****xxxx` | —— | —— |
| **报表 / 看板 / 汇总** | — | — | **不脱敏** | — |

> ★ 2026-09-11 已定：**报表、看板、汇总出口不脱敏**（经理 / 老板看真实金额）。
> ★ **2026-09-14 重写**：联系方式**详情默认全可见**（**与角色无关**）、只有**列表 / 卡片**给掩码（**是出参形态、不是权限**）；新增**联系人「锁」** —— **仅归属关系 owner 可锁**、**落锁人审批**、放行 **24h**、**掉公海 / 离职 / 转岗自动失效**（`→需求§4.3`）。**规则写在一处，改口径只改这一处。**

### 7.4 审计留痕

> ★ **2026-09-15 口径扩写**（七叔：「**符合等保标准，所有的增删改都有迹可查**」→ 需求 §4.2 ★）。
> 原文那句（登录 / 改手机号 / 审批 / 公海操作 / 金额改动）是**举例，不是穷尽清单** ——
> 下三条才是完整口径，**三条并存、别互相替代**。

**① 所有增删改都留痕（覆盖面无例外）**：由**统一审计切面**（`kernel/audit/audit.decorator.ts`
的 `@Audit('模块.动词')` ＋ `shared/interceptors/audit-log.interceptor.ts`）在端点**成功后**自动写
`operation_log`：业务成功才落、业务失败不留（与 M5-07 判据「业务失败回滚后无 log」一致）。
**不许在各域 service 里各写一遍** —— 那正是本节首段「散在 ~80 个接口里各写一遍，必然有漏的」的复现路径。
⚠ 语义是读的写方法（如 `POST /companies/search-dup`）与**已有专门审计**的端点（登录）标 `@AuditSkip()`；
漏标不会漏审计（兜底名 `http.<method>`），并由 `shared/audit-coverage.spec.ts` **机械卡住**。

**② 敏感动作仍在业务事务内（额外要求）**：**登录 / 改手机号 / 审批 / 公海操作 / 金额改动**这些敏感动作，
额外在**业务事务内**写 `operation_log`（数据架构 A10）：操作人快照 ＋ `before/after` ＋ IP/UA ＋ `req_id`，
**业务失败则一起回滚**。★ 为什么两条并存：切面在事务外，**拿不到改前值**；要前后快照就得在业务事务里写。

**③ 查看类留痕＝独立写入（best-effort）**：管理员的「**每次查看写 `operation_log`**」（需求 §4.2 ★ / §4.3 三，
如 `event.view`）走 `AuditService.recordStandalone()`。★ 读路径**本就没有业务事务**，硬造一个只会污染语义；
写失败**只记系统日志、绝不冒泡**（审计表抖动不能让谁看不了客户）。代价＝可能丢记录，属**明示取舍**。

**④ 越权尝试也留痕（401 / 403）**：动作名 `authz.denied`，由**全局异常过滤器**
（`shared/filters/all-exceptions.filter.ts`）写。★ 为什么在过滤器：401 由**守卫**抛、403 由业务 service 抛，
**都发生在拦截器之外** ⇒ 上面那条切面**根本看不到**它们；过滤器是唯一能覆盖"所有失败出口"的位置。
`operator_id` 取不到请求上下文时落 `0n`（A10「系统动作 = 0」）并在 `detail.operator_kind` 标 `anonymous`。
⚠ 只记 401 / 403（安全关注点）：400 / 422 这类调用方参数问题**不记**，否则审计表被噪音淹掉。

### 7.5 异常映射（P2002 → 409 / 422）

Prisma 的唯一约束冲突错误码是 **`P2002`**（不是 MySQL 的 1062）。全局异常过滤器统一映射：

| 错误 | 映射 | 场景 |
| --- | --- | --- |
| `P2002` + `uk_active_rel` | **409** | 激活竞态 →「已有归属：张三」 |
| `P2002` + `uk_phone_active` | **409** | 撞单 →「该手机号已存在」 |
| `P2002` + `uk_owner` | **409** | 一关系多 owner |
| `P2025` | 404 | 找不到记录 |
| 业务校验失败 | **422** | 未标开发价值 / 缺签约必填项 |

约束名从 **`meta.driverAdapterError.cause.constraint.index`** 读出（**v7 下已无 `meta.target`**，→ 废止口径登记表 #29），返回人话提示，**不把「Duplicate entry」这种数据库原话丢给销售**。

> **取值位置的实现细节与真库实测记录 → `服务端/prisma/README.md §七`（唯一落点）**；本节只保留「分档映射」这一层的设计。

## 八、扩展路线（三阶段，每阶段只改一处）

### 8.1 阶段一（现在）的部署形态：本机 phpStudy 开发 → 服务器 Docker Compose

> 2026-09-12 定：**本机不走 Docker**（本机没装 Docker，起库 / 起缓存直接用 phpStudy 小皮面板）；`docker-compose.yml` 从「本机起环境」改任「**服务器 / CI 的部署描述**」—— 一份文件、两个用途。

| 项 | 本机（开发期 · 现在） | 服务器（试用期） |
| --- | --- | --- |
| 起库 / 起缓存 | phpStudy 小皮面板：MySQL **8.0.12** ＋ Redis **3.0.504** | `docker compose`：`mysql:8`（**须 ≥8.0.16**）＋ `redis:7` |
| 连接串 | `…@127.0.0.1:3306/win_crm`、`redis://127.0.0.1:6379` | `…@mysql:3306/win_crm`、`redis://redis:6379` |
| 业务代码要改吗 | — | **不用改，只换 `.env`** |

**服务器上四个容器**（同一个应用镜像，分两个角色）：

| 服务 | 镜像 / 命令 | 要点 |
| --- | --- | --- |
| `mysql` | `mysql:8`（**≥8.0.16**） | `--default-time-zone=+08:00`、utf8mb4 / utf8mb4_unicode_ci；具名卷 `mysql_data` |
| `redis` | `redis:7` | 具名卷 `redis_data` |
| `web` | 应用镜像 → `npm run start:prod:web` | **可多开**（无状态，会话在 Redis） |
| `worker` | **同一镜像** → `npm run start:prod:worker` | **恒 1 个实例**，多开＝定时任务重复跑（§六） |

前端 `前端/dist` 交给对外的 Nginx / Caddy（或轻量服务器自带反代），不塞进 Node 容器。

**六条硬口径**（都是既有铁律的延续，不是新规矩）：

1. **Worker 只跑 1 个** —— 否则掉海扫描重复写 `operation_log`；
2. **3306 / 6379 不对公网暴露** —— compose 里**不写** `ports`，只走容器内网；
3. **MySQL ≥ 8.0.16** —— 本机 8.0.12 的 `CHECK` 是「解析后静默忽略」，服务器上会**真生效**（M0-19b 在此复验）；但**应用层兜底单测照样要写**（本机开发也得过）；
4. **时区 +8 ＋ utf8mb4** 与本机口径一致，否则 `DATETIME(0)` 整体漂；
5. **具名数据卷** —— 否则一次 `docker compose down` 数据全丢；
6. **`.env` 不进 git**，`JWT_SECRET` 用真随机，别抄 `.env.example` 的占位值。

**首次部署顺序（一次性）**：

1. 装 Docker Engine ＋ `docker compose` 插件（官方脚本，别用系统源旧版）；
2. 传 `docker-compose.yml` ＋ `.env`；
3. `docker compose up -d mysql redis` → 等 healthcheck 过；
4. 把 `prisma/migrations/0001_init/migration.sql` 挂进容器执行，灌出 `win_crm`；
5. `npx prisma migrate resolve --applied 0001_init` 登记基线；
6. `docker compose up -d web worker`；
7. 反代 ＋ HTTPS，托管 `前端/dist`；
8. **重跑 M0-14 ~ M0-19 的核对**（`show create table` 那套），把本机跳过的 `CHECK` 验收补上。

> ⚠ 第 4 步有坑：本机 8.0.12 跑得过的 SQL，到服务器 8.0.4x 上要**完整重跑一遍**再确认 —— 分区、生成列、`ON UPDATE RESTRICT` 这些跨版本行为会变。

**回滚**：镜像打 tag（如 `win-crm-web:2026-09-12-01`），出事 `docker compose up -d` 换回旧 tag；DB 变更只走 migration 编号，不手改数据。

| | **阶段一 · 验证期（现在）** | **阶段二 · 增长期** | **阶段三 · 规模期** |
| --- | --- | --- | --- |
| **触发条件** | — | 接口变慢 / 全员上量 / 看板卡 | 单表破千万行 / 某域要单独扩容 |
| 部署 | 1 台机器 · Docker Compose | 2~3 台 | 多机 |
| Web | 1 个实例 | **扩到 N 个**（无状态已验证） | N 个 ＋ 负载均衡 |
| Worker | 1 个 | 1 个（不变） | 1 个（不变） |
| MySQL | 单库 | **加只读副本，报表走副本** | 按域分库 |
| Redis | 只用会话 / 字典 | **加业务缓存**（客户列表、看板等热点） | 加集群 |
| 域 | 7 个模块在一个进程 | 不变 | **把最忙的域拆出去**（大概率是 D 行动引擎 或 B 客户资产） |
| **改造点在哪** | — | 改配置 ＋ `report` 模块的连接串 | 搬文件夹 ＋ 事件改走消息队列 |

**为什么能"不重写"？**

| 扩展动作 | 为什么不用改业务代码 |
| --- | --- |
| Web 多开实例 | 进程无状态（会话在 Redis），直接多开 |
| 定时任务不会重复跑 | Worker 本来就独立，只有 1 个 |
| 报表走只读副本 | 报表已经圈在 `report/`，只改这一处连接配置 |
| 拆某个域为独立服务 | 域边界已硬卡，**搬文件夹 ＋ 把同步调用换成事件** |
| 换 Redis / 换消息队列 | 缓存与异步已走接口，只换适配器实现 |

## 九、开发顺序（竖切一条动线）

> **一句话**：在《数据架构文档》§十五.4 的域顺序（A/B/C → D → E/G → F）基础上，**每个域只先做"这条动线用得到"的最小切片**，先把一条完整业务线打通、先能用；每个域剩下的功能（导入、合并、留痕、报表…）在骨架验证通过后按域顺序补齐。

> **为什么竖切比横切快？** 横着做（A 域全做完再做 B 域）会在很长时间里看不到任何可用界面，而且第一次集成时才暴露域间衔接问题 —— 那才是真正拖慢验证的原因。

**目标动线**：登录 → 建公司/联系人 → 建业务关系 → 写一条跟单 → 工作台看到它
（这一条线会**穿透 A、B、C、D 四个域**。）

| 步 | 做什么 | 交付标志（能看见什么） |
| --- | --- | --- |
| **0** | **打地基**：`kernel`（上下文 / 事件 / 审计 / 错误映射）＋ Prisma 接入 ＋ 全局过滤器 ＋ OpenAPI 骨架 ＋ ESLint 边界规则 | `start:web` 起来了，`/docs` 能看到接口文档骨架；**故意写一个跨域 import，`lint` 报错** |

## 十、现在明确不做（防止过度设计）

| 不做 | 为什么 |
| --- | --- |
| 微服务 | **理由见 §三**（需求未验证 + 分布式复杂度 + 无人运维，本章不重复论证） |
| 分库分表 | 单库足够；**3 张**表已有时间分区（`stat_daily` / `operation_log` / `job_run_log`） |
| 通用表单 / 低代码引擎 | `field_template` 已够轻；升级成平台是另一个项目 |
| 多租户 | 就一家公司；多租户会污染每一张表 |
| K8s / 服务网格 | 一台机器到阶段二都够用 |
| 消息队列（Rabbit / Kafka） | 进程内事件总线够用；**接口先定好，将来换 MQ 不改业务代码** |
| 用文件代替 Redis / 缓存 | **会亲手堵死「Web 多开」**：会话落文件后 Web 一多开就各读各的文件，上服务器进容器后文件锁语义更不可靠（§八 明写「Web 多开＝进程无状态、会话在 Redis」）。真连不上 Redis 时的兜底是**落 MySQL 表**（多进程天然共享、有事务与唯一键），**不是文件**；正解是**缓存走接口**，换实现只动一个适配器（§八） |
| 读写分离（现在配） | 没压力，配了反而增加排查成本；`report/` 已预留入口 |
| 分布式事务 / Saga | 跨域不发大事务，天然不需要 |
| 前端 monorepo（Lerna / Nx / TurboRepo） | 那是**千人团队 / 跨项目复用**的解法；本项目**单仓单前端**（`前端/`），照抄＝杀鸡用牛刀（→ §4.4 调研件） |
| 前端组件发 npm 包 | 跨**项目**复用才需要发包；本项目只在**项目内**复用，目录里放一个组件即可（→ §4.4 约定 2） |
