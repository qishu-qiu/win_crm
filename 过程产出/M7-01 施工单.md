## 〇、起点（先自己核一遍）

- 端点规格只有**一行**（接口 §4.5）：`POST /sea/company/:id/claim` ——「**幂等（§2.5）**；领取即**继承原 owner 全文跟单**」；**§5 无该端点的形状章节**（req / resp / 错误码全无）。
- 级联只有一处写全（接口 §5.6 尾）：领取瞬间 **open 承诺 `owner_id` 转新 owner**；领取后新建跟单 `owner_snapshot` 取新 owner；前主人轮次跟单保留旧快照（→ 需求 §8.1）。
- 原子性硬口径：数据架构 **§10.2-3**「抢公海认领 ＝ **条件 UPDATE**（`WHERE sea_status='company_sea'`），影响 1 行才算抢到，否则 **409**」。
- 表**已落库**：`sea_record`（F2）＋ `sea_rule`（F1）已在 `schema.prisma`；`business_relation` 有 `sea_status` / `stage_id`；`relation_member` 有 `uk_owner`（生成列，在位 owner=relation_id，条件含 `revoked_at IS NULL`）。
- **现状（别重复造）**：`服务端/src/modules/` **只有 4 个域**（company / engine / org / relation）——**F 域目录不存在**；C 域 controller **只有 6 条路由**（列表 / 建 / 详情 / 改属性 / 成员 G+P），**没有 stage 路由**（即 `relation_stage_log` 的写入能力**当前不存在**）；前端公海入口＝关系列表页公海页签 ＋ 抽屉（D-32 只给了「开发价值」）。

## 一、本片要交付什么（三小片，各自独立提交）

### 片 1（核心）：后端——一次领取的完整闭环

**端点** `POST /sea/company/:id/claim`（`:id` ＝ **公司 id**）。

- **req（本次定稿）** `{dept_id, product_line_id}` —— 与 `POST /relations` 逐字同形：部门 × 产品线是**业务关系**的属性，公海的一"条"＝**一条业务关系**（→ 需求 §6.3），故必须能定位到具体那一条。
- **定位规则**：按「公司 ＋ `dept_id` ＋ `product_line_id` ＋ `sea_status='company_sea'` ＋ 未删未并」取关系；**同三元组若多行**（掉海残留），取 `sea_record.dropped_at` **最新**的一条；一条都没有 → **404 / 400**（具体码见下方「错误」）。
- **resp**：本次**不新造形状** —— 复用 C 域 `RelationVo`（列表项/详情形状的唯一落点）＋ `sea_record` 回填结果（`claimed_at`）。前端可据此直接跳 `/relations/:id`。
- **错误**：① 定位不到公海关系 → **400**（`sea.relation_not_claimed`）；② 并发被抢（条件 UPDATE 影响 0 行）→ **409 / `20401`**（"抢公海"＝竞态族，→ 接口 §2.4）；③ 越权 / 只读角色 → **403**（`sea.out_of_scope` / `relation.read_only`）；④ `dept_id` / `product_line_id` 不存在 → **400**。
- **权限（本次定稿）**：**可写角色 ＋ 读范围**，与 D-32 的读门**同一档** —— 销售＝**本部门**公海、经理＝**管辖部门**、总经理＝全部；**管理员（`all` 档但只读）与交付 / 客服一律拒**。不另开一格权限。
- **级联（三件，跨域禁大事务）**：
  1. **认领本体（C 域）**：一条条件 UPDATE 同时做 —— `sea_status: company_sea → private` ＋ **`stage_id` 置 1**（新一轮，→ 需求 §8.1）；`updateMany` **count === 1** 才算抢到，否则 409。
  2. **owner 成员（C 域，同事务）**：先撤在位 owner 行，再"**复活或插入**"新 owner 行 —— ⚠ **不能盲插**：`uk_member(relation_id, employee_id, member_type)` **不含 `revoked_at`**，同一人曾在该关系当过 owner（掉海时被撤销）再领回 → INSERT 撞 `uk_member`；正确姿势＝查到既有行则 `revoked_at=null` 复活，否则 INSERT。
  3. **阶段留痕（C 域，同事务）**：`stage_id` 原值 ≠ 1 时写一行 `relation_stage_log{from_stage: 原值, to_stage: 1, action: 'normal', reason: null, operator_id}`（**不新造 reason 码**；`action` 取值域＝normal/jump/rollback/lost，重置属"正常推进到新一轮"）。
  4. **`sea_record` 回填（F 域）**：把该关系**最近一条** `sea_record` 的 `claimed_by` / `claimed_at` 写上；**没有历史行 → 跳过、不造行**（掉海任务未建，不许假装掉过海）。
  5. **open 承诺转 owner（D 域）**：⚠ **走领域事件**，原因见下节 ★。
- **幂等**：§2.5 的 `Idempotency-Key` 横切**尚未实现**（→ D-06，同现状不额外要求请求头）；**语义幂等**由 ② 保证 —— 重复调用第二次定位不到公海关系 → **400**（不是 500、不是双写）。

### 片 2：前端——公海抽屉加「领取到我的私海」

- 入口＝关系列表页**公海页签**的抽屉（现只有「开发价值」）；按钮点击 → 确认（公海领取不可逆）→ 调 claim → 成功跳 `/relations/:id`、失败按服务端人话提示（尤其 **409 抢公海**：要重新拉列表）。
- **不摆假入口**：领取前**不出现**写跟单 / 标记 / 建承诺（D-32 已定）；领取后这些入口自然出现（关系已私海）。
- 页面**不许**自己判"这关系是不是公海"来决定能不能显示按钮 —— 以服务端返回为准（前端再判一遍＝第二套规则）。

## 二、动手前必须知道的 3 条（做错就返工）

1. **★ F 域与 D 域同层，禁止互相依赖**（架构 §3：`L3 relation(C) → L4 engine(D)/trade(E)/sea(F)/approval(G)`，**同层禁止直接依赖**）⇒ 「领取时把 open 承诺 `owner_id` 转新 owner」**不能**由 F 域同步调 D 域出口，也**不能**反过来让 D 域编排领取。**唯一合规路径＝领域事件**：F 域发 **`RelationClaimed`**，D 域订阅后转承诺 owner（承诺不要求同步返回 ⇒ 正是 §5.2「路之②：不等结果」）。⚠ 该事件的**唯一清单落点是《架构设计说明》§5.3** —— 加它要**同批**改架构说明（结构层事实源），不是随手加个字符串。
2. **C 域的"表"只能 C 域改**：F 域**不许**直接 UPDATE `business_relation` / INSERT `relation_member` / `relation_stage_log`（架构 §5.2）⇒ 认领本体 ＋ 成员 ＋ 阶段留痕这三件**都在 C 域新出口里做**（F 域只编排 ＋ 写自己的 `sea_record` ＋ 发事件）。
3. **`business_relation` 没有 `owner_id` 列**（owner 的唯一落点是 `relation_member` 的 owner 行）—— 数据架构 F2 里"与 `business_relation.owner_id` 同步写入"一句是**过时表述**（按 C1/C2 实际：归属看成员行），本片按成员行实现，不新增列。
