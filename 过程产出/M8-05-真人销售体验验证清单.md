## 二、CLI 跑出的待确认问题（交给销售前必须拍板）

### ① 【已修 D-76 `7e4a54b`】已关联公司的联系人写跟单 403 已生效
- **现象（CLI N08）**：用 `POST /contacts` 带 `company_id` 建档的联系人，再 `POST /contacts/:id/events` 返回 **200**，未按接口 §5.7 返回 `403 "请到业务关系里记"`。
- **根因（已定位）**：`服务端/src/modules/company/company.service.ts` 的 `createContact`（约 L405）**无条件** `owner_id: operatorId`，即便 `company_id` 已传入（已关联公司）。而 `engine.service.ts` 的"已挂公司 403"依赖"已关联联系人的 `owner_id` 为 null"（需求 §6.1 ⑦：归属转给业务关系）。于是"本人建的已挂公司联系人"仍带 `owner_id`，§5.7 的拦截对它不生效。
- **影响**：销售可绕过"请到业务关系里记"，在"已关联公司"的联系人上继续记跟单——破坏"联系人 ＝ 待关联线索、业务关系 ＝ 跟单主战场"的模型边界。
- **修复（D-76 `7e4a54b`）**：`createContact` 带 `company_id` 建档时 `owner_id` 置 `null`（与"激活业务关系"动线同口径）；`engine.recordContactEvent` 的"已挂公司 `owner_id` 为 `null`"不变式恢复，已挂公司联系人再走 `POST /contacts/:id/events` → **403 `contact_event.not_mine`**；repository `CreateContactData.owner_id` 改 `bigint | null`；spec 断言同步改 `null`。★ **CLI 重跑 N08 现 PASS（返回 403）**。
- **真人复现**：前端"新建联系人"时若允许直接选"关联公司"，建完后在详情页"写跟进"应被拦截；当前不会拦，肉眼可见。

### ② 【已构造并实测 2026-09-30】库内无公海关系 → 新建关系＋真掉公海复测 N07/N12
- **构造**：新建公司＋关系（dept=2/line=1）→ **真撤销 owner 成员**（`revoked_at=NOW()`）**并**置 `sea_status='company_sea'`（与真实掉海 `dropSeaRelation`＋`revokeActiveOwner` 同口径：只改 `sea_status`、不删 owner 行）。验完数据已删。
- **N12 管理员领公海 → 403/20003 ✅**（角色拦在写门前，符合设计）。
- **N07 销售对掉海关系写跟单 → 422/20408 ✅ 已对（2026-09-30 真链路复测）**：`findActiveOwner`（`domain/relation-owner.ts`）正确读 `member.revokedAt`（`toMemberLike` 自 M3 起就映射 `revoked_at`、仓储 `RELATION_SELECT` 也选它）→ 撤销后的 owner 判为"非在位"→ `ownerId=null` → `checkSeaUnclaimed` 返回 `sea_locked`（422 / `20408`，人话"该公司还在公海（未领取）：要写跟单请先领取到私海"）。
- ⚠ **09-29 那次 N07 返回 200 是测试假象，非代码缺陷**：当时用 `mysql.exe` 经 PowerShell 构造掉海，而 PowerShell 会把 SQL 里的 `()` 当子表达式解析，导致 drop SQL **根本没执行**（关系从未真正掉海），写跟单仍走私海路径返回 200（本清单第四节已记此 phpStudy/PowerShell 怪癖）。**不应登记 D-77**——`toMemberLike` 从未漏映射 `revoked_at`（用 `git log -S` 可证自 M3 即在）。
- **真人验证**：见第三节"公海"步骤（N07 已对，前端领取/写跟单交互仍可走查）。

### ③ 【覆盖缺口】所有产品线均承接部门2/3 → D-74 的 422 无法触发
- 种子 7 条产品线 `dept_ids` 均为 `[2,3]`，所以"销售建关系选部门未承接的产品线"永远构不出（N04 实测返回 200）。
- **处理**：要么补一条"部门受限"的产品线种子，要么接受该分支只能靠单测覆盖。不影响交销售试用（销售本就不会选到不能选的线——前端只给可选线）。

## 三、必须真人销售体验的部分（CLI 测不了）

> 以下全部需要浏览器 + 真人操作。建议让**真实销售**（非开发）照做，记录卡点。

### 启动
1. 后端已在 3000（当前 dist）。若不在：`cd 服务端 && npm run build && node dist/main.js`。
2. 前端：`cd 前端 && npm run dev` → 打开 `http://127.0.0.1:5173`。

### A. 销售主流程走查（账号 13800000003）
1. 登录 → 落地页是否清晰（D-14：导航/待办/快捷入口是否一眼能懂）。
2. 建档公司：填名称→撞重预检提示是否人话；强行新建是否放行（需求 §12.1 分支4）。
3. 建档联系人：只填主号→自动归一；撞号提示（409 人话）是否友好。
4. 激活业务关系：选"我的部门 + 可承接产品线"→ 成功；**故意选别的部门**应被前端拦（对应 N03 的 403，验前端是否先把不可选部门/线灰掉）。
5. 写跟单：填"有效沟通"但漏 summary → 前端是否拦截（对应 N09）；正常提交后时间线是否展示。
6. 建承诺：选"豁免"但不填原因 → 前端应拦（对应 N11）。

### B. 数据范围与脱敏（对照 §8）
7. 销售视角列表/卡片：手机号应为 `phone_masked`（掩码）；详情页给全号（D-6/D-8）。
8. 经理（13800000002）登录：能否看到管辖部门2/3 的关系；能否看到销售看不到的。
9. 总经理（13800000001）：金额是否**不脱敏**（报表/看板/汇总出口不脱敏，§8）。
10. owner 上锁的联系人：非 owner 应见 `phone_locked`（§8 联系人锁定）。

### C. 公海（需先有公海数据，见②）
11. 销售在"部门公海"领取一条 → 变成私海（对应 CLI 未验的领取成功路径）。
12. 未领取就写跟单 → 应 422（N07）。
13. 管理员（13800000006）尝试领公海 → 应被拦（N12，只读角色）。

### D. 列表/看板体验（D-12/D-13/D-10）
14. 关系列表分页、筛选、排序是否流畅；`order_by` 是否只给白名单列（N13 已证后端拦非法列）。
15. 看板/汇总：金额不脱敏（§8）；数据是否实时。

### E. 异常与提示
16. 会话过期（清 token）→ 前端是否跳登录、提示人话（对应 N01/N02 的 401/20002 人话包）。
17. 表单校验错误是否就近提示、文案是否非技术（对应 N09/N11/N13 的 20001/20403）。

  ```sql
  DELETE FROM contact WHERE name LIKE 'M8NEG%';
  DELETE FROM company WHERE full_name LIKE 'M8NEG%';
  ```
