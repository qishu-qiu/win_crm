#### ⚠️ 违规项

**CODE-004 ⚠️ P2（中危）｜SQL OFFSET 深分页**

- **文件**：`src/modules/sea/sea.repository.ts` L363
- **证据**：
  ```sql
  LIMIT ${pageSize} OFFSET ${(page - 1) * pageSize}
  ```
- **问题**：`sea_record` 表增长后，深分页（OFFSET > 1000）会导致数据库扫描大量丢弃行，性能骤降
- **影响范围**：掉海记录列表查询（用户量 ≤ 100 时暂无实际影响，属于预防类改进）
- **整改建议**：改用游标分页（`WHERE dropped_at < lastSeenDroppedAt ORDER BY dropped_at DESC LIMIT N`），或在 README 登记技术债务

---

**CODE-006 ⚠️ P2（中危）｜`new Date()` 分散使用，服务端本地时间依赖**

- **文件**：分布在 `engine.service.ts`、`relation.service.ts`、`sea.service.ts`、`visit.service.ts`、`report.service.ts` 等 17 个文件共 **50+ 处**
- **证据**（典型样例）：
  ```typescript
  // engine.service.ts L351
  const eventAt = new Date();
  // relation.service.ts L466
  const now = new Date();
  ```
- **问题**：
  1. 直接取服务端本地时间，若服务器时区非 UTC（如 +08:00），跨时区/夏令时场景可能产生偏差
  2. 测试中需要 mock 时钟（`sea.service.spec.ts:867` 注释说明"钉死假时钟"），说明已经意识到这个问题
- **缓解因素**：`domain-event.ts` L65 注释明确"缺省 `new Date()`；补录/重放/单测可显式给"，domain 层纯函数均接受 Date 参数 → 业务逻辑本身不依赖硬编码时间
- **整改建议**：引入 `@nestjs/schedule` 的 `TimeProvider` 或自定义 `Clock` 抽象，Service 层通过 DI 获取当前时间；短期可登记技术债务

**CODE-011 ⚠️ P2（中危）｜EventBus 兜底使用 `console.error`**

- **文件**：`src/kernel/events/event-bus.ts` L51
- **证据**：
  ```typescript
  // L42 注释：异步投递失败的兜底（默认 console.error）；日志设施落地后由调用方注入替换
  // L51 实现：
  ```

- **缓解因素**：代码已设计为可注入（注释说明"由调用方注入替换"），属于预留扩展点
- **整改建议**：落地日志基础设施（Pino），在 EventBus 初始化时注入 `logger.error` 回调

**CODE-012 ⚠️ P2（中危）｜核心链路无显式限流**

- **范围**：所有对外 HTTP 接口（除全局幂等拦截器外）
- **问题**：缺少请求频率保护（rate limit），流量突增时可能雪崩
- **缓解因素**：NestJS 可通过 `@nestjs/throttler` 快速接入；当前阶段并发量可控
- **整改建议**：接入 `@nestjs/throttler`，按接口重要性分级限流（登录接口最严、查询接口适中、写接口宽松）

**CODE-001 ✅ 已修复（2026-09-30）｜Refresh Token 由 localStorage → HttpOnly Cookie（XSS 根因关闭）**

- **文件**：`src/api/request.ts` L27-28、L73、L151-163
- **证据**：
  ```typescript
  // L27-28
  const ACCESS_KEY = 'crm_access_token'
  const REFRESH_KEY = 'crm_refresh_token'

  // L156-157
  localStorage.setItem(ACCESS_KEY, access)
  localStorage.setItem(REFRESH_KEY, refresh)

  // L73 - doRefresh() 读取
  const refreshToken = localStorage.getItem(REFRESH_KEY)
  ```
- **风险**：localStorage 数据在同域任何 JS 都可读取（XSS 即可窃取全部会话）。refresh_token 是**长期有效**令牌（通常 7-30 天），被盗后可持续换取 access_token，攻击窗口远大于 access_token
- **整改建议**（按优先级）：
  1. **最优**：Refresh Token 迁移为 `HttpOnly Cookie`（后端改 `Set-Cookie`，前端自动随请求带上）——需后端配合
  2. **过渡**：短期 Access Token 保留 localStorage 但缩短过期（≤ 2 小时）+ 做 CSRF 防护（SameSite=Strict/Lax）
  3. **兜底**：给 localStorage 中的 token 加编码/混淆（仅延缓脚本攻击，非根治）

**CODE-003 ✅ 已修复（2026-09-30）｜`doRefresh` 加 5s timeout，超时即释放 `waitQueue`**

- **文件**：`src/api/request.ts` L72-87、L141-143
- **证据**：
  ```typescript
  // L72-87 — doRefresh() 用裸 axios，无 timeout
  async function doRefresh(): Promise<string> {
    const refreshToken = localStorage.getItem(REFRESH_KEY)
    if (!refreshToken) throw new Error('缺少刷新令牌')
    const { data: body } = await axios.post<ApiResponse<RefreshResult>>(
      `${request.defaults.baseURL}${REFRESH_PATH}`,
      payload,
    )
    // ...
  }

  // L141-143 — 挂起队列无超时兜底
  return new Promise((resolve, reject) => {
    waitQueue.push({ config: original, resolve, reject })
  })
  ```
- **问题**：`doRefresh()` 内部用裸 `axios.post` 不经过 request 拦截器（这是正确设计，避免递归触发刷新），但裸 axios 没有 `timeout` 配置。如果后端挂了/网络闪断，`doRefresh()` 会永远 pending → `isRefreshing` 永远为 `true` → 后续所有 401 请求无限堆积在 `waitQueue` 中
- **影响范围**：所有需要刷新令牌的接口；用户看到的是页面永远 loading
- **整改建议**：
  ```typescript
  // 给 doRefresh() 加独立 timeout
  const { data: body } = await axios.post<ApiResponse<RefreshResult>>(
    `${request.defaults.baseURL}${REFRESH_PATH}`,
    payload,
    { timeout: 5000 }, // 5秒超时
  )
  ```
  并在 timeout 触发后主动执行 `waitQueue.forEach(({ reject }) => reject(timeoutError))` + `window.dispatchEvent(UNAUTHORIZED_EVENT)`
