## 一、P0 · 阻断开工（改完才能跑 M0）

### P0-1 🔴 `migration.sql` 视图带 `COMMENT` → 建库必报 1064，视图与其后 CHECK 全不执行

- **位置**：`服务端/prisma/migrations/0001_init/migration.sql:1167-1168`
  ```sql
  CREATE OR REPLACE VIEW `v_contract_performance`
  COMMENT '合同业绩分配视图（无分配记录→100% 归 signer；有分配→按 percent 摊；业绩统计一律读本视图）' AS
  ```
- **判据（已核 MySQL 8.0 官方手册原文）**：`CREATE VIEW`（15.1.23）与 `ALTER VIEW`（15.1.11）的**完整语法均无 `COMMENT` 子句**；`information_schema.VIEWS` 也无注释列 —— **MySQL 视图不支持注释**。
- **后果**：该行触发 `ERROR 1064`；用 `mysql < migration.sql` 执行时客户端默认**遇错停止** → **视图建不出来**，且紧随其后的 **④ `chk_approval_not_self` CHECK 段落（`:1183-1186`）也不会创建**。而「业绩统计一律读 `v_contract_performance`」（`数据架构:441`）是主线口径 → 报表全线断。
- **★ 同时暴露一处口径打架**：`服务端/prisma/README.md:22` 称「✅ 2026-09-12 已在真实 MySQL 8.0.12 上跑通并逐条核对（直接执行 migration.sql）」；而 `过程产出/开发计划-V1.md:96` 称该文件「⚠ **静态产出，未在真实 MySQL 8 跑过**（生成列/分区/视图/CHECK 待逐条核对）」。**二者必有一错**，且 `开发计划:484` 把"migration 未上真库"列为 ★风险。
- **改法**：① 删掉视图上的 `COMMENT '…'`（说明改写成 `--` 行注释，或写进 `服务端/prisma/README.md`）；② **在真实 MySQL 8 上重跑一次全量 migration 并逐条核对**，然后以实测结果**统一 `prisma/README.md:22` 与 `开发计划-V1.md:96` 的口径**（二选一，不留两说）。

### P0-2 🔴 `company` 表缺「注册资本 / 法人」→ 签约校验**无列可查**，成交主流程卡死

- **需求侧要求**：`需求规格/销售CRM业务需求文档.md:347`「成交后强制：信用代码、**注册资本**、**法人**、注册地址（不达不能签约）」；`:353`「系统给一套默认清单（**公司级 4 项＝信用代码/注册资本/法人/注册地址** ＋ 行业/地区 ＋ 关系级开发价值 ＋ 签约联系人关联）」。
- **数据架构侧播种**：`销售CRM数据架构文档.md:448` `scope=company` 的 `field_key` ∈ `{credit_code, registered_capital, legal_person, registered_address, industry, region}`；`:451` 「默认清单（系统播种）… `scope=company` **6 项** … `required=true`」；`:452` 校验逻辑＝「逐项查对应层级字段是否非空 → 任一缺失 → 422」。
- **反证（一手核过字段清单）**：`数据架构:167-178` B1 `company` 全部字段为 `full_name / name_core / credit_code / industry_l1,l2 / province,city,district / scale / completeness_1,2,3 / website,address,bank_name,invoice_title,tax_no / longitude,latitude / merged_into / aliases` —— **没有 `registered_capital`、没有 `legal_person`**；「注册地址」只有 `address`；`industry` / `region` 也**没有同名列**（实际是 `industry_l1/l2` 与 `province/city/district`）。
- **后果**：默认清单 6 项里 **4 项的 `field_key` 在库里找不到对应列** → 「逐项查字段是否非空」**写不出这条 SQL**。开发要么瞎猜列名，要么签约硬卡 422 → **成交主流程（动线 6）直接断**。
- **改法（须拍板，二选一）**：
  - **A（补列）**：`company` 增 `registered_capital`（`Decimal(14,2)` 或 varchar）与 `legal_person`（varchar），`credit_code`/`address` 已在 → 同步改 `schema.prisma` ＋ migration ＋ 数据架构 §10.1，完成度校验 `completeness_1/2/3` 一并纳入。
  - **B（对齐真实列名）**：把 E8 的 `field_key` 改成**真实列名**（`credit_code` / `address` / `industry_l1` / `province`），并把「注册资本 / 法人」**从默认必填清单删除**（若业务确要收这两个信息，就只能走 A）。
- **附**：`数据架构:175` 另写 `website/bank_name/invoice_title/tax_no`「成交后强制补组」，这 4 项在 `需求 §7.3` 里**找不到对应要求**（需求侧只提"信用代码/注册资本/法人/注册地址"）→ 与 P0-2 一并拍板是"多收"还是"漏写需求"。

- **位置**：`销售CRM接口API文档.md:76`

### P0-5 🔴 接口 `uk_active_rel` 描述多一列 → 与 schema 不是同一个约束

- **位置**：`销售CRM接口API文档.md:217`
  > 「`POST /relations`（激活）… 唯一约束 `uk_active_rel(company_id,dept_id,product_line_id,`**`owner_active`**`)` 撞则 409 / 20401」
- **判据**：`销售CRM数据架构文档.md:250`
  > 「唯一索引 | `uk_active_rel`：同 公司+部门+产品线 仅一条活跃私海关系（生成列 `active_key = IF(sea_status='private' AND merged_into IS NULL, 三元组, NULL)` 实现；被并分支 `merged_into IS NOT NULL` 不占活跃位）」
- **后果**：`owner_active` **在 schema / 数据架构里都不存在**（同名的近亲是 `relation_member.owner_flag`，是另一张表的另一个约束）。照接口字面实现 → **写出一个错误的唯一键**，撞单判定（撞单 SOP 的第一道闸）直接错乱。
- **改法**：接口改述为 `uk_active_rel(active_key)`，并补一句"三元组 ＋ `sea_status='private'` ＋ `merged_into IS NULL` 的条件由生成列表达"。
