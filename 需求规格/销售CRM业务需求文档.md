## 二、产品定位：一份事实账本，三个出口

**一句话定位：系统是销售的助理，不是销售的监工，也不是老板的收银机。**

```
        销售出口（干活用）              经理/老板出口（看盘用）          客户出口（履约用）
   「吃我说的」我认账              「吃我留下的」被动算             「吃承诺与节点」自动触达
  承诺到点提醒 / 今天该找谁         队伍健康度 / 客户盘子            履约通知 / 续约提醒 / 服务回访
  一句话档案 / 少填表              掉海风险榜 / 回款与转化            （V1 后置，架构预留）
        ▲                                  ▲                                ▲
        └────────────────┬─────────────────┴──────────────┬─────────────────┘
                         ▼                                ▼
                 CRM · 一份事实账本（所有业务数据）
      承诺 · 预约 · 事件流(跟单/客情) · 业务关系 · 公司档案 · 合同回款 · 工单
```

**三层含义**：
- **销售出口**吃"**我说的**"——我答应客户什么、我约了谁、我判什么；
- **经理出口**吃"**我留下的**"——跟单频率、回款、工单，全靠被动聚合，**不要求销售多填一个字段**；
- **客户出口**吃"承诺与节点"——V1 后置，先把前两个出口做透。

### 2.1 设计五铁律（任何新需求先过这五条）

| # | 铁律 | 白话 | 违背后果 |
|---|---|---|---|
| **T1** | **加规则 = 加行，不是加列** | 新判断、新节奏、新提醒一律进配置（规则表 / 字典 / 字段模板），主表永不新增判断列 | 表越加越胖，销售被迫维护一堆状态 |
| **T2** | **录入摩擦趋近于零** | 销售干活时 10 秒顺手留；**任何"为让系统/经理好看"而设的必填项一律砍掉** | 销售变文员，数据变假 |
| **T3** | **经理出口只吃"留下的"，不吃"填的"** | 报表只从事件流/回款/工单被动聚合；**绝不要求销售确认处境、点卡点、填报表字段** | 销售为老板打工，系统成负担 |
| **T4** | **推导只建议，销售说了算** | 系统推导（阶段推进、价值）一律"建议态"，销售一键接受/拒绝 | 系统自作主张，销售不信任 |
| **T5** | **停用不删** | 表/字段/字典项/规则停用后保留，历史数据照常展示 | 历史断裂、追责无据 |

> **T2 唯一例外**：判死 / 流失出口必须点选一次死因（30 秒、一单一生只判一次、错过不可补、直接决定"客户为什么不要我们"的战略数据）。**文字永不强制**。全系统仅此一处必填，新增任何必填必须先过 §十六 评审。

### 2.2 业务信条（不落表，但影响所有设计）

> **不存在吊着我们的客户，吊着的都不是意向。**
> 真实意向只有两种卡点——**见不到人** / **犹豫效价**。其余都是表象。

## 三、业务术语词典（大白话 ↔ 系统概念）

| 术语 | 大白话解释 | 属于哪一层 |
|---|---|---|
| **公司档案** | 一家客户公司一份，身份/制度/决策链建档勾一次、全公司共享。全项目禁用"公司画像"这个叫法 | 客户资产层 |
| **联系人** | 客户方的人；**手机号是唯一索引**，撞单就靠它。跳槽换公司保留历史就职 | 客户资产层 |
| **业务关系** | "我负责这家公司的法律线"——最小业务单元 = 公司 × 部门 × 产品线 × 归属销售 | 业务层 |
| **进度（阶段）** | 客观事实：谈到了哪一步（6 步） | 业务关系 |
| **紧迫（计划档）** | 主观计划：我打算多快拿下它（周重点/月重点/季度跟/长期跟/灰度） | 业务关系 |
| **客户等级** | 回款贡献：**这条业务线滚动 12 个月给我回了多少钱**（S/A/B/C/D，系统自动算、**按部门维度**、档位各部门自配） | 业务关系 |
| **快速标记** | 电话没接通这类"无效沟通"：**点一下即留痕，不强制写字**。必须落库（否则"打过多少次"统计失真），支持批量（见 §10.2） | 行动层 |
| **月度目标** | 公司 / 部门 / 个人三层月目标，**完成进度按回款额算**（并列显示签约额作参考）。老板看总进度＋分部门，经理看部门总进度＋每人（见 §7.11） | 目标层 |
| **开发价值** | 实力×契合度：这条线还值不值得我挖（高/中/低/待定，手动） | 业务关系 |
| **承诺** | **心脏**：我答应客户 X / 客户答应我 Y / 我定本周判 Z；有期限、有状态 | 行动层 |
| **事件/跟单** | 已发生的互动：电话/微信/拜访/请客…一句话留痕，是所有统计的唯一来源 | 行动层 |
| **客情动作** | 请客/送礼/问候——维护关系，不是推进成交，与业务跟进分轨 | 行动层 |
| **卡点** | 客户卡在哪（价格/效果/信任/见不到人/时机…），可选点选 | 行动层 |
| **预约** | 定好时间要见/要办的事，**完成必须留一条事件** | 行动层 |
| **补写跟进** | 逾期（该做没做）的预约 / 跟进，事后补一条记录说明办了没办、结果如何——**不是"补一张订单"**；工作台时间轴与预约页的「补写跟进」直达入口 | 行动层 |
| **今日动线** | 每天清晨系统排好"今天该花时间在谁身上"（工作台首页数据源） | 行动层 |
| **协同** | 共同跟进：可共同写事件、看全文、看全号。**正式协同走审批** | 归属层 |
| **@求助** | owner 写事件时 @ 同事 = **即时授予的临时协同，权限与正式协同一致**（默认 7 天自动收回、可撤销、免审批）。**限同部门**——跨部门须走正式协同审批（防策略泄露，见 §12） | 归属层 |
| **公司公海** | **公司档案本身就是公司公海**——全公司共享、全员可见的客户名单。任何部门都可在其上激活自己部门的关系（`→数据架构 B1`） | 流转层 |
| **部门公海** | 公海里的条目 = **一条业务关系**（不是公司）。＝ 本部门那些**暂时没有 owner** 的业务关系。掉公海 ＝ 关系失去主人，**部门恒定不变**（`→数据架构 C1`） | 流转层 |
| **竞争并行** | 跨部门同产品线同客户：各跟各的、**跟单互不可见**；**两条关系各签各的、互不干扰**（一方签约只在另一方关系上**提示不拦截**，不阻断）。**别的部门想要这个客户 ＝ 自己激活一条本部门的关系**（唯一约束含部门，互不冲突）——**不存在"跨部门捡公海"这个动作** | 流转层 |
| **竞品态势** | 这客户**没竞品 / 在用某竞品 / 正在比价**，写跟单时顺手点 | 竞品 |
| **策反/防守/竞争** | **系统推导，销售不标**：未合作×在用竞品=策反；未合作×比价/无竞品=竞争；已合作=防守 | 竞品 |
| **流失** | 已合作客户没了：被撬 / 到期未续费 / 服务不满 / 我们疏忽……**都是同一类流失，只是原因标签不同** | 复盘 |
| **出口复盘** | 三个出口动作上的顺手一问：转已合作(win) / 判死(loss) / 流失(churn) | 复盘 |
| **赢单弹药库** | 经理决定收录的赢单打法，**默认本部门可见**，总经理可设全公司 | 复盘 |

## 四、角色与权限（业务口径）

### 4.1 角色

| 角色 | 定位 | 主入口（登录后首页，2026-09-11 定） |
|---|---|---|
| 销售 | 客户经营与维护第一人（owner） | **工作台**（今日动线） |
| 交付/客服 | 售后工单、服务交付（不触发掉公海） | **工作台·工单待办版**（今日到期工单 / SLA 超时 / 待处理） |
| 部门经理 | 管辖部门全量可见；规则配置人；审批人；**弹药库质检员**；**离职批量转交发起人**（2026-09-14 定） | **数据看板**（部门盘 + 目标进度 + 周重点僵尸榜 + 公海决策待办） |
| 总经理 | 全公司可见；全局开关（如弹药库可见范围） | **数据看板**（全公司盘 + 总目标进度 + 分部门） |
| 管理员 | 组织/字典/规则维护；**离职批量转交的兜底发起人**（仅"该员工无直属经理"时，2026-09-14 定） | **组织架构**（组织 / 字典 / 规则维护） |

### 4.2 数据范围

| 角色 | 可见范围 |
|---|---|
| 销售 | 本人私海（owner + 协同）+ 公海；**他人私海一律不可见**（除非协同/@求助授权） |
| **交付/客服** | **仅「服务中」客户**（＝**在合同服务期内**，2026-09-14 定）及其公司档案、合同——**只读**；不进公海、不做客户经营动作（**不触发掉公海**） |
| 部门经理 | dept_manager 管辖的**全部部门** |
| 总经理 | 全部 |
| **管理员** | 以组织/字典/规则维护为主；**可查看业务数据（2026-09-11 定）——但一律「只读」，且操作全量留痕 `operation_log`**，不参与客户经营 |
| **一人多角色** | **取更宽的一档**（2026-09-15 定）：宽窄序 `all`（总经理/管理员）＞ `dept`（部门经理）＞ `self`（销售）＞ `serving`（交付·客服）—— 多挂角色**只会变宽、不会变窄**（如「销售 ＋ 交付」判 `self`，否则销售看不到自己的私海与掉海客户） |
| 跨部门同产品线 | 竞争并行：客户都可见，**跟单记录互不可见**（防策略泄露） |

> ★ **管理员可见业务数据的护栏（2026-09-11 定）**：管理员能看，是为了排查问题与（无直属经理时）兜底执行离职转交，**不是让他经营客户**。因此：①**只读**（不能写跟单 / 改关系 / 建合同）；②**所有查看动作写 `operation_log`**（谁、何时、看了哪个客户）；③**不解除金额脱敏**（仍按 §4.3 四）。既方便排障，又不留"无痕看全公司"的口子。

### 4.3 联系方式 · 锁 · 脱敏（库内永远明文全量，脱敏在应用层渲染）

> **★ 2026-09-14 口径重写（七叔拍板）**：联系方式**不再按角色 / 场景分档脱敏** —— 改为「**默认全可见 ＋ 联系人可上锁**」。原「手机号分档脱敏（非归属只给 `****{后4位}`）」**已废止**（`→《废止口径登记表》#30`）。

**一、联系方式：默认全可见；只有「列表 / 卡片」脱敏**
- **任何角色、任何场景，联系人的手机号在「详情」里都是全号** —— 归属本人 / 协同人 / 同部门同事 / 跨部门 / 公海 / 管理员，一律可见。（跨部门**跟单内容**仍互不可见，见 §4.3 三 / §4.2。）
- **只有「列表 / 卡片」保持脱敏**（`xxx****xxxx`）：这是**出参形态**、**不是权限** —— 目的是**防"一眼扫走一列号"的批量截图**；**点开详情即给全号**。
- 「能看见号」不等于「能打」：公海详情仍逐次写 `operation_log`（`sea.phone.view`，含 ip/user_agent）；**公海页仍全页水印**（工号 ＋ 姓名，截图可追责）。
- **理由**：号码是"能不能找到人"，**挡死业务换不来安全** —— 防盗靠「**不可导出 ＋ 逐条留痕 ＋ 水印追责 ＋ 上锁 ＋ 离职批量转交**」（`→§5.2`），不是把销售的手绑住。

**二、联系人「锁」＝ 销售的自我保护（2026-09-14 定）**
- **只有该联系人归属关系的 owner（主责销售）能上锁**；**协同人不能上锁，经理也不能替谁上锁**。
- **锁是全局的**：A 部门上了锁，**B 部门同样看不到** —— 手机号是**人**的属性，不允许出现"一半可见一半不可见"。
- **锁跟人：作用于该联系人的「全部号码」** —— 主号与 `extra_phones` **备用号一起锁**（2026-09-14 定），不允许"主号锁了、备用号仍全可见"；联系人其它字段与跟单内容**不受影响**。
- 上锁后，他人（含同部门同事）查看该联系人手机号 → 只看到「**已上锁**」提示 ＋「**申请解锁**」入口。
- **申请 → 审批**：申请人发起 → **由「落锁人」本人审批**（⚠ **本例** **例外于 §7.9「审批默认走直属上级」**：锁是**个人自我保护**、不是组织流程）→ **同时知会其直属上级**（防"锁着不放、无人知晓"）。
- **批准后限时可见 24 小时**，到期自动恢复到上锁态；**申请 / 批准 / 查看全量留痕** `operation_log`，防批量捞号。
- **解锁申请不设次数 / 频率上限（延续 2026-09-12 信条）**：**不做**"每人每天最多 N 次"这类限额。系统只负责**留痕**（谁、何时、解锁了哪个号）；是否有人批量捞号、要不要敲打，是**经理的判断**。**理由＝设计信条：系统只是助手，不干需要人干的事**（同 §10.4 预约过期）。
- **★ 锁的消失条件（一条规则覆盖三种情况）**：只要**落锁人不再是该联系人任一活跃关系的 owner**，锁即**自动消失**：
  ① **离职 / 停用**；② **转岗**（不再持有该关系）；③ **关系掉公海**（关系失去 owner）。
  → 因此**掉公海后联系方式必然全可见**（公海＝可打的资料池），这与「列表仍脱敏」**并不冲突**。
- **总经理 / 管理员可以强制解锁**（排障与离职兜底用，**强制解锁必须留痕**）；**部门经理不能强制解锁**。

**三、跟单内容可见度（跨部门互不可见，不变）**

| 角色 / 场景 | 跨部门 / 非归属 跟单全文 |
|---|---|
| 归属本人 | 全文（可写） |
| 协同人（正式协同 / @求助有效期内） | 全文（可共同写） |
| 销售 / 客服 / 交付 | **不可见**（仅"近 30 天 N 次"概览） |
| 部门经理·**管辖内** | 全文 |
| 部门经理·**跨管辖** | **不可见** |
| 总经理 | 全文 |
| 管理员 | 全文，但**只读**，且**每次查看写 `operation_log`** |

> 理由：跟单是"**我们怎么谈的**"＝策略，跨部门同产品线是**竞争并行**，泄露即伤单（`→§4.2`）。

**四、金额脱敏（跨部门）**

| 角色 / 场景 | 跨业务线金额 |
|---|---|
| 归属本人 / 协同人 | 真实金额 |
| 部门经理·**管辖内** | 真实金额（看盘需要） |
| 部门经理·**跨管辖** / 销售 / 客服 / 交付 / 管理员 | **完全脱敏（不显示数字）** |
| 总经理 | 真实金额 |

- **★「跨业务线」的判断口径（2026-09-10 定）＝ 按部门**：看这条业务关系**归属的部门**与登录人所属部门是否一致，**不一致 → 金额完全脱敏**。**不按产品线判断**——一人可挂多条产品线（`employee.product_line_ids`），按产品线判断会自相矛盾。
- **★ 报表 / 看板金额不脱敏（2026-09-11 定）**：脱敏**只作用于"销售看他人私海 / 跨部门关系"的列表与详情**；**经理 / 老板出口的报表、看板、汇总一律显示真实金额**——管理出口看得见数才管得了盘。

**五、其他不变项**
- **★ 公海内不做任何动作（2026-09-12 定）**：公海条目**不提供**标记（未联系 / 未接 / 说两句）、写跟单、改阶段任何动作，**也绝不因此重置掉海倒计时**（`→§6.3` / `§十六 N12`）；**"逐个联系"那种一屏一个客户的推进态只做在预约管理与工作台时间轴**（那里是有 owner 的客户）。
- **手机号变更**：走审批（`phone_change`，审批人＝**直属上级**），通过后**冻结 24 小时**才生效（防偷改客户资源）。
- **销售个人行踪/拜访轨迹不落库、不外显**（隐私保护）。

## 五、核心业务模型：公司档案 ＋ 业务关系（两层）

```
第 1 层  公司档案（唯一）＝ 事实上的公司公海
             1 家公司 = 1 个档案，全公司共享、**全员可见**
             任何部门都可在其上激活自己部门的关系
              │
              ▼
第 2 层  业务关系 = 公司 × 部门 × 产品线 × 归属销售   ← CRM 最小业务单元
              ★ 部门公海里的一条，就是它（不是公司）
              有 owner ＝ 员工私海 ／ 无 owner ＝ 掉公海（**部门不变**）
              一切跟单 / 合同 / 回款 / 续约 / 工单都围绕它展开
```

**三条原则**：
1. **客户主档案唯一且全员可见**——1 家公司 = 1 个档案（信用代码或全称匹配）；**这份档案本身就是公司公海**，不存在另一个"物理无主池"。
2. **公海的条目粒度是"业务关系"，不是"公司"**——"部门公海"＝ 本部门那些暂时没有 owner 的业务关系。掉公海 ＝ 关系失去 owner，**dept_id 恒定不变**，因此**不存在"改部门"、不存在历史归属断层**；别的部门想要这个客户，**自己激活一条本部门的关系**即可（见 §6.3）。
3. **业务关系是最小业务单元**——所有业务动作都挂在业务关系上，不挂在公司上。

### 5.1 业务关系唯一性与激活

- **唯一性**：同 公司 × 部门 × 产品线 仅一条活跃私海关系（后到者撞唯一约束 → 提示"已有归属"，引导申请转交/协同）。
- **激活顺序锁定**：第一个点"激活"的销售 = 该关系主责人，时间戳记录，**不可被覆盖**；后到者必须走转交/协同。
- **跨部门同产品线** = 竞争并行：双方都能跟、都能见客户，但**跟单互不可见**。**两条关系各跟各签、互不干扰**（2026-09-10 修正，取代原"谁先签约谁得"）——因为同一客户**可能确实有两次需求**（例如两个子公司各做一个网站），一方签约**不该阻断**另一方。一方签约后，在另一方关系上显示提示「**该客户已被 X 部门签约（日期）**」，**只看不拦**，由销售自己判断还有没有第二个需求。
- **同部门不同产品线** = 完全独立，各建各的关系。

### 5.2 归属规则（签单 / 维护 / 离职）

| 场景 | 规则 |
|---|---|
| **签单人（signer）** | 锁**业绩历史**，终身不变。离职也不动 |
| **主责人（owner）** | 客户经营与维护第一人，**永远只有一个**。谁在岗谁维护 |
| 换人维护 | 走**转交审批**，全量留痕。**★ 未兑现的承诺跟着客户走**（2026-09-10 定）：`me`（我答应客户）/ `verdict` 类承诺转给新 owner，`them`（客户答应我）类跟随关系不动。否则旧销售会一直收到"你答应客户 X"的提醒，可客户已经不是他的了 |
| 短期无法跟进（病假等） | 授**带期限的协同人**代看，**不动所有权** |
| **离职** | **由直属经理发起「离职批量转交」**（2026-09-14 定）：**批量勾选**该员工名下客户 / 业务关系，**可分给部门内不同在职业务员**（也可回公海）；走 **`relation_reassign`** 审批（发起人即直属上级时**上溯**到部门经理 / 总经理；该员工**无直属经理**时由管理员兜底发起，`→§7.9`）；**历史业绩仍归原签单人** |
| 客户主动要求换销售 | 主责人确认 / 部门经理重分 |

> **★ 离职后的业绩口径（2026-09-10 定）**：**历史业绩照常显示**（原签单人不变，离职也不抹），但**"人均"类指标只按当月在职人数算分母**——离职的人**不进分母**。这样既尊重历史贡献，也不会让离职人员稀释或虚高当期的人均数据。

> 不再设"维护人"这个独立概念（避免签单人/对接人/owner 三套归属打架）。**签单人锁业绩、owner 管维护**，两层足够；**售后的日常对接由客户台账的「销售对接人 / 交付对接人」两个字段承担**（可为销售或客服/交付，`→§7.7`）—— 对接人**可变更**，与 owner（谁在岗谁维护）是两件事。

## 六、客户生命周期与核心业务流程

### 6.1 生命周期全景

```
【0 线索/联系人】 电销/陌拜/表单/导入 → 录入联系人（手机号必填）→ **只建联系人，不建关系**＝「**待关联公司**」（销售名下待跟进，**跟单可挂在联系人上**）；问到公司 → 激活业务关系 → 转入员工私海
        ↓
【1 建立业务关系】 选部门 × 产品线 → 激活 → 自动建立业务关系
        ↓
【2 意向跟进】 写跟单事件（绑联系人）、建承诺、建预约
        ↓
【2.5 档案补全】 成交前补全公司档案（行业/地区/联系人）；成交后强制补（信用代码、注册地址）
        ↓
【3 签约成交】 建合同 → 自动结算签单人业绩 → 阶段置"已合作"
        ↓
【4 交付与回访】 工单交付 → 服务中 → 续约预警 → 回访 → 续约 / 流失
```

**关键**：录入时**允许只有手机号**，公司名可"暂不明确"；成交后才强制补全企业档案。
- **★ 「待关联公司」模型（2026-09-11 七叔定·方案 B）**：业务关系＝公司×部门×产品线，**没有公司就建不了关系**——所以未问到公司时：①**只建联系人**（不建业务关系、不掉海、不计入"名下关系数"）；②**跟单 / 快速标记 / 承诺可只绑联系人**（`action_event.relation_id` 可空，`relation_id` 与 `contact_id` **至少一个非空**）；③判定＝该联系人**无任何 `company_contact` 记录**（派生展示，不加字段）；④**关联公司并激活关系时，服务端自动把该联系人名下"无关系"的跟单批量挂到新关系**（历史不断，接手人看得到之前聊过什么）；⑤**节奏规则**：新联系人 **7 天**未关联公司 → 提醒补全（走 cadence_rule，T1 合规）；⑥此类跟单**计入销售工作量统计**，但不进关系维度统计。

### 6.2 各入口的落点

| 入口 | 录入内容 | 落点 |
|---|---|---|
| 电销 / 陌拜 | 联系人档案（手机号必填） | ①**问到公司** → 激活业务关系 → 员工私海；②**暂未问到** → 只建联系人＝「**待关联公司**」（销售名下待跟进，跟单可挂联系人，见 §6.1 模型 B） |
| 调研表单 / 批量导入 / 系统采集 | 联系人档案 | **公司公海**（按来源部门映射 → 显示于部门公海视图） |

> **「待关联公司」视图（派生，不加字段）**：判定＝该联系人**无任何 `company_contact` 记录**。入口：① 联系人列表筛选「**未关联公司**」；② 联系人详情顶部「⚠ 尚未关联公司」横幅 ＋「关联公司」入口（走 §12.1 撞库 → 激活关系 → 变正式私海关系）。**不进业务关系列表、不触发掉海、不计入"名下关系数"**（它只是个待跟进的人，见 §6.1 模型 B）。

### 6.3 公海与掉落规则

**关系粒度模型（2026-09-10 七叔重构，取代 09-09"池模型"表述）**：
- **公司档案 = 事实上的公司公海**：全公司共享、全员可见，它本身就是客户名单。任何部门都可以在它上面激活自己部门的关系。
- **部门公海里的每一条 = 一条业务关系**（不是公司）：＝ 本部门那些**暂时没有 owner** 的业务关系。
- **掉公海 = 这条业务关系失去 owner，`dept_id` 恒定不变**——所以**不存在"改部门"、不存在历史归属断层**。
- **别的部门想要这个客户 = 自己激活一条本部门的关系**（唯一约束含部门，互不冲突）——这正是"跨部门同产品线竞争并行"的落点。**不存在"跨部门捡公海"这个动作，也不存在"跨部门领取"的归属问题。**

**掉落触发（按业务关系维度，满足任一）**：
- 跟进频次未达标（最近 N 天**无有效跟进**）
- 成单周期超时（激活 N 天未签约）
- **推进进展停滞 = N 天内阶段未向前推进一格**（2026-09-10 定口径）

> **★ 什么算"有效跟进"（2026-09-10 定）**：只有**有效沟通事件**（写了内容、有实质交流）才重置"最近跟进时间"。
> **快速标记（未联系 / 未接电话 / 说两句挂了）不算**——它只留痕、供统计"这个客户打过 N 次"，**不重置掉海倒计时**。
> **为什么必须这样**：否则销售每天对 100 个客户点一下"未接电话"，所有客户就永不掉海了——**倒计时直接被刷爆**。（卡片上会显示"最近 30 天尝试联系 N 次"，经理看得到销售确实在努力，但客户该掉还是掉。）

> **为什么停滞看"阶段"而不看跟单的"结果"选项**：结果选项（outcome）是**选填**的（空=中性）。若用它判定停滞，就必须逼销售每条都选 → 违反 T2 录入摩擦趋零。阶段是销售本来就要确认的动作，**零额外负担**。这也对应 §2.2 的信条——阶段一直不动，就是"吊着"，不是意向。

> **★ 多联系人跟单口径（2026-09-11 七叔定）**：一条业务关系下可**同时**跟进多个联系人（今天见老板、明天见招商经理、后天见财务）——**见谁都算有效跟进，不按联系人角色区分含金量**：都重置 `last_event_at`、都计入跟进次数。
> - **不为一条关系再存一份"这条线谁说了算"**——`contact.decision_role` 是**跟着人走**的属性，跨业务线复用；若按关系另存一份，同一人在法律线是决策人、在财税线是影响人，就要维护两遍、还会打架。**不加字段、不加表。**
> - **防"吊着"的闸门是「阶段停滞」，不是「见了谁」**——与上面第 3 条掉落触发同源：只见财务、招商刷一百条跟单，只要阶段 N 天没往前走，照样掉海。**经理判断销售在不在混，看的是工作流 / 阶段的变化，不是跟单条数、也不是见了谁。**
> - **录入零负担**：跟单仍是一句话 + 可选点选；`contact_id`（本次对着谁）**选填**，但关系下已有联系人时**前端默认带出上次跟进的联系人**（一点即选，不选也可提交）——保证卡片上"对着谁"不空，又不硬卡。
> - 跟单卡片统一显示「**填单人 + 跟进的联系人**」，时间线按 `event_at` 混排（**不按人分组**）。
> - **★ 跟单 Tab 联系人筛选芯片（2026-09-11 七叔定 `→前端§6`）**：关系详情·跟单 Tab 顶部提供一排**联系人芯片**（含「全部」），点选即只看该联系人的跟单——销售回看"上次跟王总聊到哪"免翻全时间线。**纯展示、不影响规则、不新增数据。**
> - **★ 新增联系人首跟提醒只催决策人/影响人（2026-09-11 七叔定，`→§10.3`）**：一条关系下新增第 N 个联系人时，触发 `dept_rule.newbie_first_follow_hours`（建议 48h）首跟提醒——**但仅当该联系人 `decision_role` ∈ {决策人, 影响人} 才催；执行人 / 未定角色不催**（否则关系下有 10 个对接人就炸出 10 条噪音提醒）。提醒归属＝该关系 owner。

**掉落方向（只有一步）**：业务关系有 owner（员工私海）→（超时）→ 无 owner（公海）。**部门不变**，仍显示在本部门公海，本部门销售可再领取。

**公海停留超期（无人领取/无推进）→ 不自动流转，交给部门经理决策**：
- 系统把停留超期的公海客户列为**经理决策待办**（推送给管辖部门经理），**不自动删除、不自动转移到任何更深的池**（没有更深的池了）。
- **部门经理人工判断**：① **保留**——延期，或直接指派给某销售领取；② **删除关系**——该客户在本部门（×产品线）不再作为跟进目标：解除映射/作废该业务关系（逻辑删除，`deleted_at`，全留痕），公司档案与联系人保留、全部历史跟单保留可审计，其他部门仍可另行建立关系。
- **灰度寿命规则只做"提醒下结论"**（`→§8.2`）——**不产生释放候选、不落 `gray_release_at`**；灰度客户到期**照常掉公海**（掉海规则独立作用于灰度，两条规则各管一段）。

**预警节奏（三级，硬约束，永远置顶，仅作用于 私海→公海 这一步）**：
| 时点 | 动作 |
|---|---|
| 倒计时 ≤3 天 | 进入今日动线提示 |
| 到期前 24 小时 | 推送销售 |
| 到期前 6 小时 | 标红 + 推送部门经理 |
| 到期 | 执行掉落回公司公海，写历史记录（sea_record） |

**公海停留超期节奏（不自动）**：系统每日扫描 → 超期客户生成**经理决策待办**（可选提前 N 天提醒经理"即将有 X 个公海客户超期待决策"）→ 经理处理（保留 / 删除关系）后闭环；**无人处理则一直挂起在待办**，不自动执行任何删除。

**★ 公海列表的展示与排序（2026-09-12 定）**：
- 部门公海列表**默认按"掉海时间倒序"**排列（最近掉进来的排最前）；可按公司名 / 行业 / 规模 / 客户等级等**已有字段**切换排序与筛选。
- 卡片上显示「**近 30 天尝试联系 N 次**」**仅供销售参考，不作为排序键**——**不按"被跟过热度"排序，也不为此在关系表上新增"跟进次数"冗余列**（`→§十六 N11`）。
- **理由**：公海里的关系是"跟不动才掉回来"的，**"被跟过很多次"其实是反面信号**；销售挑客户看的是行业 / 规模 / 等级（这些字段本就能排）。**不为一个主观排序功能付"冗余列 ＋ 每日刷新任务"的代价**。

**★ 公海条目「能打、但不在公海里做动作」（2026-09-12 定）**：
- 公海＝**可打的资料池**：销售动线 ＝ **看号（点开详情显全号，`→§4.3`）→ 打电话 → 有戏就「领取到私海」或走「录入」**；**领取后才进入推进态**（预约 / 跟单 / 阶段）。
- **公海内不提供任何动作**：不标记（未联系 / 未接 / 说两句）、不写跟单、不改阶段，**也绝不因此重置掉海倒计时**（`→§十六 N12`）。
- **"逐个联系"那种一屏一个客户的推进态，只做在预约管理与工作台时间轴**（那里是有 owner 的客户，不是公海）。
- **后续可能加"部门级公海标记"以防重复打——V1 不做**（`→§十六 N12`）。

**规则配置层级（下级覆盖上级）**：全局默认（老板）→ 产品级（老板）→ 部门级（部门经理）→ 部门×产品级（部门经理，优先级最高）。

**★ 规则变更的 7 天缓冲（2026-09-10 定）**：掉海天数一旦调整（如 30 天 → 15 天），**不即时生效**：
- 变更后 **7 天才生效**；生效时所有在途关系的倒计时**从生效日重新起算**（等于每个客户至少再给一整轮）。
- 提交变更时系统先提示「**本次将影响 X 个客户**」，经理可取消或改小幅度。
- **目的**：避免"今天改参数、明天几十个客户集体掉海"引发混乱，让经理**敢调参数**。没有这个缓冲，规则配置就成了没人敢碰的东西。

**例外**：客服/交付角色**不触发**自动掉公海（运维中客户不被误丢）；经理"删除关系"仅针对**无主公海客户**，交付/服务中的客户不在其列。

### 6.4 工单与商机双向流转

| | 售后工单 | 商机工单 |
|---|---|---|
| 来源 | 客户反馈 / 交付登记 / 系统触发 | 客户反馈升级 / 客服回访信号 / 销售挖掘 |
| 处理人 | 交付部门 | 销售 / 客服 |
| 优先级 | P0-P3 + SLA | — |

- **售后 → 商机**：客户提出销售相关诉求 → 升级为商机工单（保留历史，备注升级原因）。
- **商机 → 售后**：销售发现产品问题 → 退回售后。
- 工单带**工时估算**（点选 0.5h/1h/2h/半天）→ 用于算"回款少事多"客户的投入产出比。

### 7.2 联系人档案
- **录入去重**：手机号必填 → 校验是否已存在 → 已存在弹窗"该联系人已存在，是否加入现有公司档案？"
- **一人多号**：**主号**（唯一，撞单校验核心）+ **附加号**（座机/备用机/第二手机，可多个，仅作联系参考、**不参与撞单**）。主号唯一性 = **"同一时刻唯一"**：换号或删除后旧号自动释放，可被他人注册
- **旧号回收提示**：注册手机号时，若该号**曾属于其他联系人**（历史号），**提示"该号曾属于 XX"但不拦截**——手机号会被运营商回收，属正常现象；只提示、不阻断，帮销售避免认错人
- **变更审核**：姓名/邮箱/微信自主改；**手机号变更需经理审核**（通过后冻结 24h）；**删除联系人销售不可、经理可**
- **上锁 / 解锁**：联系方式**默认全可见**；**只有该联系人归属关系的 owner 能上锁**（锁**全局生效**：A 部门锁了 B 部门也看不到）；他人查看需**申请 → 落锁人审批 → 放行 24h**；**掉公海 / 离职 / 转岗 → 锁自动消失**；**总经理 / 管理员可强制解锁**（`→§4.3 二`）
- **跳槽换公司**：新公司存在→自动加入不新建档案；不存在→新建公司档案；**原就职记录保留**，原公司档案显示"对接人已离职"标记；历史跟单仍可查
- **合并联系人（经理权限 · 墓碑式）**：不同手机号但实为同一人时**无法自动识别**（姓名会重名、无更强身份锚），由公司合并后的"疑似重复联系人"提示或经理日常手动发起。**操作=墓碑合并**：loser 打 `merged_into`=winner（物理不删）、traits **并集**、子记录（`company_contact` / 跟单提及等）**零改动**；统一视图聚合胜出方+被并方，原始分支可追溯。限**经理权限**（合错丢身份数据须人工担责）。字段与索引见 `→数据架构 B3`

### 7.3 公司档案
- **录入去重与信用代码策略（前期以系统本身为主）**：
  - **前期（V1）· 公司名相似度查重（两段式，无代码也能拦）**：先**标准化**（去地域/行业/公司类型词，如"安徽/信息技术/有限公司/股份/集团"）取**核心词**，再分两档——① 核心词**完全相同 → 直接判"疑似同一家"**；② 核心词**编辑距离 ≤1 且长度相近 → 标"高度疑似"交人工确认**；其余不报。例：`安徽华夏中网信息技术有限公司` vs `华夏中网` 核心词同根→疑似同一家；vs `安徽鑫中网信息技术有限公司` 核心词不同(华≠鑫)→放走（真撞单靠信用代码）。信用代码**可空、后置补充**——老系统无代码的存量数据可正常迁入，补上之后才占唯一位、才起撞单作用
  - **量大时（触发条件）**：公司档案超过约 **N 千条**后，给 `company.full_name` 加 **MySQL 全文索引（ngram 中文分词）**，做"先粗筛候选 → 再精算相似度"两阶段查重。**规则不变、只为加速**；不引入 ES 等外部搜索组件（多一个组件多一份维护）。
    - **★ V1 落点（2026-09-12 定）**：核心词**落成一列** `company.name_core`（去地域/行业/公司类型词，服务端建档 / 改名时生成）**＋ 索引** `idx_name_core`——**两段式查重第一段走该列**（精确 / 前缀匹配收缩候选集），第二段才在候选集上算编辑距离。**不引入全文索引、不引入外部搜索组件**（见 `→数据架构 B1` / §10.1 / §10.2-4）；本节上面的"全文索引"留给量更大的下一阶段
  - **外部数据源（待评估 · V1 不做）**：对接企查查/天眼查类接口"输关键词 → 候选企业 → 自动带入信用代码/法人/注册资本/地址"。**能力可行且价值大**（顺带解决"成交后强制补组"的录入负担；2026-09-13 起注册资本 / 法定代表人已改为**非强制**可选字段，自动带入的价值更偏"填得更全"），但**涉付费与合规**，列为待评估、后置开发——见 §14.2 与决策 #26
  - **撞码合并流程（信用代码撞重 · 见决策 #27/#28）**：销售给公司 B 录入/补填 `credit_code`=X 时，系统先查"是否已有**未合并**公司占用 X"——命中 A 即弹「是否合并到 A」。确认后走**墓碑合并**（单事务）：① B 打 `merged_into=A.id`（物理不删，永远可审计）；② A 的 `aliases`(JSON) 收进 B 全称（曾用名/别名，供查重兜底与展示）；③ **B 的 `credit_code` 置 NULL**（释放唯一位，X 只留 A，`credit_code` UNIQUE 可空天然支持）；④ B 的公司档案标签（B2）**并集进 A**（打标人留痕全保留；决策链若 A/B 不同弹窗让人工选一个）；⑤ B 的任职记录（B5 `company_contact`）+ 业务关系（C1 `business_relation`）整体归 A——**子表（跟单/承诺/预约/阶段/合同回款）一律零改动，只动关系行本身**：若 B 的关系与 A **同部门同产品线**（撞 `uk_active_rel`），B 的关系打 `merged_into`=A 的 survivor 关系、置为非活跃分支（不占活跃位），其跟单仍挂原关系节点；若不同轴则 B 的关系 `company_id` 直接改指 A、成为 A 的一条正常活跃关系；⑥ 写 1 条 `operation_log` 合并审计（谁/何时/把谁并给谁/影响关系数与合同数）。**不自动合并联系人**：不同手机号同人无法自动识别，改走"合并联系人（经理权限）"操作（见 §7.2）。⑦ **合并后历史以树/分支呈现（git 式，见决策 #28；显示口径见 §7.5 · 决策 #30）**：每条跟单**仍挂原始关系节点、在合并点标注来源**，**永不交叉、可单独查阅任一分支**；**展示以"当前登录人"为分界——本人填的走主线，非本人填的（合并前其他销售 / 协同同事）走树杈**，默认只显示最近 1 个月。查"公司 A 全部跟单"= 主干关系子表 ∪ 所有 `merged_into`∈A关系集合 的子表。触发时机=B 填 X 撞重那一刻；已并存的历史脏数据（UNIQUE 没拦住的）合并时同样清空 B 的 X。字段定义与索引见 `→数据架构 B1` / `→数据架构 C1`
- **完善度三档校验**：
  - 必填：公司全称
  - 成交前必填：行业、地区、联系人关联（不达不能签约）
  - 成交后强制：信用代码、注册地址（不达不能签约）
  - **注册资本 / 法定代表人：公司档案的「可选扩展字段」，不做签约强制**（2026-09-13 定）——两者只作档案信息留存与**按规模筛选**（如"注册资金 > 100 万"），**不参与签约校验、不计入完善度**。**注册资本录入与展示一律以「万元」为单位**（库内按「元」精确存储，见 `→数据架构 B1`；展示规则见 `→前端 公司档案页`）。
- **★ 签约校验口径（2026-09-10 定，2026-09-11 补清单落地）**：完善度是**公司级**的（全公司共享），签约却发生在**某条业务线**上，两者不可混用。定死：
  - **签约校验按"本条业务线自己的必填清单"卡**，不是按公司完善度百分比（那个百分比只做展示与治理抓手，不卡签约）。
  - 公司级资料（信用代码、注册地址）**补全一次全公司共享**——先签的那条线负责补，后续其他业务线签约不再重复卡。
  - 例：财税线签约只看财税线要的东西；法务线已补全的信用代码，财税线直接受益，不需要再补一次。
- **★ 签约校验清单落地（`sign_checklist`，2026-09-11 P0-③ 定）**：
  - **清单从哪来**：新增 **`sign_checklist` 表**，挂在**产品线**（`product_line_id`）上，**管理员在「系统设置 → 产品线」配置**（与工作流阶段、字典同归管理员——产品线本身是公司级元数据、跨部门同产品线共用，归管理员不会冲突）。每条产品线一组"签约前必填项"，系统**给一套默认清单**（公司级 4 项 ＋ 关系级 2 项），管理员可增删改。**⚠ 默认清单的项数 / 字段 / 层级一律以 `→数据架构 E8`「默认清单（系统播种）」为准，本节不复述。**
  - **字段分三层**：① `scope=company`（公司级，补全一次共享：信用代码/注册地址/行业/地区）；② `scope=relation`（关系级，本条业务线自己：开发价值 `value_tier`、签约联系人 `contact_id` 关联）；③ `scope=ledger`（台账级，该线 `field_template` 登记的特定 key）。每项存 `label`（中文名，弹窗显示用，前端不硬编码）＋ `required`(可改) ＋ `status`(停用不删 T5)。
  - **校验流程**：进签合同表单**先预校验**——缺失项标红 + 顶部横幅"签约前还需补全 N 项"；**点提交硬卡 422**，返回缺失清单（每项带 scope + label + 去哪补锚点）。
  - **缺了怎么补（2026-09-11 定）**：① `scope=company` 的缺失项**弹窗内联补**（信用代码等几个框直接填最快，不跳出签合同页）；② `scope=relation` / `scope=ledger` 的缺失项给「去补全」按钮，**跳对应页**（关系详情标开发价值 / 台账编辑页补字段），补完回签合同页重校验。**公司级字段共享逻辑**：清单 `scope=company` 项只要 `company` 表有值就过，不论谁、哪条线补的。
  - **边界**：合同自身的字段（金额/付款方式/签约日期/服务起止）是**合同表单必填**，不进签约清单——签约校验清单只管"签约前客户资料齐不齐"。
  - 数据落点见 `→数据架构 E8 sign_checklist`；配置/查询接口见 `→接口 §5.15`；前端交互见 `→《销售CRM前端页面与交互文档》§六（页 16~18 / 页 25 系统设置）`。
- **业务线列表（自动汇总）**：已合作业务线（含签约日期/状态）｜正在跟进（含主责销售/上次跟进时间）｜已流失（含流失原因）
- **坐标**：建档时**人工调高德坐标拾取器点选**（不做地址自动解析，实战易错）；**非必填**，可后补。一家公司一个地址一个坐标
- **列表展示**：「地址是否维护」标记 = `address` 或坐标任一为空即显示"未维护"（**派生展示，不加字段**）
- 地图展示 / 附近客户 / 顺路推荐 → **不在 V1 需求范围**，坐标字段先存着，后续产品方案确定再说

### 7.5 跟进与工作流
- **写跟单 = 销售日常唯一必做动作**：就一句话 + 最多两个可选点选，**无任何为报表设的必填**
- **6 步阶段状态机**：见 §8
- **外出登记 = 纯行政考勤（2026-09-10 精简，砍掉一切多余字段）**：一句话目的——**让行政知道他不在公司、去干啥了**。
  - **出去时登记**：什么时间出去 ＋ 去干什么（一句话）＋ **可选**关联业务关系（**不关联也行**）。
  - **回来时点一下**：记录回来时间。**就这一个动作**。
  - **不做**：不填预计返回时间、不填交通方式、**不自动产生业务事件、不关联报销**（报销一期不做）。
  - 拜访的业务结果由销售**另外**决定要不要写事件记录——**行政不污染业务、业务不背行政包袱**。
- **跟单显示原则（默认近 1 个月 + 以主跟单人分界 + 历史轮次归组 · 决策 #30 / #56；分界基准 2026-09-10 修正，历史轮次 2026-09-11 P0-④⑤ 补）**：打开客户/公司，跟单记录**默认只显示最近 1 个月**（可手动切"全部"）；展示**先按"归属轮次"分组、轮次内再以该关系 owner 分界**：
  - **本轮（当前 owner 持有）**：owner 自己填的走**主线**、协同同事（collaborator）/ 合并前其他销售填的走**树杈**——两者视觉分开、不混（见 §10.2 / §13）。
  - **前主人轮次（曾被重新领取，round>1）**：按 `action_event.owner_snapshot` 把**上一任及更早 owner 的跟单归组**，每组标"前主人【姓名】的跟进记录"，与本轮明确分隔（虚线框 + 提示），让接手人一眼区分"现在是谁在跟、以前是谁跟的"（见 `→数据架构 D2`）。
  - **新 owner 本轮尚无跟单时**：明确横幅"本轮暂无跟单，以下是前主人【X】的跟进记录供参考"，**避免"主线空白、树杈一大堆"的别扭**（动线 8 断层，P0-⑤ 补）。
  - 每条跟单仍标"谁填的 + 跟的联系人"（都可点，见 §13）。
  - **★ 分界基准 = 该关系的 owner，不是"当前登录人"**（2026-09-10 七叔定）：**经理 / 老板打开时，看到的就是「主跟单人的视角」**——owner 的主线完整呈现、其他人走树杈。若按"当前登录人"分界，经理不是 owner，会看到"全是树杈、没有主线"，等于看不到重点。

### 7.6 合同与财务
- 合同：编号、业务关系、产品线、联系人、**签单人（业绩归属）**、金额、已收金额、付款方式、签约日期、服务起止、自动续约、续约提醒(30/60/90天)、附件、状态
- **★ 业绩归属：默认"谁签的算谁的"**（`signer_id` 100%）——离职也不变（§5.2）。
- **★ 业绩分配（2026-09-10 定，取代原"介绍费 10%"）**：如果一单是**别人协助 / 转介绍**促成的，可在**合同上设置业绩分配**——指定给几个人各占多少百分比（**合计 100%**）。**不设置就默认全归签单人**。
  - **刻意做极简**：**不做介绍费规则、不做费率配置、不做分成审批**——就在合同上填"给谁多少"。场景：张三签的单、李四帮着谈的 → 张三设「张三 70% / 李四 30%」，报表按分配算业绩。
  - 数据落点见 `→数据架构 E7 contract_split`。
- **附件与回款凭证**：统一走**文件资产表**（`→数据架构 B8 file_asset`）——合同附件、回款凭证都存那儿，**不在合同表里堆文件字段**。
- **签约触发**：合同创建 → 自动写入业务关系（阶段置"已合作"）；已收款=合同金额 → 状态转"执行中"；服务截止前 N 天 → 推送销售+客服+经理
- **★ 签约校验（2026-09-11 P0-③）**：`POST /contracts` 创建前按本条产品线 `sign_checklist` **预校验 + 提交硬卡**（详见 §7.3「签约校验清单落地」）——进表单先标红缺失项、提交时任一缺失返回 422 + 缺失清单（scope + label + 去哪补）；`scope=company` 缺失弹窗内联补、`scope=relation`/`scope=ledger` 缺失跳对应页补。合同自身字段（金额/付款方式/签约日期/服务起止）属合同表单必填，不在此校验范围内。
- **回款**：到账后按部门档位**自动重算客户等级**，任何人不可手填
- **★ 疑似重复合同：系统只"找"、不"判"（2026-09-12 定 · 检测不合并）**：先说清——**"同合同号录两遍"在库层已不可能**（`contract_no` 唯一约束拦死）。**真实风险是"逻辑重复"**：**同一笔真合同被录成两个不同编号**（重复录 / 先补录后又正式录 / 两个人各录一遍）→ 会让该销售**业绩、目标进度、客户等级（按回款额）静默翻倍**，而且**没人会主动对账**——这是**数据静默错误，不是"人该干的活"**。
  - **系统做的**：按 **同公司 ＋ 同签单人 ＋ 同金额 ＋ 签约日期相近（默认 ≤7 天）** 这条规则**采集可疑项**，在合同页给经理列一张「**疑似重复合同**」清单（每条并排显示两份合同号 / 金额 / 签单人 / 签约日期）。
  - **系统不做的**：**不自动合并、不自动拦截、不自动删任何一份**。因为**同公司同金额完全可能是两笔真合同**（续费 / 增购），系统替人判断就会**误杀真单**。**合并 / 保留由经理逐条点选决定**，判定动作留痕。
  - **依据信条**：**模式匹配＝软件活（系统干），判定是不是同一笔＝人的活（经理干）**——贴合"系统只是助手、不干需要人干的事"。

### 7.11 目标与进度（2026-09-10 七叔定）

**为什么要有这一块**：报表能回答"客户为什么不要我们"，但回答不了老板最焦虑的那句——"**这个月能不能完成？还差多少？**"。目标层就是为这一句而存在。

**三层月目标**：

| 层 | 谁定 | 谁能看 |
|---|---|---|
| 公司月目标 | 总经理 | 老板（总进度 ＋ 分部门进度） |
| 部门月目标 | 部门经理 | 经理 ＋ 老板 |
| 个人月目标 | 部门经理给每个人定 | 本人 ＋ 经理 ＋ 老板 |

**五条口径**：

1. **完成进度按回款额算**（七叔定）——目标金额与已完成金额都以回款为准。
2. **并列显示签约额**：回款有账期滞后（本月签的单可能下月才到账），销售会觉得"我签了单进度不动"。所以进度条主指标＝回款额，**旁边挂一行"签约额 XX 万"作参考**。
3. **★ 时间进度对比（本模块的核心价值）**：每个进度条下方显示"**时间已过 X%**"（按当月天数算），并算出**领先/落后几个点**。
   - 领先时间进度 ＝ 绿色，持平 ＝ 橙色，**落后 ＝ 红色**。
   - 这是"这个月能不能完成"的**早期信号**——不用等月底，15 号就能看出哪个部门、哪个人掉队了。
4. **目标可改但必须留痕**：月中允许调整（临时调低不可怕，偷偷调低才可怕）。看板标注"目标已调整过"，改前改后写入 operation_log。
5. **自上而下，不自下而上报数**：目标由上级定（老板 → 经理 → 个人），系统按人数/历史给一个**建议分解值**供参考，避免讨价还价。

**三个视角看到什么**：

- **老板**：公司总进度条（含时间进度对比）＋ 分部门列表（谁领先、谁落后）
- **经理**：本部门总进度条 ＋ 每个人列表
- **销售**：只看自己的月目标和进度（不显示他人排名之外的业绩数字，延续 §13.1"销售互查不暴露业绩"）

> **铁律**：目标由经理 / 老板填，**不增加销售任何填报负担**（符合 T3）。目标数据是系统里**唯一由管理层主动填**的东西——因为它回答的是管理问题，不是业务事实。

## 八、意向跟进体系

### 8.1 进度（阶段）= 客观事实：6 个推进阶段 ＋ 1 个流失终态

| 阶段 | 验证动作 | 系统建议信号 |
|---|---|---|
| 1 初步建联 | 首次有效电话/微信沟通 | 有通话/微信类事件 |
| 2 需求确认 | 聊清预算/需求/决策链 | 有需求类记录 |
| 3 面访产品讲解 | 当面演示过产品 | 有外出/见面类记录 |
| 4 异议与卡点 | 客户提出效果/价格疑虑 | 有异议类记录 |
| 5 逼单 | 明确报价、要求表态 | 手动进逼单（常与"周重点"呼应） |
| 6 已合作 | 签约回款 | 合同创建自动置位（终态） |
| **7 已流失** | **已合作客户没了**：被竞品撬走 / 到期未续费 / 服务不满 / 客户经营变故（＝ §11.2 ③ churn） | 流失复盘提交时自动置位（**终态**） |

**规则**：
- **动作驱动**：写跟单时右下角建议"当前动作 → 阶段 N"，销售确认或改；**建议态 + 一键确认，绝不自动改**（T4）
- **限频**：同客户距上次阶段变更 ≥3 天、或跨里程碑（进入面访/逼单）才建议——防一天 40 通电话弹 20 次
- **允许跳级与回退**（转介绍客户建联后直进逼单；异议没谈拢退回需求确认），**全部留痕**（谁、何时、从哪到哪）
- **★ 推进自认、零证据、经理不审核（2026-09-11 七叔定）**：阶段**往前推**＝销售一键确认即生效（T4「销售说了算」），**系统不要求附跟单/拜访证据，经理不审核推进**——防"推进"变审批、销售嫌烦绕过系统。**防糊弄靠"阶段 N 天未推进"这道闸门，不靠推进时卡证据。**
- **★ 回退单向知会经理（2026-09-11 七叔定）**：阶段**往后退（rollback）**时，触发经理 notification（`biz_type=stage_revert`，→数据架构 A9 / 接口 §4.14.3）——**经理只收到知会、不审核、不拦截**（流程照走），让经理知道"谁把哪单从哪退到哪"即可。
- **异议无解两条出路**：① 回落"长期跟"（等时机，不算死）② 判流失（必选死因）
- **★ 判死 / 流失的处置（2026-09-10 七叔定，取代原"已流失=不回流公海终态"）**：
  - **判死（loss）**："**这个销售没本事签，不等于客户签不了**"——写 loss 死因（点选必填）后，**关系掉回公海**，其他部门/销售可以去激活。**阶段保留**（停在谈到的那一步），接手的人能看到之前谈到哪、卡在哪。
  - **流失（churn）**：已合作客户被撬 / 到期不续费 / 服务不满 / 客户经营变故——**同样掉回公海**（客户可能还能抢回来，或还有新需求）。阶段置 7「已流失」标记**本轮生命周期结束**；本轮历史（跟单/合同/回款）**全部保留**。
  - **★「老客户」标识**：客户回到公海后，**公海卡片与公司抽屉显示「老客户」徽标**——判断依据＝**该公司的档案下存在历史合同**（**派生展示、不加字段**，符合 §九"系统能推导的不设标签"）。目的：让新领取的人一眼知道"这家我们以前做过"，不要当新客重新开发、也不要重复踩坑。
  - **重新领取后（新一轮开启 · P0-④⑤ 2026-09-11 补）**：阶段**从 1 重新开始**（新一轮），但**历史阶段日志（`relation_stage_log`）保留**——随时可查上一轮谈到哪、为什么结束；**轮次号 = 已掉海次数 + 1**（派生，不落表）。合同、回款、跟单全部挂原关系节点，不迁移，按 `action_event.owner_snapshot` 归组展示（见 `→数据架构 D2` / `→接口 /relations/:id/rounds`）。
  - **★ 历史轮次展示（P0-④ 2026-09-11 补）**：关系详情新增"历史轮次"区块——"第 N 轮跟进"徽标 + 上一轮卡片（归属人 / 起止日期 / 结束原因【判死橙·流失红·超时灰·手动】/ 结束阶段）；重新领取时弹横幅"⚠ 这是第 N 轮：上一轮由【张三】于 X 月 X 日判死（原因：…），上次谈到【阶段3 面访产品讲解】，避免重踩坑"。让接手人不重蹈覆辙（动线 7 断层，P0-④ 补）。
  - **★ 重新领取时未兑现承诺跟客户走（P0-④ 2026-09-11 补）**：领取瞬间，该关系所有**进行中（open）的承诺 `owner_id` 转给新 owner**（`me`/`verdict`/`them` 随关系走，与 §10.1 转交口径一致），避免旧销售继续收到"你答应客户 X"；新 owner 一打开即见"前主人留下 N 条未兑现承诺"清单。

### 8.2 紧迫（计划档）= 主观计划，5 档

| 档 | 语义 | 颜色 |
|---|---|---|
| **周重点** | 本周判生死——**标记即承诺本周推进或放弃** | 红（实心） |
| 月重点 | 本月能往前推进 | 橙 |
| 季度跟 | 季度内推进 | 蓝 |
| 长期跟 | 值得长期维护，时机未到 | 绿 |
| **灰度**（默认） | 暂未下结论 | 灰 |

- **纯手动，无自动降级**
- **★ 周重点闭环（2026-09-10 定）**——防止"标记即承诺"变成空话：
  - **不自动生成承诺**（周级名单生成日级承诺没锚点，会造出一堆空承诺）。保留：写事件时轻提醒"周重点勿忘" + **每周五自动清点"本周周重点都动过没有"**。
  - **挂满 2 周仍无任何推进 → 强制二选一**：① **推一把**（本周必须动）② **降级**（改成月重点/季度跟）③ **判死**（走 loss 流程）。**不接受"什么都不做"**——周重点不是收藏夹。
  - **经理看板新增「周重点僵尸榜」**：列出挂了 ≥2 周没动的客户及负责人。**这是经理抓"本周判生死"这个动作唯一的硬抓手**（§10.4 的动线防逃逸规则只管动线条目，管不到周重点）。
- **★ 灰度：不豁免掉海，且寿命规则只管"提醒"（2026-09-10 定）**：
  - 灰度 ＝ 紧迫档的**默认档**，意思是"**暂未下结论**"（不是客户意向强度，也不是跟进频率）。新客户进来默认灰度，想清楚了再往上改。
  - **灰度寿命规则（部门级）只负责提醒**：N 天未定性 → 提醒下结论。**不再"列为公海释放候选"**。
  - **掉海规则照常作用于灰度客户**——一直挂着不判断的，本来就该掉公海（符合 §2.2 信条"不存在吊着我们的客户"）。
  - 好处：两条规则**各管一段、不打架**。经理只需配「**一套掉海天数 + 一个灰度提醒天数**」，不必再配"释放天数"，也不会出现"灰度规则被掉海规则抢先命中、形同虚设"。

### 8.3 两轴分离：客户等级 ≠ 开发价值

| | 开发价值 | 客户等级 |
|---|---|---|
| 回答 | 这条线值不值得投 | **这条线**现在给我多少钱 |
| 值域 | 高/中/低/待定（默认空） | **S/A/B/C/D**（S=头部大额回款老钱罐） |
| 维护 | 销售手动（**非灰度必标**；灰度可留待定） | **系统自动**（回款到账事务内按部门档位算） |
| 配置 | — | 金额档位阈值 = 各部门经理自配 |

**★ 客户等级口径三要素（2026-09-10 七叔定，写死）**：

1. **范围 = 业务关系级（本部门 × 本产品线）**——等级回答的是"**这条线**给我挣多少钱"，不是"这家公司值多少钱"。同一客户在法务线是 S、在财税线是 B，**这是故意的**，与"业务关系是最小业务单元"（§5）一致。
2. **时间窗 = 滚动 12 个月回款额**（不是自然年累计、不是累计总额）。每日重算，**跨年不清零**。
3. **档位金额 = 各部门经理自配**（`dept_rule.level_tiers`），保持各业务线差异，不强制全公司统一。

> **报表口径提醒**：等级是关系级的，因此看板上"S 级客户 N"**默认统计关系数（条）**，不是公司数（家）。若需按公司去重，取该客户**全公司最高等级**。**报表必须标注"条"还是"家"**——否则同一个人今天看 30、明天看 18，数就不可信了。

> 两个反例约束：能长期跟的不一定最有实力；有实力的不一定适合本条线。**价值判断以该线契合度为主，公司实力只作背景参考。**
> 不再设"价值评估金额"字段——金额谁填都不准、没人敢信，只留一个软档位。

### 8.4 自动风险信号（系统执行，不落库、不要求人工维护）

| 信号 | 触发 | 摘除 |
|---|---|---|
| 流失信号 | 连续 7 天无跟进且阶段∈(1,2,3) | 恢复跟进即摘 |
| 回款风险 | 合同回款逾期 15 天 | 回款到账 |
| 交付风险 | 工单超时未处理（SLA 超标） | 工单关闭 |
| 对接人变动 | 联系人离职 / 在职状态变更 | 新对接人稳定 7 天 |

## 九、标签体系（三层，跟着判断主体走）

**核心原则**：
1. **判断属于谁，标签就挂谁身上**——公司背景挂公司、人的风格挂联系人、业务线判断挂业务关系。禁止把"人的特质"打在"公司"上误导全公司。
2. **系统能推导的不设标签**（T1/T3）。
3. **可统计的用字段、可浏览的用标签**。

| 层级 | 内容 | 值域 | 维护 |
|---|---|---|---|
| **公司档案** | 身份标签（多选） | 本地知名/上市公司/国资背景/连锁集团/集团型/其他（可自定义） | 建档人工勾一次，全公司共享 |
| 公司档案 | 制度标签（多选） | 需招投标/已用竞品/集团统一采购… | 建档勾选，可后补 |
| 公司档案 | 决策链（**单选**） | 老板直拍 / 多层评审 / 未知 | 建档选一次 |
| **联系人** | 谈判特质（**默认 ≤3，部门经理可配 1~5**） | 价格敏感/关系型/方案型/专业控/犹豫型/快决策/爱面子… | 手动，**跟着人走、换公司保留**；上限由部门规则配置（`dept_rule.contact_trait_max`），调小后存量保留、仅对新写入/编辑生效 |
| 联系人 | 决策权角色 | 决策人/影响人/执行人 | 已有字段 |
| 联系人 | 个人标签 | 自由 tag（爱喝茶/老板亲戚…） | 与谈判特质分栏并存 |
| **业务关系** | 紧迫档 | 周重点/月重点/季度跟/长期跟/灰度 | 纯手动 |
| 业务关系 | 开发价值 | 高/中/低/待定 | **手动；但"非灰度的关系必须标"**（见下） |
| 业务关系 | 风险标签（多选） | 流失信号/回款风险/竞品渗透/换对接人/组织变动 | **系统自动为主 + 人工可补** |

**★ 开发价值必标规则（2026-09-10 七叔定）**：**但凡不是"灰度"的关系，都必须标记开发价值。**

- **理由**：给客户定了紧迫档（周重点 / 月重点 / 季度跟 / 长期跟），就等于承认"**这是我的意向客户**"——那你就必须回答"**这条线值不值得投**"。否则经理打开客户盘子一看全是"待定"，这个视图等于白做。
- **灰度客户不强制**（还没下结论，价值自然也没结论）。
- **摩擦控制（不违反 T2）**：① 系统按公司档案（规模 / 行业 / 决策链）先给一个**建议档位**，销售**一键确认或改一下**；② **把紧迫档从"灰度"改成其他档时，顺手必选价值档**——一个点选、两秒完成，**服务端校验（422）**，不能空着离开灰度。
- 经理可代标补录。

**留痕**：所有打标/改动留痕（谁、何时）。公司/联系人级标签全部门可见；业务关系级标签仅数据范围内可见。

**谈判特质上限（部门可配）**：默认 ≤3，部门经理可在部门规则中调整为 **1~5**（`dept_rule.contact_trait_max`，写入留痕）。设计意图=防标签通胀（不限则人人全勾、失去"一眼分辨"价值），故给一线小幅弹性而非完全放开。**经理调小上限时，已有超限特质保留不动，仅对之后的新写入/编辑生效**（不追溯裁剪、不丢历史）。个人自由标签（tags）不受此限，二者分栏并存。

- **★ 上限校验口径（2026-09-11 定，防误拦）**：`contact_trait_max` 的 **422 只拦「新增」**——若某人特质数量已超过调小后的新上限（存量），**编辑（数量不增加）一律放行**，只在他**再加新特质**时才拦（否则经理一调小上限，存量客户的标签就再也编辑不了）。

## 十、行动引擎（助理心脏）

### 10.1 承诺（心脏）

| 类型 | 语义 | 到点提醒语气 |
|---|---|---|
| **me 我答应客户** | 我发资料 / 我报价… | "你答应 X 的，办了吗？"——**催自己** |
| **them 客户答应我** | 他给答复 / 他确认… | "客户答应 X，去问一句"——**催客户** |
| **verdict 我定的判定点** | 灰度/判断题专用 | "跟还是放，给个结论" |

**规则**：
- 到期 → 进今日动线；逾期 → 次日置顶标红
- **★ 承诺怎么收尾：只有三条路，没有第四条（2026-09-15 定）**——一条承诺挂着就**不许"放着不管"**，只有三种收法：
  - **兑现 `done`**：事办了（写兑现时间 / 兑现人）；
  - **取消 `cancelled`**：**录错了 / 这事不成立了** —— 纠正误录，**不填原因**；
  - **豁免 `waived`**：**确有其事、但做不成**（客户变卦、特殊原因做不了…）—— **必须填原因**（存 `waive_reason`）。
  - **为什么必须分成两个**：**取消＝这条记录本身错了；豁免＝记录没错、但结果没成**——混成一个动作，经理事后就分不清"这条线到底还有没有戏"。而**豁免的原因必填**是同一道闸：否则"点一下就当处理完了"，逾期抽屉会变成藏事的地方（见下条 them 类出口）。
- 兑现检测：写事件命中"发过报价/资料" → 建议关联销项对应承诺
- **★ them 类承诺的出口（2026-09-10 定）**：客户答应我、但一直不兑现——**催问 3 次无果 → 系统建议"转成卡点"或"建议判死"**。否则这类承诺只有"豁免（要填原因）"和"无限拖延"两条路，会在逾期抽屉里越堆越多，最后没人看。
- **录入摩擦（T2）**：写事件时"有承诺吗？"默认无；有 → **三快选**（我发资料 / 他给答复 / 约见面）+ 可选时间（默认明天），**10 秒完成**，不做独立录入页

### 10.2 事件流（跟单 / 客情 / 求助 / 系统）

- **动作类型**：电话 / 微信 / 拜访 / 现场 / 邮件 / **请客** / **送礼** / **节点问候** / **@求助** / 纯备注 / 系统
- 内容 = **一句话结果**（销售说的人话）+ 最多两个可选点选（进展、卡点）
- **★ 录入分两类（2026-09-10 七叔定）**——白话：**有效沟通写字，没接通点一下。都不漏，都不累**：
  - **有效沟通（接通了、聊了）→ 必须写跟单**：一句话结果 + 可选点选。
  - **无效沟通 → 点一下「快速标记」即可，不强制写一个字**。**三选一（2026-09-10 定）**：**未联系 / 未接电话 / 说两句挂了**。
    - **快速标记必须落库**——否则"这个客户打过多少次"统计失真。**支持批量**：勾选多个客户 → 一次性标记。电销一天几十通，不批量就没人好好写。
    - **★ 关键：快速标记不算"有效跟进"，不重置掉海倒计时**（见 §6.3）。否则销售每天对 100 个客户点一下，所有客户就永不掉海了，倒计时直接被刷爆。
    - 卡片上显示「**最近 30 天尝试联系 N 次**」——让经理看得到销售确实在努力（不是没干活），但客户该掉还是掉。
- **完成预约/拜访 → 服务端强制生成一条事件**（422 兜底，T2 唯一例外之外的强制项）
- 卡点：可选点选（价格/效果/信任/见不到人/时机/竞品/内部/其他）；**卡住时选主卡点 + 一句话补充**
- 可见性继承业务关系权限（本人全文 / 协同可读写 / 他人私海不可见 / 公海仅"近30天 N 次"）
- 跟单卡片统一显示**谁填的 + 跟进的联系人**（都可点，见 §13）；**列表默认近 1 个月、以主跟单人（owner）分界——owner 主线 / 他人树杈，不混（见 §7.5 · 决策 #30）**
- **★ 多联系人（2026-09-11 七叔定，`→§6.3`）**：一条关系可**同时**跟多个联系人（老板 / 招商 / 财务…）——**每人每次写一条事件，都挂在同一个 `relation_id` 下**，`contact_id` = 本次对着谁。**见谁都算有效跟进**，不按角色加权，也不按人拆成多条关系。**防糊弄靠「阶段 N 天没推进」，不靠"见了谁"——经理盯的是工作流的变化**（详见 §6.3「多联系人跟单口径」）。

### 10.3 节奏规则（加提醒 = 加行，不写代码）

| 节奏 | 触发 | 强度 |
|---|---|---|
| 新客趁热 | 新关系 / 新联系人 48h 内无事件 | 提醒（**联系人口径见 §6.3：仅 `decision_role`∈{决策人,影响人} 的新联系人触发，执行人不催**） |
| S 级客情 | 已合作 S 级客户距上次客情 > 45 天 | **软提醒**（不催） |
| 灰度定性 | 灰度超 N 天未下结论 | 提醒 |
| 周重点清点 | 每周五检查本周周重点是否都动过 | 提醒 |
| 掉海预警 | 距掉海 ≤3 天 | **硬提醒**（永远置顶） |
| 待关联补全 | 新联系人 **7 天**未关联公司 | 提醒（催补全公司） |

> 统一收进节奏规则表，经理可配。**软提醒可以划掉，硬提醒不行。**

### 10.4 今日动线（工作台首页）

- **每日清晨自动组装**：承诺今日到期/逾期 → 预约今日 → 节奏命中 → 掉海倒计时 → 排序，逾期置顶标红
- **降噪收敛（防红墙）**：
  - 逾期 ≤3 天 → 逐条置顶红
  - 逾期 >3 天 → 自动收进「**逾期抽屉**」，首页只留一条汇总提示（不铺满红墙）
  - **掉海/灰度判定/今日预约等硬约束永远置顶**
  - 同一客户同一原因被"忽略"后，7 天内不再重复推
  - **★ 同类提醒自动合并（2026-09-10 定）**：**相同类型、相同原因的提醒合并成一条**——例如"有 10 个客户的判死教训待补写"显示为一条汇总，**点开详情能看到具体是哪些客户、什么事**。避免"一天判死 10 单、第二天来 10 条提醒"这种红墙。
  - **★ 预约过期 ＝ 只提醒、不强制（2026-09-12 定）**：预约到期没处理，**只走"逾期 ≤3 天置顶标红 / >3 天收进逾期抽屉"这一套提醒**；系统**不自动判死、不自动降级、不自动关闭关系、不替销售做任何后果动作**。**理由**：经理看到过期预约会**自己分析、自己干预**——**系统不要干需要人干的活**（同 §4.3 联系方式解锁不设限额）。
- **处理反馈**：done → 引导写事件并自动销承诺；snoozed → 推明天；ignored → 留痕（防骚扰 + 规则学习）
- **防逃逸规则（防止用按钮逃避跟进）**：
  - **snoozed 上限**：同一条动线最多 snooze **3 次**；第 4 次起不再提供"推明天"，强制二选一——`done`（并写跟单事件）或 `ignored`（须填原因），杜绝"无限推迟、客户悄悄掉海"
  - **ignored 必须填原因 + 经理可见**：`ignored` 不是消失，是"我故意不跟，因为___"；原因留痕，经理看板可看"某人 ignored 占比"作为管理抓手
  - **长期停滞自动降权**：某关系持续被 snooze/ignored，系统标"停滞"并提醒经理介入

> 设计底线：**销售每天真正能消化的提醒是有上限的**。宁可少推，不可推错；宁可折叠，不可铺满。

## 十一、竞品与出口复盘

### 11.1 竞品：三层，不建"档案库"

| 层 | 内容 | 谁维护 |
|---|---|---|
| **① 每次跟单顺手标** | "这单有竞品吗？"→ 无（默认，直接跳过）/ 在用某家 / 比价中 + 一句话情况 | 销售，**10 秒** |
| **② 竞品名册** | 名称 + 产品线 + 一句话定位（**不是价格表/功能对照表**） | **经理维护，销售只读引用** |
| **③ 打赢才记** | 赢单时顺手留"对谁、怎么赢的" | 销售（低频、有成就感） |

- **UI 口径**：竞品标记**折叠成一行**"这单有竞品吗？"，默认"无"直接跳过，有才展开——竞品对多数单子是低频事实，不许变成高频负担
- **竞品三分关系 = 系统推导，销售不标**：未合作×在用竞品=**策反**｜未合作×比价/无竞品=**竞争**｜已合作=**防守**
- **不点名原则**：销售大多只知道"有竞品、客户跟别家合作了"，具体哪家看客户愿不愿意透露——**能说才填，不说不强求**，统计按"有竞品（未点名）"归并
- **为什么不做"竞品档案库"**：价格政策三个月一变，让销售维护 = 录入者≠受益者，必腐，半年后一堆过期资料比没有更害人

### 11.2 出口复盘：经验继承，不是复盘作业

**原则：复盘挂在"本来就要点的按钮"后面，不新增复盘作业。** 错过时机不可补——绝不事后单独填表。

#### ① win 新签复盘（经理主导，销售零负担）
- **触发**：转已合作（阶段→6）时**系统自动建档**，不是销售自愿建
- 销售可在同一弹窗顺手填一句"赢在哪"（**可填可不填，10 秒可跳过**）
- **经理是唯一收录人 + 修订人**：无论销售填没填，经理都能直接修订/补写；觉得有沉淀价值 → 收录进**赢单弹药库**；觉得是运气单 → 不收录（可注明原因）
- **防经理积压**：S/A 级签约 → 经理必须逐条处理；B/C/D 级 → 可批量处理，**超 30 天未处理自动不收录**
- **弹药库可见范围**：**默认本部门可见**；总经理可在设置中改为全公司可见
- 未收录的（待处理/已丢弃）仅本人 + 直属经理可见——**销售敢写真话，不怕丢脸**

#### ② loss 判死复盘（死因点选必填，文字可缓）
- **死因点选必填**（服务端 422）：没真需求 / 输给竞品 / 我们没跟住 / 预算问题 / 决策链断了 / 说不清
- **文字当天不强制**：次日动线提醒补写——输单当天情绪最差，逼出来的全是甩锅
- 为什么死因强制、文字不强制：死因是公司要的**结构化底线**（客户为什么不要我们），文字是个人反思（逼不出来）；判死一单一生只判一次，30 秒可接受

#### ③ churn 已合作流失复盘（统一出口，原因=标签）
- **建模口径**：被撬、到期未续费、服务不满、我们疏忽、客户经营变故……**是同一类——"已合作客户流失"，只是原因标签不同**。不分类型、不分流程
- 销售初填：选一个主因标签（可附备注）
- **高价值流失（S/A 级）经理必须亲自回访客户听真话**：防"甩锅式死因"（被撬常写"竞品低价"、到期未续常被写成"客户没预算"——**真话在客户嘴里**），也是挽留机会
- B/C/D 级：销售填原因标签即闭环；经理有异议可抽访

#### 三个消费视图
- **赢单弹药库**（本部门/gm 可全公司）→ 供同事搜"谁打过这仗"
- **死因看板** → 客户为什么不要我们
- **防守清单** → 哪个竞品在反挖我们的客户

全部来自销售"本来就要点"的出口动作，**零额外报表填报**。

## 十二、撞单与竞争 SOP

| # | 场景 | 处理 |
|---|---|---|
| 1 | 同部门同产品线重复激活 | 后到者申请转交 / 协同 |
| 2 | 同部门不同产品线 | 并行，各自独立 |
| 3 | **跨部门同产品线** | **竞争并行**：都能跟、都能见客户，但**跟单互不可见**（防策略泄露）；**两条关系各签各的、互不干扰**——一方签约只在另一方关系上**提示不拦截** |
| 4 | 跨部门不同产品线 | 完全独立 |
| 5 | 主责人离职/转岗 | 走转交，关系更新 |
| 6 | 签单人离职 | **签单人记录不可变更，业绩仍归原签单人**（离职只不进「人均」分母，`→§5.2`） |
| 7 | 客户主动要求换销售 | 主责人确认 / 部门经理重分 |
| 8 | 客户签单到多级公司（母子） | 按签约公司归档，不拆分 |

### 12.1 撞库 4 分支（录入 / 激活关系时查重）

> 触发点：① 录入联系人时按**手机号**查重；② 第 2 步「选公司」按**公司名 / 信用代码**查重。命中即弹窗，按分支给文案 + 按钮 + 落点（前端 `/entry/new` 步骤条，见前端 §六-7）。

| 分支 | 触发 | 弹窗文案 | 按钮（主→次） | 落点 |
|---|---|---|---|---|
| **1 公海可直领** | 命中公海里**无主**的关系 | 「这个客户已在**公司公海**（X 进入，原因 Y），你可以直接领到自己名下」 | **领取到我的私海** · 查看客户 · 取消 | `claim` → 继承全文跟单 → 关系详情 |
| **2 本部门已激活** | 同部门同产品线已有**活跃**关系 | 「这条线**已有归属：张三**（激活于 X），同部门同产品线只能有一条关系」 | 联系张三（悬浮卡）· **申请转交给我** · 申请协同 · 取消 | 转交 / 协同走审批（§7.9） |
| **3 跨部门可并行** | 别的部门有、本部门没有 | 「**法务部**已在跟进（X）。你们是**竞争并行**——可建自己部门的关系，各跟各的，一方签约**不阻断**另一方」 | **仍然激活（建我部门的关系）** · 查看对方概要 · 取消 | `POST /relations` → 挂「已被 X 部门跟进」徽标 |
| **4 挂现有公司** | 公司名 / 信用代码命中，但本产品线无关系 | 「已有这家公司：**全称**（信用代码…）｜别名…」＋相似候选列表 | **挂在现有公司** · **确认新建公司**（强行） · 取消 | 选现有→建关系；新建→建档（后续撞码可合并，§7.3） |

- **分支 2 细节**：「申请转交」**次推**（先给「联系张三」悬浮卡促进直接沟通），且**必须走审批**（防抢单）。
- **分支 3 细节**：只显示对方**部门名 + 激活 / 签约日期**，**不露任何跟单内容与进展**（严格按 §13 / §4.3「跟单互不可见」，防策略泄露）。
- **分支 4 细节**：高度疑似由人工选；**疑似同一家默认选现有，仍须保留「强行新建」出口**（同名不同司真实存在）；**强行新建留痕**（`operation_log`）+ 经理看板显示「疑似重复新建」，**不阻断**销售。

- **协同 = 共同跟进**：后到者可申请协同，审批通过成为协同人（可共同写跟单、看全文、看全号）
- **业绩分配（取代介绍费）**：**不做介绍费 / 提成分账规则**；需要时在**合同上填"给谁多少"**（合同业绩分配，**默认谁签的算谁的**，合计 100%，不分类型、不配费率、不走审批，`→§7.6`）。

## 十五、业务规则速查（★ 索引·非规范：以正文 §4~§14 为准）

> **⚠ 本表是"索引"，不是"规范"。** 46 条只是压缩摘要，**每条规则的完整条件与例外一律以正文（§4~§14）为准**；本表与正文不一致时，**以正文为准**（并去《废止口径登记表》登记"本表待修正"）。用途＝写测试时逐条打钩，**不得作为唯一实现依据**。
> **★ 本表中含"不…"的表述，仅为打钩时的上下文**——**负面约束的权威落点＝§十六《否决与后置清单》**（该表才是完整清单）。两表若有出入，**以后者为准**。

1. 同 公司×部门×产品线 仅一条活跃私海关系（撞单/激活竞态由唯一约束兜底）
2. 手机号唯一、信用代码唯一；撞码引导使用已有档案
3. 完成预约 → 服务端强制生成一条事件（422）；外出登记**不自动产生事件**（纯行政）
4. 承诺：me 催自己 / them 催客户 / verdict 给结论；豁免必填原因
5. 周重点 = 标记即承诺本周动作；**不自动生成承诺**，周五自动清点
6. 阶段推进 = 建议态 + 一键确认，限频（≥3 天或跨里程碑）；跳退留痕
7. 客户等级 = **滚动 12 个月回款额**，按**本部门×本产品线（关系级）**自动算、部门自配档位，任何人不可手填；含 S 档；**看板统计默认按"条"，按"家"时取全公司最高等级，必须标注**（§8.3）
8. 开发价值与客户等级**两轴独立**（§8.3）；**非灰度的关系必标**（系统给建议值、一键确认，服务端 422），**灰度方可留待定**——"愿标才标"只适用于灰度
9. 掉海/灰度/协同到期/节奏 = 规则表统一调度（T1，加行不加列）
10. 协同 = 共同跟进（可共同写+全号可见），正式协同走审批；**@求助 = 即时授予的临时协同，权限一致**（默认 7 天自动收回、owner 可撤销、留痕、免审批），**但限同部门**——跨部门必须走正式协同审批（防策略泄露）；想长期必须走正式协同
11. 联系方式**默认全可见 ＋ 可上锁**（完整口径见第 46 条与 §4.3 二）；**手机号变更走审批、通过后冻结 24h 生效**（§4.3）
12. 金额库内明文全量，脱敏在应用层；跨业务线金额完全脱敏
13. 台账自定义字段：先登记模板，key/类型不可变，停用不删，未登记拒收
14. 不存在吊着我们的客户 → 卡点只认"见不到人 / 犹豫效价"两类核心
15. 竞品标记在**跟单事件**里顺手做（默认折叠一行）；关系上的竞品态势只是最近一次快照；三分为推导只读，不设标签
16. 竞品名册只存"名称+产品线+一句话定位"，经理维护；"输给竞品/被撬"均**不点名**
17. 出口复盘：win 自动建档、经理决定收录；loss 死因点选必填、文字次日缓写；churn = 流失统一出口，S/A 级经理必回访
18. 完成预约必留事件、判死必选死因 —— 两处"出口动作的强制性"，但死因只点选不作文；**跟单录入分两类：有效沟通写字（必写一句话）、没接通点一下快速标记（不写字但必须落库，支持批量）**（§10.2）
19. 主责 = 唯一 owner（谁在岗谁维护）；签单人只锁业绩；换人走审批、病假授带期限协同、离职批量转交
20. 坐标 = 两个字段，一家公司一个坐标；人工拾取、非必填、GCJ-02；「地址是否维护」派生展示，不加字段
21. **任何页面出现的公司名/人名都可点，点开即可查看，不需要去对应模块搜索**（§13.1）
22. 公海 = **关系粒度**：**公司档案本身即公司公海（全员可见）；部门公海里的一条 = 一条业务关系**。掉公海 = 关系失去 owner，**dept_id 恒定不变**；别的部门想要 = **自己激活本部门的关系**（唯一约束含部门，互不冲突），**不存在"跨部门捡公海"这个动作**。公海停留超期 → 经理决策待办（保留 / 删除关系 = 逻辑删除留痕），**无任何自动删除/自动流转**（§6.3）
23. **跟单分界基准 = 该关系的主跟单人（owner），不是"当前登录人"**：经理/老板打开看到的就是"主跟单人的视角"——owner 主线、他人树杈（§7.5）
24. **停滞判定 = N 天内阶段未向前推进一格**（不看跟单 outcome，避免逼销售每条必选、违反 T2）（§6.3）
25. **签约校验按"本条业务线的必填清单"卡**，不是按公司完善度百分比（百分比只展示不卡签约）；公司级资料补全一次全公司共享（§7.3）
26. **判死 / 流失都回公海**（2026-09-10 修正）：**判死**＝这个销售没本事签、客户还能被别人激活 → 写死因后关系**掉回公海**、**阶段保留**；**流失**＝已合作客户被撬/到期不续费/服务不满/客户经营变故 → 也**掉回公海**、阶段置 7 标记本轮结束（原因走标签）。回到公海后**公海卡片与公司抽屉显示「老客户」徽标**（**派生**：该公司存在历史合同，不加字段）；重新领取后阶段从 1 重新开始，`relation_stage_log` 保留可查上一轮（§8.1 / §11.2）
27. **目标三层（公司/部门/个人月目标），完成进度按回款额算**，并列显示签约额；**每个进度条显示"时间已过 X%"并算出领先/落后几个点**（领先绿/落后红）；目标可改但留痕，自上而下不定自下而上（§7.11）
28. **快速标记三选一**：未联系 / 未接电话 / 说两句挂了——落库、可批量，**但不重置掉海倒计时**（只有有效沟通才算有效跟进）（§6.3 / §10.2）
29. **周重点挂满 2 周无推进 → 强制二选一**（推一把 / 降级 / 判死），经理看板有「周重点僵尸榜」（§8.2）
30. **价值档的补标 / 代标**：经理可代标；把紧迫档从灰度改成其他档时**必须同时选价值档**（服务端 422）；"非灰度必标"见第 8 条（§9）
31. **灰度不豁免掉海**；灰度寿命规则**只管提醒下结论**，不再"列为释放候选"（§8.2）
32. **规则变更（掉海天数）有 7 天缓冲**：7 天后生效、生效时倒计时重新起算；提交时提示"将影响 X 个客户"（§6.3）
33. **跨部门同产品线的两条关系各签各的、互不干扰**（取代"谁先签约谁得"）——同一客户可能确有两次需求；一方签约后在另一方关系上**提示不拦截**（§5.1 / §12）
34. **them 类承诺催问 3 次无果 → 系统建议转卡点或判死**（§10.1）；**转交时未兑现承诺跟客户走**（`me`/`verdict` 转新 owner，`them` 随关系）（§5.2）
35. **合同业绩：默认谁签的算谁的**；需要时在**合同上设置业绩分配**（给谁多少，合计 100%），**不配费率、不走审批**；**介绍费不做**（§7.6 / §14.2）
36. **附件与回款凭证统一走文件资产表**，不在业务表堆文件字段（§7.6）
37. **审批人默认 = 直属上级**；跨部门转交双签；上级缺失上溯（§7.9）
38. **离职后：历史业绩照常显示，"人均"只按当月在职人数算分母**（§5.2）
39. **"跨业务线"判定按部门**（不按产品线）（§4.3）
40. **相同类型/原因的提醒自动合并成一条**，点详情看是哪些客户什么事（§10.4）；**外出登记只留三样**：出去时间、去干什么、回来点一下（§7.5）
41. **联系方式解锁不设次数/频率上限**（系统只留痕，不做限额）（§4.3）
