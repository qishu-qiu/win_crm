# 销售 CRM 系统开发需求文档（V2.1）

> **文档定位**：可直接进入开发评审的完整需求文档
> **业务模式**：电销/陌拜获取资料 → 跟进转化意向 → 成交签约 → 工单转交付 → 销售/客服回访维护
> **核心模型**：**3 层映射架构**（公司公海 → 部门公海 → 业务关系）
> **目标**：用一个统一 CRM 支持多业务线、多部门、多角色协同，把"人和人的对接"做成可落地的资产
> **V2.1 修订（2026-09-08）**：跟单可见性分档 + 协同升级为共同跟进（新增 `collaborator`）+ 手机号脱敏可申请解锁。详见 §2.2、§3.3/3.3.2、§5.3、§8。版本来源：需求总纲（V2.0 → V2.1），下游《数据库 V1.2 / 接口 V1.4 / 前端 V2.6》同批对齐。

## 一、业务全景与术语定义

### 1.1 客户生命周期五阶段

| 阶段 | 定义 | 数据归属 | 主要操作人 |
|---|---|---|---|
| **联系人** | 只有手机号/微信，未明确公司 | 联系人档案 | 销售、电销专员 |
| **资料（公司档案）** | 已明确公司，进入跟进流程 | 公司公海 + 各部门映射 | 销售 |
| **意向** | 已激活业务线，正在跟进 | 业务关系表 | 销售 |
| **客户（成交）** | 已签约合作中 | 业务关系表 + 台账 | 销售/客服/交付 |
| **客户（流失）** | 跟单失败或合同到期未续 | 业务关系表（归档） | 销售（仅查看） |

### 1.2 3 层映射模型（核心架构）

```
┌─────────────────────────────────────────────────────────────┐
│  第 1 层：公司公海（主实体池）                              │
│                                                              │
│  ┌──────────────────────────────────────────┐               │
│  │  企业档案（唯一，1 家公司 = 1 个档案）    │               │
│  │  ──────────────────────────────          │               │
│  │  公司名（必填、全称）                     │               │
│  │  行业、地区、规模等基础信息               │               │
│  │  社会统一代码（成交后必填）               │               │
│  └──────────────────────────────────────────┘               │
│           ↑       ↑        ↑                                 │
│           │       │        │                                 │
│  ┌────────┴───┐  ┌┴────────┴──┐  ┌──────────┐               │
│  │部门公海(A) │  │部门公海(B) │  │部门公海(N) │              │
│  │"A 部门     │  │"B 部门     │  │"N 部门     │              │
│  │ 判断有潜力 │  │ 判断有潜力 │  │ 判断有潜力 │              │
│  │ 的客户"   │  │ 的客户"   │  │ 的客户"   │              │
│  └──────┬────┘  └──────┬─────┘  └──────┬───┘               │
│         │             │              │                     │
│  第 2 层：员工私海                                       │
│         │             │              │                     │
│  ┌──────┴────────┐  ┌─┴───────────┐ ┌─┴──────────┐        │
│  │员工 a-客户A1  │  │员工b-客户B1 │ │员工n-客户N1 │        │
│  │员工 a-客户A2  │  │员工b-客户B2 │ │员工n-客户N2 │        │
│  └───────────────┘  └─────────────┘ └────────────┘        │
│                                                              │
│  第 3 层：业务关系（企业 × 部门 × 产品线 × 对接人 × 销售） │
│                                                              │
│  ┌───────────────────────────────────────────────────┐     │
│  │"唯一业务关系"每个企业 × 部门 × 产品线 的实际跟进关系 │     │
│  │ ──────────────────────────────────                 │     │
│  │ 主对接销售（1 个）· 维护人（客情归属）· 共同跟进（多人，协同） │     │
│  │ 跟单记录 / 工单 / 合同 / 续约                      │     │
│  └───────────────────────────────────────────────────┘     │
└─────────────────────────────────────────────────────────────┘
```

**核心设计原则**：
- **客户主档案唯一** —— 1 家公司 = 1 个档案（社会统一代码或全称匹配）
- **部门公海 ≠ 公司公海子集** —— 部门公海是部门**主动认领**的有价值客户，与公司公海是映射关系
- **业务关系是最小单元** —— 一切跟单/合同/续约围绕"业务关系"展开

### 1.3 关键术语

| 术语 | 定义 |
|---|---|
| **公司公海** | 主实体池，全量企业档案，所有部门共享 |
| **部门公海** | 部门认领的有价值客户（公司档案 × 部门 映射） |
| **员工私海** | 员工在部门公海里认领的客户（公司档案 × 员工 映射） |
| **业务关系** | 企业 × 部门 × 产品线 × 对接人 × 销售，CRM 的最小业务单元 |
| **签单人** | 完成签约的销售（业绩归属人） |
| **维护人** | 后续跟进/回访/续约的销售（客情归属人，可与签单人不同） |
| **共同跟进人（协同人）** | 经协同审批加入、可共同写跟单的销售（V2.1）；区别于"维护人"，维护人管客情、协同人专项共同跟进，二者可见范围相同（全文）但定位不同 |
| **对接人** | 客户方联系人，独立建档，以手机号为唯一索引 |
| **联系人档案** | 仅记录联系人信息（成交前），企业档案待补全 |
| **公司档案** | 完整的企业档案（成交后强制补全） |
| **售后工单** | 需交付部门处理的售后服务请求 |
| **商机工单** | 销售对接的客户反馈/二次销售机会 |

## 二、组织架构与权限体系

### 2.1 角色与关系

```
总经理 ──┬── 经理 A ──┬── 销售 1
         │            ├── 销售 2
         │            ├── 客服 1（部门启用时）
         │            └── 交付 1
         ├── 经理 B ──┬── 销售 3
         │            └── 销售 4
         └── 经理 C ──┬── 销售 5 (跨部门)
                      └── 销售 6 (跨部门)
```

**关键规则**：
1. **部门 ↔ 产品线** 是**多对多**
2. **总经理 ↔ 经理** 是**多对多**
3. **成员角色**：`销售` / `交付` / `客服` / `行政`
4. **客服角色** 按部门配置是否启用

### 2.2 角色权限矩阵（V2 调整后）

| 数据/操作 | 销售 | 客服 | 交付 | 部门经理 | 总经理 | 行政 |
|---|---|---|---|---|---|---|
| 公司公海（简表） | ✅ | ✅ | ✅ | ✅ | ✅ | ✅ |
| 公司公海（详情） | ✅ 简版 | ✅ 简版 | ✅ 简版 | ✅ 全 | ✅ 全 | ❌ |
| 部门公海（自己部门） | ✅ | ✅ | ✅ | ✅ | ✅ | ❌ |
| 部门公海（其他部门） | ❌ | ❌ | ❌ | ❌ | ✅ | ❌ |
| 员工私海（自己） | ✅ | ✅ | ✅ | ✅ | ✅ | ❌ |
| 员工私海（同部门） | ❌ | ❌ | ❌ | ✅ | ✅ | ❌ |
| 员工私海（跨部门） | ❌ | ❌ | ❌ | ❌ | ✅ | ❌ |
| 客户台账（合作中） | ✅ 自己的 | ✅ 自己负责 | ✅ 自己负责 | ✅ 部门明细 | ✅ 全 | ✅ 只读 |
| 合同/财务 | ✅ 自己客户 | 🚫 脱敏 | 🚫 脱敏 | ✅ 部门汇总 | ✅ 全 | ✅ 只读 |
| 工单创建 | ✅ | ✅ | ✅ | ✅ | ✅ | ❌ |
| 工单处理 | 商机类 | 售后类 | 售后类 | 全 | 全 | ❌ |
| 业务关系激活 | ✅ | ❌ | ❌ | ✅ | ✅ | ❌ |
| 客户/联系人录入 | ✅ | ✅ | ✅ | ✅ | ✅ | ❌ |
| 公海规则配置 | ❌ | ❌ | ❌ | ✅ 本部门 | ✅ 全公司 | ❌ |
| 部门公海认领 | ✅ | ❌ | ❌ | ✅ | ✅ | ❌ |
| 跨业务线可见 | ✅（脱敏） | ✅（脱敏） | ✅（脱敏） | ✅ 明细 | ✅ 明细 | ❌ |

**敏感字段脱敏规则**（跨业务线/跨部门/非归属时）：

| 数据 | 脱敏范围 |
|---|---|
| 合同金额 | 完全脱敏（不显示数字） |
| 合同续约日期 | 仅显示"还剩 X 月" |
| 他人私海跟单记录 | **不可见**（非协同时；协同人 = 共同跟进全文） |
| 公司公海客户的跟单记录 | 仅显示"近 30 天跟进 N 次"（让销售判断值不值得领，不泄露具体话术） |
| 跨业务线跟单记录 | 仅显示"近 N 天内跟进 M 次" |
| 工单详情 | 仅显示"N 个工单进行中" |
| 对接人姓名 | ✅ 完全可见（资源调动：知道谁在对接，能对得上人） |
| **对接人电话** | 归属本人/协同人=全号；非归属部门联系人=**仅后 4 位** `****8000`，可「一键申请解锁」（经理审批后限时可见全号，防批量捞号） |
| 公司业务线列表 | ✅ 完全可见（含签约日期） |

> **跟单记录可见范围（销售，V2.1 裁决）**：① **公海客户**（公司公海/部门公海）→ 可看近 30 天跟进次数概览；② **本人私海** → 全文；③ **协同跟进的关系**（`collaborator`）→ 全文且可共同写；④ **他人私海** → 不可见（本部门同事、跨部门同事均不可见，除非走协同审批）。

## 三、核心业务流程

### 3.1 业务关系全生命周期（核心流程图）

```
【阶段 0：线索/联系人】
  电销/陌拜/表单/导入 → 录入联系人档案（手机号 + 基础信息）
            ↓
【阶段 1：建立业务关系】
  联系人足够明确 → 选择产品线 × 部门 → 激活业务关系
            ↓  → 自动建立：业务关系（企业 × 部门 × 产品线 × 对接人 × 销售）
            ↓
【阶段 2：意向跟进】
  销售在业务关系下写入跟单记录（仅绑联系人）
            ↓
【阶段 2.5：公司档案补全】
  成交前/后必须补全公司档案（统一社会代码 等）
  跟单记录自动从联系人同步到公司档案
            ↓
【阶段 3：签约成交】
  创建合同 → 自动结算签单人业绩 → 维护人 = 签单人
            ↓
【阶段 4：交付与回访】
  工单转交付 → 服务中 → 续约预警 → 回访 → 续约/流失
            ↓              ↑
            └────── 维护人 持续跟进
```

### 3.2 资料/线索录入规则

| 入口 | 录入内容 | 落点 |
|---|---|---|
| 电销/陌拜 | 联系人档案（手机号必填） | 员工私海 |
| 调研表单 | 联系人档案 | 部门公海 |
| 批量导入 | 联系人档案 | 部门公海 |
| 系统采集 | 联系人档案 | 部门公海 |

**关键**：录入时**允许只有手机号**——成交后才强制补全企业档案。

### 3.3 业务关系激活规则

#### 3.3.1 触发条件
销售从员工私海或部门公海领取联系人 → 选择**产品线** + **所属部门** → 系统检查是否已有同业务关系。

#### 3.3.2 唯一性约束

```
1 个业务关系 = 1 个企业 × 1 个部门 × 1 个产品线

违反规则的处理：
├─ 同部门同产品线已有归属 → 后到者申请转交/协同
├─ 跨部门同产品线 → 可并行（竞争关系）：双方都能见客户、各自跟进，**但跟单记录互不可见**（防策略泄露，见 §8.1 场景 3）
└─ 同部门不同产品线 → 可并行（独立业务关系）
```

#### 3.3.3 激活顺序锁定
- 第一个点"激活"动作的销售 = **该业务关系的主对接销售**
- 系统按时间戳记录，无法被覆盖
- 后到者必须申请转交（系统走转交流程）

#### 3.3.4 维护人切换
- 维护人 = 默认主对接销售
- 维护人变更（离职/转岗）时：原维护人卸任、新维护人接管
- 签单人业绩归属不随维护人变更加载

### 3.4 公海自动掉落规则

#### 3.4.1 触发逻辑（按业务关系维度）

```
业务关系中满足以下任一：
├─ 跟进频次未达标（最近 N 天无跟单记录）
├─ 成单周期超时（激活 N 天未签约）
└─ 推荐进展停滞（连续 N 次跟进无推进）

维护人 ≠ 客服/专员岗位
└─ 触发掉公海流程
```

> **客服角色不触发**自动掉公海（运维中客户不被误丢）

#### 3.4.2 掉公海方向

```
业务关系从【员工私海】↓ 触发后落到【部门公海】
   ↓ 部门公海停留超过部门设定时间
   └─→ 落入【公司公海】
   （注：员工的业务关系被释放）
```

#### 3.4.3 规则配置层级

| 配置项 | 设置人 | 作用范围 | 优先级 |
|---|---|---|---|
| 全局默认规则 | 老板 | 全公司 | 最低 |
| 产品级规则 | 老板 | 指定产品全公司 | 中 |
| 部门级规则 | 部门经理 | 本部门所有产品 | 中 |
| 部门×产品规则 | 部门经理 | 本部门指定产品 | 最高 |

#### 3.4.4 各产品线推荐默认值

| 产品线 | 跟进频次 | 成单周期 | 部门公海停留 |
|---|---|---|---|
| 网站建设 | 3 天 | 30 天 | 7 天 |
| 短视频推广 | 3 天 | 15 天 | 5 天 |
| GEO 优化 | 5 天 | 60 天 | 10 天 |
| 财税 | 5 天 | 20 天 | 7 天 |
| 招牌网 | 5 天 | 20 天 | 7 天 |
| 房产网 | 7 天 | 30 天 | 7 天 |
| 法律咨询 | 5 天 | 25 天 | 7 天 |

### 3.5 工单与商机的双向流转

```
┌────────────────────────┐    ┌────────────────────────┐
│  售后工单（后端处理）  │    │  商机工单（销售对接）  │
│  ───────────────────  │    │  ───────────────────  │
│  来源：客户反馈/       │    │  来源：客户反馈升级/   │
│   交付登记/系统触发     │    │  客服回访信号/销售挖掘 │
│  处理人：交付部门       │    │  处理人：销售/客服      │
│  关联：业务关系         │    │  关联：业务关系+原工单  │
└──────────┬─────────────┘    └──────────┬────────────┘
           │                            │
           └─→ 双向可升级 ←─────────────┘
           售后 ↔ 商机
```

## 四、客户与联系人档案（二阶段建模）

### 4.1 二阶段建模总览

```
┌─────────────────────────────────────────────────────────────┐
│  阶段一：联系人档案（成交前主要存储）                          │
│  ────────────────────────────────                          │
│  · 唯一标识：手机号（必须）                                   │
│  · 可在签单前后一直使用                                       │
│  · 公司信息可空（仅当未明确时）                                │
├─────────────────────────────────────────────────────────────┤
│  阶段二：公司档案（成交后强制补全）                            │
│  ────────────────────────────────                          │
│  · 唯一标识：社会统一代码 或 公司全称匹配                      │
│  · 必填：社会统一代码、营业执照、法人、注册地址               │
│  · 与联系人档案 N:M 关联                                     │
└─────────────────────────────────────────────────────────────┘
```

### 4.2 联系人档案（独立表）

**核心字段**：

| 字段 | 类型 | 说明 |
|---|---|---|
| **联系人 ID** | 系统自动 | 唯一主键 |
| **姓名** | 文本 | 必填 |
| **手机号** | 文本 | **唯一索引**，防重复 |
| **微信号** | 文本 | 可选 |
| **邮箱** | 文本 | 可选 |
| **性别** | 枚举 | 男/女/未知 |
| **生日** | 日期 | 可选（生日营销用） |
| **关键决策权** | 枚举 | 决策人/影响人/执行人 |
| **个人标签** | 多选 | 自定义（如：技术偏好、人脉资源） |
| **就职历史** | 表 | 公司名称 + 起止日期 + 在职状态（当前/历史） |
| **关系网络** | 关联 | 谁推荐的/推荐了谁 |
| **变更历史** | 表 | 手机号、姓名等变更留痕（经理审核记录） |
| **历史跟单记录** | 关联 | 自动聚合 |
| **备注** | 富文本 | — |
| **创建时间** | 日期 | 系统自动 |
| **更新时间** | 日期 | 系统自动 |

**关键规则**：
- 手机号唯一索引，变更需要经理审核
- 在职状态（当前就职公司 / 离职公司 / 自由职业）

### 4.3 公司档案（独立表）

**基础字段**：

| 字段 | 类型 | 说明 |
|---|---|---|
| **公司 ID** | 系统自动 | 唯一主键 |
| **公司全称** | 文本 | **必填**，系统校验唯一性 |
| **社会统一代码** | 文本 | **成交后必填**，系统校验唯一性 |
| **简称** | 文本 | 可选 |
| **行业** | 字典 | 一级/二级行业 |
| **规模** | 枚举 | 微型企业/小型/中型/大型/集团 |
| **地区** | 字典 | 省/市/区 |
| **注册资本** | 数字 | 成交后填 |
| **法人** | 文本 | 成交后填 |

- 社会统一代码如有 → 强匹配（强制使用已有档案）

### 4.4 公司档案完善度（强制验收项）

公司档案分为**两阶段补全**：

| 字段 | 录入联系人时 | 成交前 | 成交后强制 |
|---|---|---|---|
| 公司全称 | 推荐填 | 必填 | 必填 |
| 社会统一代码 | 可空 | 推荐填 | **强制必填** |
| 行业 | 推荐填 | 必填 | 必填 |
| 地区 | 推荐填 | 必填 | 必填 |
| 注册资本 | 可空 | 推荐填 | 必填 |
| 法人 | 可空 | 推荐填 | 必填 |
| 注册地址 | 可空 | 推荐填 | 必填 |
| 联系人（手机号） | 必填 | 必填 | 必填 |

**强制规则**：成交时公司档案**未达到"成交后必填"**的标准 → **禁止签约**，必须先补全。

### 4.5 跟单记录的迁移规则

```
【成交前】
  跟单记录 = 绑定【联系人档案】+ 标注"所属公司（可选）"
  
【成交后】
  跟单记录 = 自动迁移到【公司档案】下，绑定公司 + 联系人
  原绑定联系人不变，跟单记录同时出现在公司档案和联系人档案下
```

**迁移触发时机**：公司档案第一次"成交后必填"全部补全的那一刻。

**特殊场景处理**：
- 一个联系人签单到**多级公司**（如母公司+子公司）→ 跟单记录按"签约对应公司"归入，不再拆分
- 同一联系人 + 多公司业务关系 → 跟单记录独立归档

### 5.3 业务关系激活顺序锁定

- **第一个激活的销售 = 主对接销售**（系统时间戳）

- **第二个销售可申请"协同跟进"**（= **共同跟进**，审批通过写入 `relation_member.member_type=collaborator`，可共同写跟单，可带有效期）
- **第二个销售也可申请"转交"**（需要主对接销售或经理确认）

> **跨部门同产品线**：可各自并行激活（竞争关系）——**但跟单记录互相不可见**（避免泄露跟进策略；谁先签约谁赢）。可见性裁定见 §8.1 场景 3。

### 5.4 意向跟进体系（V1.1 定稿）

> 本章把"怎么跟、跟得急不急、值不值得跟"做成可落库、可统计的资产。落库字段详见《数据库设计文档》V1.1 §5.1：`urgency` / `value_level` / `customer_level` / `gray_release_at` / `risk_tags_manual` / `coop_tags` / `company_profile_tag` / `contact_trait`。

**① 两字段正交（核心心法）**

| 维度 | 性质 | 来源 | 说明 |
|---|---|---|---|
| **进度（阶段）** | 客观事实 | `workflow_stage`（§6.5.2，6 步状态机） | 客户现在走到哪了 |
| **紧迫** | 主观计划 | `urgency`（5 档，全手动） | 我这周/月打算推谁 |

两者**互不替代**：一个客户可以"阶段在需求确认"但"紧迫=长期跟"，也可以"阶段在逼单"但"紧迫=周重点"。

**② 紧迫 5 档（手动标签，无自动降级）**

| 档位 | 含义（七叔原话） |
|---|---|
| **周重点** | 本周判生死的客户——标记即承诺本周动作 |
| **月重点** | 本月能够往前推进的客户 |
| **季度跟** | 季度内推进的客户 |
| **长期跟** | 有实力、决策人、适合做推广（MAN 资格已确认），时机未到 |
| **灰度（默认）** | 暂未下结论的客户 |

- **灰度寿命**：由 `dept_rule.gray_remind_days`（N 天未定性→提醒下结论）/ `gray_release_days`（再 M 天未动→置 `gray_release_at` 列为公海释放候选，经理确认后释放）控制。
- **周重点仅手动标签，无复盘机制**；客户等级档位与灰度规则均为**部门经理级配置**（`dept_rule`）。

**③ 两轴价值判断（不同轴）**

| 轴 | 计算方式 | 含义 |
|---|---|---|
| **客户等级** A/B/C/D | 系统**自动**（回款金额按本部门 `dept_rule` 档位算） | = 回款贡献 |
| **业务线价值** 高/中/低/待定 | **手动标记**（默认空，愿意标才标） | = 实力×契合度（开发价值） |

**④ 标签分层**

- **公司级标签（全部门通用、标注留痕可查谁打的）**：打法特征（如公司档案 `company_profile_tag`：身份/制度/决策链）。
- **关系级标签**：风险（`risk_tags_manual` 人工补 + 规则实时派生 `auto` 项只读回传）、协同（`coop_tags`，可 @ 同事：需陪访/技术支持/方案支持）。
- **联系人级**：谈判特质 `contact_trait`（≤3，跟着人走、换公司保留）。

> ⚠ **"协同"两种语义务必区分（V2.1 澄清）**：① **协同标签 `coop_tags`**（关系级，E09/E10）= 临时喊人"帮我看一眼/陪个访"，@ 同事即可，**不授跟单读权**；② **共同跟进人 `collaborator`**（`relation_member.member_type`，见 §5.3）= 经协同审批的**正式共同跟进关系**，**授予该关系跟单全文读写权**。前者是轻量标签，后者才是改可见范围的正主。

## 八、撞单与竞争规则（运营 SOP）

### 8.1 八大典型场景

| # | 场景 | 处理 |
|---|---|---|
| 1 | 同部门同产品线重复激活 | 后到者申请转交/协同 |
| 2 | 同部门不同产品线激活 | 并行，各自独立 |
| 3 | 跨部门同产品线激活 | **竞争并行**，各自都可跟进，但**跟单记录互相不可见**（防策略泄露）；谁先签约谁得 |
| 4 | 跨部门不同产品线激活 | 完全独立 |
| 5 | 维护人离职/转岗 | 维护人变更，业务关系更新 |
| 6 | 签单人离职 | 签单人业绩归公司，**不可变更** |
| 7 | 客户主动要求对接其他销售 | 主对接销售确认/部门经理重分 |
| 8 | 客户签单到多级公司（母子） | 按签约公司归档，不拆分 |

### 8.2 抢单与介绍费机制

- 同业务关系已有归属 → 后到者可申请**协同**（= **共同跟进**：审批通过成为 `collaborator`，可共同写跟单；区别于只读，见 §5.3 与《数据库 V1.2 §5.2》）
- **介绍费规则**：跨部门转介绍成交，介绍人拿 10% 提成（可在系统预设）
- 同部门内部转介绍 → 由部门经理分配，无介绍费

### 8.3 客情归属原则

- **签单人 = 业绩归属人**
- **维护人 = 客情归属人**（默认 = 签单人，可变更）
- 维护人变更 → 签单人业绩不变
- 离职时：维护人强制转交，签单人记录不动

## 十、技术与实施建议

### 10.1 关键技术选型

| 层级 | 推荐 |
|---|---|
| 前端 | Vue 3 + Element Plus + Vite + TypeScript |
| 后端 | **NestJS 12（Node + TypeScript）** |
| 数据库 | MySQL 8.0 + Redis |
| 异步队列 | **Redis（BullMQ）**——随 NestJS 技术栈复用 Redis，不引入独立 MQ（RabbitMQ 废弃） |
| 文件存储 | MinIO / 阿里云 OSS |

> **技术栈已定案（路线 B，2026-09-05）**：以《README》项目章程为权威。后端 NestJS 12、前端 Vue3+TS、全栈共用一套 TS 类型（后端 OpenAPI → 前端自动生成，禁止双真相源）。异步任务（掉公海扫描、续约预警、SLA 超时推送）统一走 Redis + BullMQ。详见《技术栈方案对比》结论与 README 路线 B。

### 10.2 实施风险

| 风险 | 应对 |
|---|---|
| 规则配置太灵活导致混乱 | 先用固定规则，加 UI 配置不要太多分支 |
| 客户数据被销售带走 | 严格角色权限 + 导出审批 |
| 公海规则误触发 | 预警机制必须做（推送+标红） |
| 业务关系混淆 | 激活锁定时间戳，维护人/签单人两个角色分清 |
| 跨部门协作扯皮 | 系统记录"介绍人"+提成比例预设 |
