# 销售 CRM 系统建设方案（高层摘要 V2）

> **面向**：老板 / 总经理 / 项目决策人  
> **目标**：一页纸讲清楚"我们要做什么、怎么做、投入多少"

---

## 一、为什么做这件事

**当前痛点**：

| # | 问题                     | 业务影响      |
| - | ---------------------- | --------- |
| 1 | 客户数据散落在 Excel 和销售个人微信里 | 员工离职=客户流失 |
| 2 | 公海机制靠人工喊话，规则跑偏         | 资源浪费、效率低  |
| 3 | 跨部门跨产品线撞单/丢单频发         | 内部竞争无规则   |
| 4 | 多产品线切换无差异化             | 服务质量参差不齐  |
| 5 | 管理者看不到实时数据             | 决策靠"感觉"   |
| 6 | 工单/商机/售后流程无系统支撑        | 沟通成本高     |

**我们的目标**：用一套系统支持**多业务线 × 多部门 × 多角色**的销售与交付协同，让人效提升 30%，客户流失率下降 50%。

---

## 二、客户模型（核心）

我们设计的 CRM 是一个**「公司档案 + 业务关系」**两层结构，区别于传统 CRM 的"客户表多份"模式：

```
第 1 层：公司档案（＝公司公海，1 家公司 = 1 个档案）
         全公司共享、全员可见 —— 它就是客户名单本身
   ↓
第 2 层：业务关系（CRM 的最小业务单元）
         粒度是"关系"不是"公司"：部门 × 产品线 × 销售
         （＝本部门公海里的一条；掉公海 = 这条暂时没有归属人，部门不变）
```

> **口径说明（2026-09-10 更新）**：早期表述为"公司公海 → 部门公海 → 员工私海"三级；现已统一为上面两层 —— **部门公海不是独立一层**，它就是"本部门的关系集合"。公司档案全公司唯一，任何部门都能在它之上激活自己部门的关系。

**关键认知**：

- **公司主档案唯一** —— 同一家公司无论几个部门对接，都共享 1 个档案
- **对接人以手机号为唯一索引** —— 跳槽也保留历史，形成客户关系网
- **业务关系是核心** —— 跟单/合同/续约都围绕业务关系展开，一家公司可有多条业务关系（不同部门/产品线）
- **签单人和维护人分离** —— 离职不影响业绩归属，换人不影响客户体验

## 三、典型业务场景举例

**某客户"XX 教育公司"** 同时与我们公司合作 3 条业务线：

| 业务关系         | 部门   | 产品线    | 主对接销售 | 业务线关系     |
| ------------ | ---- | ------ | ----- | --------- |
| XX 教育·财税·小张  | A 部门 | 财税     | 小张    | 已签约 5 万/年 |
| XX 教育·GEO·小李 | B 部门 | GEO 优化 | 小李    | 跟进中       |
| XX 教育·网站·待激活 | A 部门 | 网站建设   | 待分配   | 跨部门竞争     |

→ 一个客户、三个业务关系、销售可独立跟进。**公司档案唯一共享**。

## 四、核心能力清单

### 4.1 第一期（MVP，12 周）

✅ 多部门/多产品线/多角色组织架构  
✅ **联系人档案独立**（手机号唯一、跳槽保留历史）  
✅ **公司档案分阶段补全**（**签约前**按本条业务线清单硬校验；**成交后**的档案字段改为可选补全、不强制、不计入完善度）  
✅ **业务关系**为最小业务单元（激活/转交/协同）  
✅ **两层管理**：**公司档案（＝公司公海，全公司唯一共享）＋ 业务关系**（部门 × 产品线 × 销售）；「部门公海」＝ 本部门的关系集合，不是独立一层  
✅ 公海自动掉落（按业务关系 × 产品线）  
✅ 跟单记录 + 工作流阶段  
✅ 出门登记（只留三样：出去时间、去干什么、回来点一下；**不关联报销、不产生业务事件**）  
✅ 工单双分类（售后/商机）  
✅ 续约预警  
✅ 数据看板  
✅ **合同业绩分配**（默认谁签的算谁的；需要时在合同上填"给谁多少"）

### 4.2 第二期（V2）

📦 调研表单自动采集  
📦 批量导入工具  
📦 企业微信/钉钉对接  
📦 短视频/GEO 平台数据同步  
📦 数据导出审批 + 离职交接  
🚫 ~~抢单介绍费自动分账~~（**不做** —— 已改为「合同业绩分配」，见 §4.1）

## 五、撞单与竞争规则（核心运营 SOP）

| 场景          | 规则                |
| ----------- | ----------------- |
| 同部门同产品线重复激活 | 后到者申请转交/协同        |
| 同部门不同产品线    | 并行独立              |
| 跨部门同产品线     | **竞争并行**（各签各的、互不干扰；一方签约只提示不拦截） |
| 跨部门不同产品线    | 完全独立              |
| 维护人离职/转岗    | 维护人变更，签单人业绩不变     |
| 客户主动要求换对接   | 主对接销售确认/经理重分      |

## 六、实施投入与产出

### 6.1 投入估算

| 项    | 自研           | 采购二次开发           |
| ---- | ------------ | ---------------- |
| 工期   | 12-14 周 MVP  | 6-8 周            |
| 成本   | 50-80 万（含人力） | 15-30 万（SAAS 年费） |
| 灵活度  | 极高           | 中等               |
| 数据安全 | 完全自主         | 依赖厂商             |
| 适配度  | 100% 贴合业务    | 需业务妥协            |

### 6.2 建议路径

> **建议**：规模 10 人以下销售 → 采购主流 SAAS  
> 规模 30+ 销售/多业务线复杂 → 走自研（本项目按此规划）

## 七、风险与应对

| 风险        | 应对                            |
| --------- | ----------------------------- |
| 销售抵触、不愿意用 | 主管带头 + 强制要求 + 简化操作            |
| 数据迁移混乱    | 分批导入 + 专人校验 + 旧 Excel 保留 30 天 |
| 公海规则误触发   | 到期前 24h 推送预警，不"悄悄掉"           |
| 跨部门协作扯皮   | 系统留痕转介绍关系；业绩分配在合同上设置（默认归签单人） |
| 需求蔓延      | 严格按 MVP 边界，V2 再做扩展            |
